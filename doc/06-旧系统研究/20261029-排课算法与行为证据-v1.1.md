单班、多班、自动排老师和教室均属首版业务范围。保留旧算法的业务语义与优先级，建立真实基准后选择新算法，不要求逐行翻译或逐格一致；不锁定编程语言、求解器、内存结构或数据库。

## 1. 旧算法拆解

### 1.1 核心对象

| 对象 | 说明 | 旧实现 |
| --- | --- | --- |
| 班级 `Class` | 预设/新班/开班/结班/取消 | `ClassDictionary.java:12-16` |
| 班级课程设置 | 每门课需要排多少课次、绑定哪些教师 | `IAClassCurricula` / `IAClassCurriculaBox` |
| 课次 `CSItem` | 班级 + 日期 + 起止分钟 + 课程 + 教师 A/B/C + 教室 + 状态 | `H_CS_Item`、`TCSItemKey` |
| 时段 `TimeSpace` | 日期 + 分钟区间 | `TTimeSpace` |
| 占用 | 活动、休假、教室预订、非教务课时、其他系统占用都用“课次 + systemType”表达 | `TCSItemKey` |
| 冲突原因 | 15–23 种，分硬约束与提示 | `ClashTypeDictionary` |

### 1.2 编排流程

```
准备任务
  → 读取班级、课程设置、教师、教室、学员时间要求、休息日、活动、休假、预订
  → 预处理：为每个班级生成候选“日期×时段”对
  → 对每个候选对，判断是否可用（canUsed）
  → 按“不可用比例”排序班级（越受限越先排）
  → 逐班贪心排课
  → 排不下的课次，做深度 1–5 的交换搜索
  → 保存（逐条写课次、教师、日志）
```

关键代码：

- 预处理与贪心：`TSchool_IACS/.../iaprocessor/MCIACSItemAutoArrange.java:99`（排序）、`:151-206`（预处理）、`:210+`（逐班排课）。
- 单班贪心：`SCIACSItemAutoArrange.java:247-368`；时段评分 `computeScore` 在 `:693-719,789-856`。
- 深度交换：`CSItemAutoArrange.java:65`（深度 1–5）、`CSDeepSearchArrange.java:36-116`。
- 冲突检测：`AllClashCheck.java:84`（62 天窗口）、`:365`（按天全量取课次）、`:344-496`（逐项比较）。
- 索引：`CSItemBox_TRS.java:15-53`（班级/教师/教室/学员四个索引）。
- 保存：`IACSItemProcessor.java:129-148`（任务锁 + 班级锁）、`:246-267`（逐条写）。

### 1.3 约束清单

**硬约束（会阻断）**：

- 同班课次时间不重叠，且满足最小课间间隔（`ClassTimeSpaceCheck.java:89-105`）。
- 结班/取消班不能排课（`CSOperateValidate.java:104-129`）。
- 不能超过班级/课程购买课时（`CSItemUpdate_Operator.java:125`）。
- 已发布课次不能改成“无课程/无教师”（`:96-119`）。
- 自动排课不能移动锁定课次（`SCIACSItemAutoArrange.java:141-161`）。
- 教师、教室、学员在同一时段不能冲突（`ClashCheckProcessor`）。

**软约束/提示（可降级）**：

- 教师活动、休假、教室预订、教室生命周期、座位不足、跨校区距离、班级休息日、学员距离、其他系统占用。
- 旧系统在保存时冲突可能“清空教师或教室”而不是拒绝（`CSItemUpdate_Operator.java:286-315`），这是需要在新系统里明确的策略：**哪些冲突阻断、哪些只警告、哪些自动降级**。

**分类必须按操作定义**：人工保存、自动排课、发布、已确认后修改，分别定义阻断、警告与降级。旧研究对部分约束分类不一致，不能直接当作新系统已确认规则，需教务确认。

### 1.4 旧算法的优点

- 约束建模贴近业务：活动/休假/预订/非教务课时统一成“占用”，比较逻辑统一。
- 班级优先级合理：越难排的班越先排，符合人工排课直觉。
- 有局部修复：不是纯贪心，排不下会尝试交换。
- 与业务系统深度集成：排完直接发布/确认/关闭。

### 1.5 旧算法的问题

- 预处理对每个班级、每门课、每个候选时段做 `canUsed`，复杂度高。
- 每天重新全量加载当天所有课次，重复构建索引。
- 深度搜索分支因子大，深度 5 可能爆炸；失败后没有更好的回退。
- 逐条写库，事务大、锁持有时间长。
- 结果不可解释：只给冲突原因，没有“为什么排在这里”的评分依据。
- 无全局目标：教师连续上课、教室稳定、校区往返、每日均衡都没有优化。
- 单 JVM 内存模型，无法并行/多实例。

## 附录 A：旧算法代码级拆解

> 本节保留旧算法入口、流程和行为证据；不是新技术选型或实现进度。

### A.1 入口与分工

| 场景 | 类 | 说明 |
| --- | --- | --- |
| 单班排课 | `SCIACSItemRuleMSAutoArrange`（继承 `SCIACSItemAutoArrange`） | 一个班、若干门课、给定可用时段 |
| 多班排课 | `MCIACSItemAutoArrange` | 多个班，按班级优先级串行排，失败回滚 |
| 深度交换 | `CSItemAutoArrange` + `CSDeepSearchArrange` | 贪心排不完时，做深度 1–5 的交换搜索 |
| 冲突检测 | `IATaskDataModel.isHasClash` + `ClashCheckProcessor` | 教师/教室/学员冲突、距离冲突 |
| 冲突原因 | `ClashReasonsBuilder`、`ClashTypeDictionary` | 把冲突转成原因码，供界面显示 |

### A.2 单班流程（`SCIACSItemRuleMSAutoArrange`）

1. **预处理**（`preProcessor`，父类 `SCIACSItemAutoArrange:103-162`）
   - 为班级建立 `IAClassCurriculaBox`；
   - 读取班级已有课次，**锁定课次放回模型，不参与重排**；
   - 未锁定课次按时间排序，计算平均课次分钟数；
   - 计算班级剩余课次、课程剩余课次、课程前序规则。

2. **生成可用时段**
   - `getDateMultMS()` 把 `canUsedDateMultMS` 与 `autoMode` 的每日可用时段、午休/晚休、课间间隔合并；
   - 如果班级设置了“连排”，按最大间隔把一天切成若干候选时段组（`toMinuteSpaceListForContinue`）。

3. **时段组评分**（`pinggu` / `computeScore`，`:675-719`）
   - 对每个候选时段组，遍历“当前可排课程 × 组内每个分钟段”；
   - 用 `isCanSetToClass` 判断能否放下，能放一个加 1 分；
   - 分数 = 该时段组内可放下的（课程，分钟段）组合数；
   - 按分数从高到低排序，优先尝试“最宽松”的时段组。

4. **贪心排课**（`autoArrange(TDateMultMS)`，约 `:250-377`）
   - 对每个分钟段：
     - 取当天可排课程 `ccs`；
     - 默认取 `ccs[0]`；如果开启“时段利用优先”，则依次尝试多门课；
     - 如果当天第一堂课且教师“未开班”，尝试到第一个能开班的教师为止；
     - `isCanSetToClass` 通过后，写入模型、扣减课程/班级剩余课次、更新课程间隔；
   - 一门课排完就从 `classCurriculaBox` 移除。

5. **未排完的兜底**（`:56-89`）
   - 如果还有剩余课次，取已排课次的最后日期，把剩余课次**整体平移到该日期之后**；
   - 这是“保证有课次”的兜底，不是真正的排课；会突破原定结束日期，业务上需要确认是否保留。

6. **深度交换**（`CSItemAutoArrange:65`）
   - 若还有剩余，按深度 1..5 调用 `CSDeepSearchArrange.swapArrange`；
   - 在课次之间交换“课程/教师”归属，做深度受限的 DFS；
   - 深度越大，搜索空间指数增长；旧实现没有全局目标，只找“能放下”的交换。

### A.3 多班流程（`MCIACSItemAutoArrange`）

1. `preProcessor`：为每个班生成候选“日期×时段”对，标记可用/不可用。
2. 计算每个班的“不可用课次比例”（`getCanNotUsedCSItemCountParent`）。
3. `Arrays.sort(boxs)`：按不可用比例从高到低排，**越难排的班越先排**（`IAClassCurriculaBox.compareTo`）。
4. 逐班 `autoArrange`；每排完一个班，`removeCannotUsedPair` 重新评估后续班级的可用时段。
5. 某班失败时整批回滚（`MCIACSItemAutoArrange:1129-1139`），再交给深度搜索兜底。
6. 自动排教室：按教学区优先级试放，失败再跨班换教室（`AutoRoomPKProcessor`）。

### A.4 冲突判断

`isCanSetToClass(item)`：

```java
if (dataModel.isHasClash(item, true)) return false;      // 教师/教室/学员冲突
if (!isFirstTimeSpace(item.getTimeSpace())) return true;
if (dataModel.isHasNotOpenClassTeacher(...)) return false; // 第一堂课必须能开班
return true;
```

`isHasClash`（`IATaskDataModel:2019-2035`）依次检查：

- `isHasCurriculaTeacherClash`：教师时间冲突、教师跨校、教师距离、教师活动/休假/非教务课时；
- `isHasRoomClash`：教室时间冲突、教室距离/位置、教室预订、生命周期、座位；
- `isHasStudentClash`：学员时间冲突、学员距离、班级休息日。

冲突判断最终落到 `ClashCheckProcessor`（`TSchool_IACS/.../clashcheck/ClashCheckProcessor.java`），它按时间段重叠 + 资源匹配判断，距离冲突用 `DistancePool` 的校区距离。

### A.5 数据结构

- `IATaskDataModel`：一次排课任务的全量内存模型，含班级、课次、教师、教室、学员关系、其他占用；
- `CSItemBox`：按课次编码索引；
- `CSItemBox_TRS`：按班级/教师/教室/学员四维索引，`getItems` 取四类候选的并集；
- `TimeSpaceBox`：活动、休假、预订、非教务课时的时段集合；
- `LockPool`：按班级加 JVM 锁，防止并发改同一班。

### A.6 复杂度

- 预处理：`O(C × K × P × check)`，C 班、K 课程、P 候选时段；
- 贪心：`O(N × T × check)`，N 课次、T 每天时段；
- 深度搜索：`O(b^d)`，b 分支因子、d ≤ 5；
- 每天冲突检测：全量加载当天课次 + 四维索引 + 候选比较；
- 保存：逐条写课次、教师、日志。

### A.7 必须保留的行为

1. 锁定课次不被移动。
2. 班级按“不可用比例”排序，越难越先排。
3. 第一堂课必须有能开班的教师。
4. 同一班级时间不重叠 + 最小课间。
5. 教师/教室/学员三向冲突 + 跨校区距离。
6. 连排模式、时段利用优先、课程前序规则。
7. 多班失败回滚，不留下半成品。
8. 排完后的发布/确认/关闭链路不变。

### A.8 可以实现得更好、但不要悄悄改变的行为

1. **未排完课次整体后移**：旧实现会把剩余课次推到已排最后日期之后，可能超出班级结束日期。新系统应明确：是提示“排不下”、还是允许延期、还是自动加课；不能默默改日期。
2. **教师/教室选择**：旧贪心基本固定课程的默认教师，教室由后续流程分配；新算法可以在满足约束下优化教师/教室，但要允许锁定和人工覆盖。
3. **评分函数**：旧 `computeScore` 只数“能放几个”，没有考虑教师连续、教室稳定、空档、公平；新算法可以加软约束，但要可配置、可解释。
4. **深度搜索**：旧实现深度 5 且无全局目标；新实现可以用局部搜索/CP-SAT 替代，但必须保留“失败可回退、结果可解释”。
5. **冲突降级**：旧保存在冲突时可能清空教师/教室；新系统应明确“阻断/警告/自动降级”的策略，不能静默改数据。
