以下只记录旧系统的菜单、功能和字段结构，不包含客户数据或登录凭据，也不锁定新登录协议、账号表或角色实现。

## 1. 登录入口

一个登录页，四种身份单选：**员工 / 学员 / 家长 / 系统管理员**；表单字段 `username`、`password`，带“在此电脑上记住帐号”。

- 系统管理员与员工是**两套账号**，各自独立菜单。
- 学员/家长走同一入口，用手机号+密码（页面另有切换手机版 H5 的入口）。


## 2. 系统管理员菜单（实测）

| 一级 | 二级 |
| --- | --- |
| 基础数据 | 学校管理、部门管理、员工管理 |
| 账户与权限 | 系统管理员、员工账户、角色管理 |
| 系统配置 | 基本配置、系统控制、界面配置、导出配置、微信系统配置、在线支付配置、客户资源配置、第三方平台配置、功能扩展配置、智能排课配置 |
| 系统资源 | 短信资源 |

注意：**系统管理员菜单里没有“校区管理”**。校区在员工侧菜单「组织与资源 → 组织结构 → 校区管理」（`/t/org_resource/area`），系统管理员账号也能直接访问该页面。

## 3. 组织相关页面（实测）

### 3.1 学校管理

- 列表列：编码、名称；操作：添加、修改、删除、设置 K12 标识、设置是否有效。
- 没有“校区”页签，校区是独立页面。

### 3.2 校区管理（`/t/org_resource/area`）

- 页签：**校区 / 校区分组 / 距离关系 / 校区可预约试听课程**。
- 操作：添加、修改、删除、更改校区编号、设置代表色、设置为虚拟校区、设置是否有效。
- 筛选：编号、名称、**所属学校**。
- 结论：`校区.所属学校` 是必填归属 → **学校 1:N 校区**；校区分组（大区）与“距离关系”（跨校区通行时间）都挂在校区上，是排课跨校区约束的数据来源。

### 3.3 部门管理

- 列：名称、**归属学校**；操作：添加、删除。
- 结论：**学校 1:N 部门**，与校区是两条平行的 1:N 分支（与 2026-10-26 业务确认一致）。

### 3.4 员工管理

- 列/筛选：编号、姓名、类型（正式员工 / 试用期员工 / 临时员工）、所属学校、是否有效。
- 操作：添加、修改、删除、审核、设置是否有效。

## 4. 账号功能（实测）

### 4.1 员工账户（`/user_popedom/employeeUser`）

工具条操作：

| 操作 | 说明 |
| --- | --- |
| 创建账户 | 弹窗只填 **账户名、密码、确认密码**；账户挂在员工上 |
| 删除账户 | 删账号，不删员工 |
| 删除微信公众号注册 | 解绑微信 openid |
| 重置账户名 | 允许改登录名 |
| 重置密码 | 管理员直接改密码 |
| 设置功能角色 | 选角色（实测角色示例：财务、教务、课程顾问、课程顾问主管、全权限、人力、市场、学习顾问…） |
| 自定义功能权限 | 在角色基础上单独加减功能权限 |
| 设置数据权限 | 见 4.3 |

筛选/列：员工姓名、用户名、类型、角色、所属学校；行内含 `Is_Audited`（审核）、`Is_Valid`（是否有效）等状态位。

### 4.2 系统管理员账户（`/user_popedom/system_user`）

- 操作：创建账户、删除账户、**设置可管理学校**。
- 列：账户名、系统内置（是/否）。
- 说明：旧系统的“系统管理员”不是租户概念，而是**部署级管理员**，靠“可管理学校”限定范围。

### 4.3 数据权限（实测到的维度）

从员工账户页与权限弹窗可见，数据权限按以下维度配置：

- 学校、校区（含“可选择所有教学区（包含无效校区）”）、部门；
- 渠道来源（客户资源渠道，单独弹窗选择）；
- 客户资源可见范围（如“登记报名时可选择校区权限范围内客户资源”）；
- “更改所属学校”这类高危操作单独作为权限项。

### 4.4 角色管理（`/user_popedom/role`）

- 列：名称、备注；操作：添加、修改、删除、查看权限列表。
- 角色只承载**功能权限**，数据权限在账号上单独设置。

## 5. 对需求核对的意义

目标需求需保留账户创建、改名、密码管理、启停、删除、角色、账号级增减和数据范围；具体状态与界面重新设计。平台运营账号与租户管理身份区分；旧“可管理学校”不是跨租户权限。

渠道、教学项目等细粒度范围和岗位矩阵仍需确认。历史观察不能代替真实客户启用情况，也不能自动证明新系统的权限策略完整。
