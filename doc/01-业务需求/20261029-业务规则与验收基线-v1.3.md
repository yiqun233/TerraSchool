## 1. 规则来源与追踪

每条重要规则应建立台账：规则 ID、业务含义、旧代码/表/手册证据、适用机构和配置、目标规则、验收输入与预期、确认状态、对应任务。旧代码、注释、文档和财务预期冲突时登记差异，不直接照搬。

以下是业务基线，不是已设计完成的 ER、接口或全部公式。迁移兼容与新业务规则必须有明确版本和生效边界。

## 2. 组织、账号与权限

- 租户、学校、校区、部门、员工、教师、学员和家长各自具有稳定身份；显示名称、手机号和登录名不能代替稳定主键。
- 学校下的校区、部门平级；部门若树形，父子属于同一学校，禁止成环，移动、删除和历史引用规则明确。
- 员工档案与账号分开；删除或停用账号不等于删除业务人员和历史操作记录。教师有独立业务角色与资源属性，不因“员工上增加标识”就视为完整教师模型。
- 功能授权、数据范围和字段敏感级别分别处理；角色权限与账号增减合并后执行 deny 优先。
- 数据范围可按具体业务动作区分，包含学校、校区、部门、本人、团队；渠道、教学项目、金额类型等维度按问题清单确认，不能丢失旧系统使用需求。
- 查询、详情、关联选项、统计、导出、附件和写操作受一致授权；上级范围 allow 不能跳过子范围 deny。
- 管理他人权限时检查目标原有及修改后的最终有效权限与范围，禁止通过删除 deny、清空配置或全局范围绕过委派边界。
- 保护最后一个有效权限管理员；授权集合的并发替换不得变成多个请求的意外并集。权限、组织树等跨行不变量有统一并发协议。
- 登录名变更保留稳定账号身份及审计。租户停用、账号停用、权限撤销需要影响有效会话与待执行任务。
- 预置角色矩阵需业务确认，历史角色名不等于目标系统已批准授权。

## 3. 学员、产品、报名与收款

- 学员、家长/联系人及其关系分别建模；同一手机号可能关联多个学员，不能默认自动合并。
- 客户资源、学员主档与报名区分；查重、合并、归属变更及例外操作可追溯。
- 一条报名是一个履约单元；多产品、多班业务可能生成多条报名，不能简化成一个金额字段。
- 课程、班型、产品、价格与优惠保留版本和生效范围；报名记录当时适用规则，后续改价不能改写历史承诺。
- 报名与实际收款、收款分配分开；定金、尾款、服务费和账户余额具有明确流转。
- 支付分配守恒，不能超分、漏分或重复入账。团培的付款单位、参训学员、费用分配与普通报名区分。
- 转班、退班、延期、报名审核与反审核显式建模，并检查关联金额、课时和历史状态。

## 4. 金额、课时与结算

### 4.1 精度和历史单位

金额与课时必须精确计算，禁止二进制浮点作为权威金额/课时表示。DEC-011 已确认新系统采用 BigDecimal/PostgreSQL numeric，接口用十进制字符串并显式金额/课时单位；不再将权威数值类型列为全新未决项。具体字段精度、舍入、尾差、序列化配置与显示规则按业务金标准统一，不因类型确定就重算固化历史或强制全部两位小数。

旧系统的历史单位是迁移事实：金额按分、课时按 0.01 课时、时间段按分钟；部分消耗金额为“分 × 60”。逐列记录放大倍数，禁止以字段名称猜测单位。

旧代码存在除法和注释不一致：例如 `800/50=160` 注释实际应为 16；尾差代码 `1000*60` 对应旧单位下 10 元，注释写 5 元。保留为待对账证据，不自行更改为另一个业务阈值。

### 4.2 模式范围

| 编码 | 旧系统含义 | 要求 |
| --- | --- | --- |
| 0 | 自动选择计算路径 | 提取选择条件及回退逻辑，单独验收 |
| 1 | 平均价格 | 用真实案例验证金额、课时、尾差 |
| 2 | 课程匹配 | 记录课程映射和费用分配口径 |
| 3 | 完全匹配 | 记录匹配条件和不足/剩余处理 |
| 4 | 平均价格下“退课时后实际费用”变体 | 验证退费后剩余费用/剩余课时及单价重算 |
| 5 | 完全匹配下“退课时后实际费用”变体 | 独立覆盖退费、续算、尾差案例 |

六编码和团培全部保留，不能只实现模式 1–3。具体公式与自动选择规则须由旧实现及财务预期共同确认。

### 4.3 不变量

- 课次关闭是既有业务的消耗与收入确认点；收款统计与收入统计不可混用。
- 退课时、退款、账户退回、现金退出、错误冲销、服务费退费及差额是不同业务事实。
- 已固化历史不直接重算或覆盖；调整通过明确的差额/冲正单据表达。
- 每条报名与课次的消费明细不得重复；汇总可从明细重算并对账。
- 旧退课时与退费字段可能表达累计值，不能当作本次增量重复应用。
- 学校锁月后限制回写；旧差额月份的 `max(锁定月+1,课次月)` 行为纳入案例，边界月份需财务确认。
- 收款与分配、课次关闭与消耗、退款与流水、转班与费用课时转移、锁月与结算保持业务原子性；不可只靠异步事件最终凑齐。
- 已结算历史按旧值固化，在读业务按冻结的规则版本承接，新业务按生效规则处理；规则变化必须可解释、可追溯。

## 5. 排课、课次与考勤

- 单班、多班自动排课、自动排老师、自动排教室均属于 P0；算法先建立等价行为基线，再评估优化，不锁定求解器。
- 生命周期、锁定、补课/合班等标记与财务固化状态分别建模，既不照搬多布尔，也不合并成一个不能表达并行维度的大枚举。
- 锁定课次不可被自动移动；教师、教室、学员和同班的时间冲突需要确定性判断。
- 跨校区通行时间、活动、休假、教室容量/生命周期、课程顺序、连排和休息日纳入约束目录。
- 按“人工保存、自动排课、发布、确认后修改”分别规定阻断、警告和降级；旧资料分类存在冲突，未确认前不得做全局一刀切。
- 自动排不下时返回明确原因；延长班级日期、清空教师/教室、自动改变课程不能成为静默兜底。
- 方案、草稿、发布、确认和财务关闭是不同业务动作；未来 AI 可以保存草稿，发布和通知另有确认。
- 计算结果基于明确输入及资源版本，提交时重新检查变化与冲突；多人、多任务竞争不能产生双重占用。
- 自动排课验收看硬约束、完成率、教务盲评及解释，不要求与旧系统逐格一致。
- 缺勤、请假、补课、换课对消耗的影响逐项明确；“默认上课、只记例外”的具体适用规则待业务确认。

## 6. 报表、审批、导入导出与打印

- 指标记录业务定义、单位、时间归属、维度、权限和版本；页面、导出与未来 AI 共用受控查询契约。
- 自由组合限于已定义的指标和维度，不允许任意模型生成 SQL 直接执行；跨域关联不能产生重复聚合。
- 既有 P0 报表候选为 11 项报表/查询及 1 项导出能力，详见功能清单；不能把导出算作一张统计口径。
- 固定审批候选为转班、退班、延期、退费、优惠、减款/服务费调整六类；通过、拒绝、撤回、失效和执行失败有明确状态。
- 导入先校验、展示影响及错误，再按规则入库；大任务可重试，部分成功语义明确；导出和下载重新检查授权。
- 合同、收据、听课证和课表可打印，支持套打配置；DEC-021 已确认统一 PDF 流程与 HTML/Chromium 首选方向，具体版本/效果后验、模板编辑方式待定，不要求像素级复刻。
- 首版发票仅记录号码、抬头、税号与状态，不接税务开票；高级发票管理后续评估。

## 7. 数据迁移与历史承接

| 模式 | 内容与约束 |
| --- | --- |
| FULL | 全量必须支持；完整保留历史业务、关键字段、附件与关联，不要求逐表照搬为新业务表 |
| OPENING | 主数据、在读报名、余额、剩余课时、未关闭课次，以及继续计算所需累计消耗、已退累计、固化金额、规则版本 |
| HYBRID | 指定明细范围与更早汇总，清楚说明可查询与可继续办理范围 |
| CUSTOM | 按实体、学校、校区、时间等选择，自动补足依赖闭包 |

迁移从旧库最终结构与脱敏样本出发；历史 SQL 是考证材料，不是可安全直接重放的迁移脚本。源资料只读，清洗在隔离环境完成；我方执行剖析与清洗，业务确认规则与抽查结果。

建立可重复的发现、剖析、映射、试装、校验、对账、切换流程；每次运行记录输入快照、规则版本、变更边界、去重和差异。部分迁移不能按单表条件简单截断。

历史承接区分“完整保留、可查询、可继续办理”；正在履约业务必须续算，后续功能的数据也要保留与可定位，不能只复制文件就声称迁移完成。

数量、金额、课时原则上零差异；例外逐笔记录旧值、新值、原因、处理结论与确认。切换前业务与财务共同验收；开放新写入前后的回退方案分开，写入后不能靠旧快照直接丢弃新交易。

## 8. 验收案例最低结构

每条案例有 ID、来源、前置状态、脱敏输入、操作、预期业务结果、金额/课时/状态/审计结果、拒绝场景与确认状态。对外报表和排课验收需要旧结果或业务确认结果作基准。

| 专题 | 必须覆盖 |
| --- | --- |
| 金标准 | 模式 1–5 各至少两例；模式 0 的选择分支；4/5 退费后续算；团培、尾差、跨课程分配 |
| 业务闭环 | 线索到两班报名、定金与尾款、排课、考勤、课次关闭、部分退款、对账 |
| 失败与并发 | 重复提交、超时重试、两人退款、关课与退费并发、锁月与结算并发、任务重启 |
| 授权 | 跨租户、同租户越范围、deny 组合、字段与导出、授权撤销、委派及最后管理员 |
| 排课 | 单班与多班、资源冲突、跨校区距离、锁定、无解、取消、提交时资源变化 |
| 迁移 | 全量、部分依赖闭包、在读续算、重复运行、历史只读、业务开放后回退 |

上述案例应随业务阶段实现，不因尚未接入大模型而省略多入口调用验证。
