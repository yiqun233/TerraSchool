## 1. 总体判断

**项目已具备有测试支撑的基础业务闭环，正在从 R5 首片进入 R6 的局部扩展；完整 P0、真实迁移和生产交付尚未完成。建议先安排一次收敛纠偏，再扩大业务覆盖。**

审阅基点为 Git `1b39264`，审阅开始时工作区无已有修改。范围是当前新工程及现行需求、设计、计划、问题和验证材料；未重新逐项研究全部旧源码、手册或客户合同。本轮未操作真实旧库、生产系统或远程 Runner。没有把测试数量折算为项目完成百分比，也没有推断用户已验收。

已有价值：模块化单体、租户事务和 RLS、账号与组织授权、发布后价格冻结、账户流水、课次关闭固化消费、退到账户与现金退出分离，均形成了实际代码和测试。SC01 的 1000 元/10 课时、消费 100、退 200、现金退出 200 主例已有自动化闭环。继续沿用这些基础，无需推倒重建。

主要风险是**实现范围扩大得快，业务口径确认、异常组合验证和当前状态维护没有同步收敛**。本次发现的课时边界、防重复、迁移和 CI 问题表明，既有回归通过还不足以证明所有组合成立。

本轮在隔离源码和临时数据库中重跑：既有后端 **250 项**、前端 **47 项**通过；追加 **3 项定向探针全部失败**，确认购买 4 课时仍可消费 4.5、模式 2 提前停止消费、相同 400 元优惠请求重复减应收（2000 变 1200，预期 1600）。这些属于待修复的实际缺陷，不能用原回归通过抵消。

## 3. 发现与纠偏要求

优先级“阻断”指阻断相关功能验收或真实业务写入，不要求暂停所有无关开发。下表问题本轮登记，业务代码修复留在执行路线，未宣称已经修复。

### AUD-01｜课时跨上限仍会整节计入，模式 2 的封顶维度也有偏差｜阻断

证据：`TeachingService.closeWithTrace` 先以 `consumed >= feeHours` 判断是否跳过，随后直接写入整节 `lessonHours`；没有处理“剩余 0.5、课次 1”这样的跨界，也没有对大于上限的课次统一拒绝或裁切。按课程取价后又把 `feeHours` 改成课程课时，模式 2 虽按总已消耗比较，比较上限仍是该课程课时；与设计中的“模式 2 按报名总课时封顶”不符。

风险：课时可超耗，尾差分支只在恰好相等时触发；模式 2 可能提前停止消费。后续迁移续算、退费与收入都会受影响。先确定超界是拒绝、截断还是拼接；在未实现拼接时至少保证不产生超耗。补齐小数跨界、不同课程交替消费、退课后继续消费等案例。

### AUD-02｜优惠请求号未参与幂等，且允许在已有消费/分配后继续改价｜阻断

证据：`ApplyDiscount` 含 `requestId`，`EnrollmentService.applyDiscountWithTrace` 没有读取它，也没有登记请求摘要；相同请求再次执行会再插一条优惠及应收减项。该方法只校验 ACTIVE 与净应收，未检查已有消费或资金分配，没有接优惠审批、财务期间或资金重新分配。

风险：网络重试会重复减应收；全额分配后减免可能使有效分配大于净应收；已消费后追加优惠又会改变后续课时计价，而历史已消费不重算。应先修防重和不变量，再决定“仅消费前允许优惠”还是提供版本化调整单。具体权限和审批由 Q38/Q39 讨论。

### AUD-03｜待确认业务不能一律按“解释性实现”进入真实资金规则｜阻断相关口径验收

证据：既有 Q1～Q12、Q34～Q37，涉及服务费退费、NORMAL 班模式 0、缺勤、优惠、退费和锁月。当前按最近提交，消费模式 **1/4 扣优惠、2/3/5 不扣**，退课时仍按对应原价/课程规则；旧 Q2 的“全部不扣”已过期。

需要区分：兼容旧行为是当前实现依据，不自动等于财务认可；用户此前要求照旧系统的方向仍保留，不能在本轮擅改公式。将这些分支标记“已实现、待口径验收”，以同一组应收/消费/可退/现金案例一起确认，避免分次补丁互相抵消。历史规则与未来修正规则需版本边界。

### AUD-04｜审批没有默认闭合，范围只覆盖退费两动作｜阻断生产退费开放

证据：`ApprovalService.ACTIONS` 只有 `REFUND_HOURS`、`CASH_REFUND`；`consume` 在策略缺失或停用时直接返回。初始化脚本未创建强制退费策略。优惠没有接审批调用。

现有禁止自批、金额匹配与一次消耗是有效基础，但不等于 P0 六类审批已完成。建议生产显式选择“必须审批/明示免审批”，缺失配置拒绝高风险动作；学校开通与上线预检均检查。默认规则和岗位阈值由 Q9/Q10 确认。

### AUD-05｜迁移直接写其他领域表，绕过统一业务约束｜阻断真实迁移

证据：`LegacyMigrationService.commit` 直接插入 `archive.student/contact/student_contact`、`funds.receipt/account_entry`，没有通过对应领域导入契约；收款导入路径没有调用 `PeriodGate`，也没有正常收款审计。虽持有机构锁，但没有与普通资金写入相同的事务内权限复核。暂存冲突键只用 `(tenant_id, legacy_id)`，缺源库命名空间；跨源/跨校旧主键重复的行为需专项验证。

应给领域增加受限的迁移入口，由领域统一校验、隔离、日期、审计与记账；只让迁移模块编排映射。不能因为是离线工具就直接绕过已确认边界。

### AUD-06｜期初导入和对账没有稳定绑定目标报名与批次｜阻断真实迁移

证据：`importOpenings` 只按学员号选最新 ACTIVE 报名；一名学员多条报名时无法指定正确履约单元。余额、课时和行记录分别提交，未形成注释所称“每行独立事务”；余额成功后课时失败可能返回 FAILED 但余额已入账。找不到在读报名会写“课时未带入”，仍可能计 OK。`dryRun` 的缺学员分支在判断干跑前写入 `opening_row`，正常干跑也写 `migration.run`，且没有执行完整金额/期间/报名校验。

对账把该学员**所有** OPENING 金额及所有报名的期初课时与一个批次期望比较，没有按本批来源核对，也没有核对 `consumedAmount`；多个批次会互相影响，错报名可能仍汇总相等。应持久化源快照、批次、行、目标报名、金额/课时/消费额与状态，明确部分成功和修复重跑，干跑只预检。

### AUD-07｜迁移候选建议会丢失业务语义，且部分对账等式错误｜阻断方案照单实施

原候选表建议丢弃拼接、锁账、多教师、退班状态，甚至把退班报名迁为 ACTIVE；这些都不能用“当前新模型不支持”推导为允许丢弃。FULL 必须支持仍是基线，历史明细可归档承接，但不能消失或被当作当前可操作数据。

“旧实收 = 新 RECEIPT + OPENING”“旧费用−退费−消费 = 新账户余额”也不普遍成立。账户未分配余额、报名未收和未履约价值是不同量；消费当前不直接扣账户分录，不能混用。候选表已在本轮修订为需逐层对账、保留来源和状态的方案；C1～C6 仍待负责人选择，未自动批准任何迁移降级。

### AUD-08｜CI 文件存在可静态确认的执行缺陷｜阻断远程门禁验收

证据：两份流水线的数据库管理员密码与 PostgreSQL 服务初始化密码不一致；GitLab 的 Maven 镜像直接调用 `psql`，却没有安装/验证客户端。前端读取的 `shared/generated/api.ts` 被 `.gitignore` 排除，但前端 job 没有下载后端 OpenAPI 产物或运行 `generate`；后端也没有将契约作为 job 产物传递。两份 CI 不等同本地 `verify.py`，也没有运行旧库抽取自检。

先修 GitLab 主线：统一测试凭据来源、准备客户端与容器测试环境、传递 OpenAPI、冻结生成客户端并校验、明确测试不跳过和报告保留；实际 Runner 成功后才关闭 Q26。GitHub 是备用，不擅自启用双推。

### AUD-09｜恢复脚本可能强删已有目标库，且通过标准不足｜阻断作为交付工具使用

证据：`backup_restore_drill.py` 接受自由 `--target`，建库前无归属检查即 `drop database if exists ... with (force)`；甚至未拒绝 target=source。脚本本轮未执行。恢复使用 `--no-owner --no-privileges`，只查固定 10 张表行数、迁移记录数及 RLS 标志；没有恢复并验证普通角色授权、数据内容/金额课时、登录与业务继续办理。已有记录的核心业务表为 0 行。

先改为拒绝同源、拒绝已有库、生成唯一受控目标并核验归属；恢复演练覆盖库、附件、配置和密钥，普通运行账号真实读写/拒绝、完整主链与对账。现有结果只能称“小样本数据库 dump/restore 冒烟”，不能替代 pgBackRest/restic 配套恢复或 RPO/RTO 验收。

### AUD-10｜同步 CSV 会截断且没有公式防护｜阻断完整导出验收

证据：学员、报名、收款、课次导出均使用 `limit 5000`，没有超限提示或后续游标；CSV `cell` 处理逗号、引号、换行，没有处理以 `=`/`+`/`-`/`@` 开头的用户文本。

风险：用户容易把前 5000 行当成全量；电子表格打开时可能解释文本为公式。先让同步导出明确拒绝超限或标明不完整，并防护公式文本；随后按 DEC-020 落实持久任务、快照、下载鉴权和 xlsx。CSV 不算完整报表系统或正式票据。

### AUD-11｜架构门禁落后于新模块，领域服务继续膨胀｜较高

证据：`ModuleBoundaryTest` 检查 `.internal` 的名单只有 platform/identity/organization/archive/product/enrollment/funds，遗漏 teaching/approval/finance/migration；禁止领域依赖 server 的名单也遗漏 migration。迁移直接跨域 SQL 又无法被类依赖检查发现。`TeachingService` 同时承担课次、入班、结算、期初和导出，`LegacyMigrationService` 同时承担暂存、导入、期初、对账。

先补所有模块的边界检查和跨域表所有权清单；在修复真实用例时抽出计价、迁移编排和导出职责，避免为重构另造通用平台。UUIDv7 决策与大量 `UUID.randomUUID()` 实现也需形成明确差异记录；不建议为统一 ID 立即重写历史主键。

### AUD-12｜机构级锁保证一致性，但会串行化不相干业务｜需要容量证据

证据：多个领域写入共用 `SchoolWriteGuard` 的 `authorization:<tenant>` 事务 advisory lock，包括退款、关课、优惠和迁移。当前这是撤权/停校一致性的保护手段，不应直接删除。

风险判断是容量推断，尚无压测证明已发生性能故障。先定义一个机构的并发量、批量课次与导出规模，再测锁等待、事务耗时和连接占用；只有证据显示瓶颈后，设计授权版本/细粒度锁协议并回归撤权竞态。

### AUD-13｜文档以追加历史替代维护当前事实，已影响方向判断｜本轮部分纠正

证据：审阅开始时的 101 份 doc Markdown 中，导航、根规范、README 与路线反复追加相同批次；元数据仍停在 11-01，内容已到 11-03。功能清单称“全部实现未开始”，路线首部称首片未完成，后文又称闭环完成；问题 Q2/Q20/Q27/Q28 也滞后。

本轮建立按职责分工的索引、功能台账、审阅快照与当前路线；更新主要入口和过期问题，同时纠正两份结算设计的文件/正文版本不一致及模式 0、优惠和审批的过期表述。历史结果继续由功能设计、验证记录和 Git 保存，导航不再复制进度日志。尚未逐句重审全部旧功能设计，不把链接通过当作语义一致性全部解决。

### AUD-14｜P0 范围存在漏排风险｜阻断完整 P0 宣称完成

招生公私海/渠道/跟进、定金、转班退班延期、补课换课、全班生命周期、单/多班自动选老师与教室、教师本人工作台、核心指标报表、合同收据听课证打印归档、租户套餐与配额、短信、完整字典编号等，未因前序闭环实现而被取消。六类审批目前仅有退费一类的两个动作；四类 CSV 不能代表 11 项核心查询报表完成。

把这些能力逐项纳入功能台账和路线，先闭合已实现能力的正确性，再按招生、教务、经营交付三条依赖链补齐。范围变更必须由负责人明确确认，不能靠实现取舍隐式缩小 P0。

## 4. 推进方式需要调整的地方

1. 每批围绕一个可验收业务结果推进，同时交付正常、边界、撤权、重复、失败与对账证据；避免只累计接口和测试数。
2. 待确认项按影响面处理：会改变金额、权限、历史承接的项，在确认前限制对应验收和真实数据操作；其他功能可继续。删除原问题表“未回答不影响继续开发”的笼统承诺。
3. 财务金标准采用一个共享案例目录，写明来源、规则版本、人工预期、实际值与差异；不要让每个新测试都只重复当前公式。
4. 验证必须包含清洁源码生成链、浏览器主流程、岗位权限和真实迁移续算；已有 250 项后端测试仍可能漏掉本轮发现的组合。
5. 审阅结论用 AUD 编号、任务用 REV 编号、功能用 F 编号，互相引用；关闭问题要附证据，负责人验收单独留痕。
