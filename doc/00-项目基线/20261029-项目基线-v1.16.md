## 1. 项目定位

以旧版培训学校综合业务系统的业务逻辑、使用场景和数据为基础，重新设计并实现支持多租户 SaaS、客户独立部署、Web 与移动端场景的新系统。升级操作体验、可靠性、权限、可维护性和扩展能力，保留有实际业务价值的功能。

业务主链为：招生获客 → 学员与家长 → 报名 → 收款与支付分配 → 分班排课 → 上课与考勤 → 课时消耗与结算 → 退课时、退费、差额与报表。

旧系统提供业务证据和迁移来源，不要求逐行翻译代码、照搬表结构、复刻页面或保留已确认的安全缺陷。已结算历史与现行业务规则要有明确承接与变更边界。

业务范围与主要规则已有基线。当前重点是确定开发规范、文档规范、项目结构、技术选型及其他开工准备；不要求重新进行全量业务确认。具体功能的代码对照、金标准和例外核验随开发进行，仅实际歧义或变更需要再次确认。

## 2. 本次重启的范围

- 上一轮新项目的实现全部废弃，重新开始开发；已有实现进度不继承。
- 上一轮开发计划、技术决策、代码评审、实现随附设计和归档不保留为当前依据。
- 保留旧系统原始参考资料，提炼并保留仍有效的研究证据与业务需求。
- 原评审中关于统一业务入口、权限、幂等、任务、审计和 AI 预留的原则重新编写为技术中立要求；“保留现有代码和技术栈”的结论不再有效。
- R0 只建立文档基线；用户随后明确授权 R3 最小技术验证，已形成独立原型和实际结果，见[核心技术组合验证记录](../03-研发规范/工程质量/验证记录/20261031-核心技术组合验证记录-v1.0.md)。用户于2026-10-31授权正式初始化，现已创建首批账号/组织查询工程，不接入 AI；Git 提交与推送按每次任务的明确授权执行，主仓库及 CI 平台见 DEC-013。

## 3. 已确认的产品与业务约束

| 编号 | 要求 |
| --- | --- |
| BASE-01 | 标准产品以多租户 SaaS 为主，支持大客户独立部署和客户内网部署 |
| BASE-02 | 租户代表机构/品牌；机构内有多学校；学校下校区与部门是两条平行分支，不是校区下挂部门 |
| BASE-03 | 学校承担财务主体、锁月、收入及合同归属；校区承担教学地点、教室与跨校区距离；部门承担归属、审批和业绩 |
| BASE-04 | 用户是租户内独立账号；同一人在不同租户的身份相互独立；平台运营身份独立 |
| BASE-05 | 管理端承接旧桌面能力，不发布旧式桌面客户端；移动端按教师、家长和学员的高频场景提供能力 |
| BASE-06 | P0 必须形成完整业务闭环，单班与多班自动排课均在首版；并非只上线组织和账号管理 |
| BASE-07 | 旧系统出现过的结算模式 0–5、团培、退课时、退费、冲销、差额和锁月均保留 |
| BASE-08 | 未明确放弃的旧业务进入后续范围，不因重启遗漏；功能清单尚需逐菜单、手册和定制项核对 |
| BASE-09 | 全量迁移必须支持，同时支持部分迁移；按租户切换，不建设长期双写替换体系 |
| BASE-10 | 标准产品以配置和受控扩展满足差异；客户代码定制单独评估，不复制一套标准产品长期维护 |
| BASE-11 | 订阅沿用年付与线下签约、运营开通方向，支持套餐、配额、到期与用量；价格及商业细则不作为技术硬编码 |
| BASE-12 | 现在设计 AI 可调用业务底座，未来再开发 AI 产品功能；场景不限于本次举例 |
| BASE-13 | 首版使用系统账号登录，预留统一登录扩展；客户既有统一登录不作为首版必须接入项，见 DEC-007；认证采用 Spring Security、服务端会话及 Spring Session JDBC/PostgreSQL，具体版本和配置见 DEC-008 的未决边界 |
| BASE-14 | SaaS 必须支持自建开源对象存储，SeaweedFS 为自建首选，SaaS/客户版优先复用 S3 接口，云托管为可选实现，见 DEC-010；首批客户主要单台 Linux，硬盘与备份规格未定 |
| BASE-15 | 客户允许 Docker Engine/Compose，优先容器交付和维护窗口升级；SaaS 初期 A 维护窗口发布、后续 B 应用双版本切换，见 DEC-015；现在设计多实例/恢复/版本兼容，不自动承诺完整高可用或所有升级无感 |

默认“一旧部署/数据库对应一个机构”，是基于历史考证的迁移工作假设；遇到多库合并或一库多机构时必须重新剖析，不能自行切分。

## 4. 本次确认的 AI 需求边界

- 支持未来系统内置助手与外部 Agent；员工本人授权，机构管理员限制客户端、功能与数据范围。
- 查询可在授权范围内直接执行；普通写操作按授权执行；高风险修改需要服务端确认或审批。
- 资料可来自粘贴文本、上传截图/文件、未来自动渠道同步；自动渠道另行确定。
- 提取资料自动保存待核实草稿；关联已有学员、覆盖旧信息或合并档案时确认。
- 排课信息不完整时追问；允许生成并保存草稿；发布课表与通知师生需确认。
- 支持标准报表及在已定义指标、维度内组合查询、图表与导出。
- 客户内网部署将来可使用本地模型，无公网仍能调用内网业务；不要求个人电脑断网后离线修改 SaaS 再同步。
- 定时巡检、主动发现和无人值守处置尚未确定，不纳入本次实现范围。

用户补充确认 AI 初期作为辅助助手，未来保留成为主要操作入口的可能。该可能性不等于当前开发承诺；当前仍只设计底座，业务页面独立可用。见[技术决策记录](../05-决策与问题/20261030-技术决策记录-v1.19.md) DEC-002。

## 5. 已确认技术主线与待细化选择

用户已确认 Java + Spring Boot 业务核心、PostgreSQL、React + TypeScript 前端，见[技术决策记录](../05-决策与问题/20261030-技术决策记录-v1.19.md) DEC-001。数据访问与结构迁移已确认 jOOQ + Flyway，详见 DEC-005。租户隔离方向已确认标准 SaaS 共享库/表、tenant_id 与 PostgreSQL RLS，客户本地版同代码独立部署并保留专属部署选项，详见 DEC-006。当前没有单客户独立时间点恢复或独占数据库资源要求，不据此承诺恢复 SLA。工程工具与质量门禁已在 DEC-014 确认，采用 Maven/Wrapper、pnpm、分层检查与真实数据库验证。具体版本、生成配置、已选工程工具的配置、已选前端组合的配置（见 DEC-012）、隔离落地细节、身份会话/权限落地细节（组合已在 DEC-008 确认）、未来委托、已选任务/事件组合的落地细节（PostgreSQL + db-scheduler + 事务 Outbox，见 DEC-009）、已选文件存储的落地细节（SeaweedFS 自建首选与 S3 接口，见 DEC-010）、已选接口与数据表示的细节（见 DEC-011）、报表、已选部署发布方向的落地细节（初期 A、后续 B，见 DEC-015）与观测继续细化；AI 编排技术和模型留到实际 AI 开发时选择。

模块职责、可靠事务、多入口授权和确定性业务规则属于需求与架构约束。按业务模块化组织，应用形态和运行进程的具体布局继续设计，不从上一轮自动继承工程。

本轮补充确认：主要由 AI 开发，用户验收并阅读修改代码，因此要求清晰中文注释；以产品方公有云 SaaS 为主，客户版部署于客户提供的 Linux 服务器，暂不扩大平台兼容。客户服务器资源规格未定，不预设为办公电脑或要求特定集群。技术由 AI 提出首选及取舍，用户选择。

## 6. 非功能工作假设

下列值来自既有需求讨论，保留为评估输入，不能代替真实数据和合同确认：

| 类别 | 评估输入 | 处理要求 |
| --- | --- | --- |
| 租户规模 | 目标约 100–200 家租户 | 不据此预设分库、分区或集群方案 |
| 大租户 | 约 2 万学员、1000 员工、20 校区；峰值并发约 500，统计范围待确认 | 补充读写比例、排课和导出负载，避免误当成全部租户统一上限 |
| 排课样本 | 200 班、100 教师、40 教室、62 天窗口 | 是初始压测样例，需真实数据验证 |
| 可用性与恢复 | 99.9% 月可用性、RTO 4 小时、RPO 15 分钟 | 运维设计后复核可兑现范围 |
| 安全 | 境内数据存储、敏感信息最小化、访问与导出审计；既有等保二级设计方向 | 适用要求、数据分类与评估由专项设计确认，不将旧文档概括当作法律结论 |
| 审计与备份 | 审计保留一年方向；备份保留与恢复演练要求 | 结合合同、数据类别与恢复测试细化 |

本地版客户自运维，产品侧提供安装升级与支持；SaaS 由产品侧或托管方运维。具体交付环境、授权与依赖方式随技术选型重新设计。
