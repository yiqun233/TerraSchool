- 状态：Accepted，用户已确认。

| 部署约束 | 以产品方公有云 SaaS 为主，客户版部署于客户提供的 Linux 服务器 |

Java/Spring Boot/PostgreSQL/React 的具体版本及依赖兼容矩阵；已选 Maven/Wrapper、pnpm 与检查/测试工具的版本及配置（见 DEC-014）；jOOQ/Flyway 的具体版本与生成配置（选型已在 DEC-005 确认）；已选前端组合的版本与配置（见 DEC-012）；租户隔离落地细节（方向已在 DEC-006 确认）、身份会话/权限落地细节（组合已在 DEC-008 确认）与未来委托；已选任务/事件组合的版本与落地细节（见 DEC-009）、已选文件存储的版本与配置（见 DEC-010）、接口/数据表示落地细节（方向见 DEC-011）、报表、缓存和部署编排。

未来只有实际 AI 需求证明独立运行时有价值时，才决定是否新增 TypeScript 或其他语言的 AI 服务；该选择会带来服务间鉴权、部署和追踪成本，目前不创建。

## DEC-002 AI 初期辅助，后期保留主入口演进

- 状态：Accepted，初期定位与演进边界已确认；未来主入口不是已承诺功能。
- 确认日期：2026-10-30。
- 用户依据：“初期项目还是辅助助手，后期不排除有第二种可能”。

### 决定

1. 当前只预留 AI 可调用底座，不开始开发 AI 功能。
2. 将来初期引入 AI 时，定位为辅助助手；普通业务页面可以独立完成完整操作，不能依赖模型才能使用系统。
3. 后期保留自然语言成为主要操作入口的可能，不据此现在开发生成式界面、通用 Agent 平台或无人值守自动处置。
4. 页面、任务、内置 AI、外部 Agent 共用确定性应用服务和授权规则；前端不拥有核心业务判断。
5. 草稿、预检、确认、审批、执行结果与错误形成业务契约。即使未来入口改变，也能复用同一业务能力。
6. 未来助手展示提取材料、修改差异、待确认方案、任务进度和结果，应可关联真实业务对象；信息不只保存在聊天文本中。

### 保持有效的风险规则

资料提取保存待核实草稿，关联、覆盖和合并需要确认；排课可以保存草稿，发布和通知另行确认。权限、风险策略、金额计算和冲突判定由业务系统执行，模型不能自行批准。

### 未决定

AI 开发启动顺序、首发场景、模型和本地推理运行时、TypeScript 或 Spring AI 编排、MCP 接入实现、聊天与任务状态存储、主动巡检。普通 AI 调用能力不要求现在把这些全部选定。

## DEC-006 标准 SaaS 共享表与双层租户隔离

- 状态：Accepted，标准方案及专属部署边界已确认；尚未实现或验证。
- 确认日期：2026-10-30。
- 用户依据：在共享库/表、tenant_id 与 RLS 方案讨论后，用户确认“目前没有，标准 SaaS 采用共享方案，保留专属部署选项”；目前没有单客户独立时间点恢复或独占数据库资源要求。

### 决定与边界

1. 标准 SaaS 共享 PostgreSQL 数据库与业务表，租户业务数据以 tenant_id 明确归属，应用授权与数据库 RLS 双层保护。
2. 租户仍代表机构/品牌，学校/校区/部门为租户内部组织；同租户内功能、资源范围与敏感字段权限另外执行。
3. 客户本地版使用同一套代码和结构演进基线独立部署，保留 tenant_id 及隔离规范；特殊 SaaS 客户保留专属部署选项，不预建通用分库平台。
4. 普通运行角色与迁移角色分离，租户业务表启用并强制 RLS，读写均受策略约束；可信入口建立租户身份，并在实际连接/事务内绑定，缺失时拒绝。
5. 租户内唯一性、关联约束、文件、缓存、任务、导出和未来检索索引同样遵守租户边界；未来内置 AI/外部 Agent 复用执行上下文，模型不能选择租户或数据库。
6. 单客户恢复不回滚共享线上库；当前不承诺独立 PITR、独占资源或对应 SLA。专属数据库不自动等于专属实例或独立物理恢复边界。

### 备选、理由与代价

相较每租户 schema/数据库，默认共享表减少多份结构迁移、连接和运维成本；不默认每租户 schema。代价是隔离实现及测试必须严格，资源仍共享，单客户恢复和迁移更复杂。专属部署按合同、负载与恢复要求另行评估，不能承诺无成本切换。

### 验证与未决

角色与 RLS 策略、查询/写入事务绑定、连接池/回滚、跨租户关联、任务与非数据库资源访问必须用真实 PostgreSQL 及双租户场景验证。RLS 不能替代同租户授权，也不保证应用完全失陷后的隔离。具体策略 SQL、路由实现、备份工具、资源配额、恢复 SLA、专属部署切换流程仍待设计。

详见[多租户数据隔离](../02-架构设计/租户隔离/多租户数据隔离.md)。当前只维护文档，不创建代码、数据库或 AI 服务。

- 状态：Accepted，仅确认首版登录接入范围；技术实现仍待确认。
- 确认日期：2026-10-30。

### 已确认

首版提供系统账号登录，不将接入企业微信、钉钉或客户内网身份系统作为首版必须完成的条件。身份入口保留后续统一登录接入位置，外部身份经验证后映射到明确的租户内账号，再复用现有业务授权。

### 实现决策的后续关系

本条只确认登录接入范围；随后 DEC-008 已另行确认 Spring Security、服务端会话、Spring Session JDBC/PostgreSQL 及权限模型。具体版本、配置、Redis 引入条件、独立身份产品、MFA、会话期限/并发策略等未决项见[登录会话与权限方案](../02-架构设计/身份权限/登录会话与权限方案.md)。外部 Agent 委托仍按 DEC-002 预留，具体 OAuth/MCP 授权实现待接入时设计。

### 理由与验证边界

按用户确认范围保持首版登录独立于客户统一身份系统，同时为后续扩展留出入口适配边界。尚未实现或测试；未来统一登录仍须验证租户绑定、账号映射、停用与撤销，并不能仅因通过外部认证就授予业务权限。本条不授权创建工程、部署身份服务或安装依赖。

## DEC-008 认证会话技术组合与业务权限模型

- 状态：Accepted，用户确认采用推荐组合；尚未实现或验证。
- 确认日期：2026-10-30。
- 用户依据：针对 Spring Security + 服务端会话 + Spring Session JDBC/PostgreSQL，以及角色、账号增减、按操作的数据范围和字段控制，用户选择“采用推荐组合，具体版本和配置后续确定”。

### 决定

1. Spring Security 负责认证与安全集成，浏览器使用服务端会话；初期使用 Spring Session JDBC/PostgreSQL 持久化会话，多实例共享存储。
2. 权限保留角色功能权限、账号单独增减、按操作的数据范围及字段控制，显式 deny 优先。统一应用服务执行授权，页面、任务与未来 AI/Agent 不能绕过。
3. 首版登录范围继续遵循 DEC-007，预留统一登录扩展；未来员工委托和外部 Agent 的权限交集仍遵循既有架构约束。
4. 会话不以长期权限快照代替当前有效授权；停用、撤权、任务执行和高风险提交按明确协议复检。认证/会话存储在业务租户上下文建立前使用受限访问路径，不给普通业务连接开放 RLS 绕过权限。
5. Cookie 会话配套 CSRF 防护；JDBC 会话存储属于身份基础设施，业务主数据访问仍为 jOOQ，会话结构升级纳入迁移管理。

### 取舍

相较先引入 Redis 或独立身份平台，复用 PostgreSQL 减少当前部署依赖，适配 SaaS 与客户内网；代价是数据库承担会话读写、清理与并发负载，须验证后评估扩展。浏览器 JWT 不作为默认方案，未来外部 API/Agent 的令牌格式另行决定；不把网页会话选择绑定到外部协议实现。

### 未决与验证

具体 Spring Security/Spring Session 等版本及兼容矩阵、Cookie/域名、会话期限与并发登录、序列化/清理、撤销并发、身份数据库访问角色、查询过滤实现与 MFA/恢复规则继续设计；本次不自动选择 Redis、Keycloak、授权服务器或通用权限引擎。

工程验证使用真实 PostgreSQL 及多实例/双租户场景，覆盖登录、会话生命周期、CSRF、RLS 组合、撤权、任务和权限并发。当前只有文档检查，无实现、性能或安全测试结果，不开始创建代码或安装依赖。

详见[登录会话与权限方案](../02-架构设计/身份权限/登录会话与权限方案.md)。

## DEC-009 开源持久任务、db-scheduler 与事务 Outbox

- 状态：Accepted，用户确认组合及边界；未实现或运行验证。
- 确认日期：2026-10-30。
- 用户依据：进一步比较任务框架、消息队列与工作流引擎后，用户选择“优先开源方案，可自行补充业务界面”，并对 PostgreSQL + db-scheduler + 事务 Outbox、worker 按需独立运行的组合回复“确认”。

### 决定与边界

1. PostgreSQL 持久化业务任务与待处理事件，db-scheduler 承担调度；计算任务按需独立 worker，复用业务模块公开契约。
2. 业务修改和对应 Outbox 记录同事务提交，后续派发/消费可重试并幂等；业务任务状态、进度、取消、身份和结果由系统掌握，不直接暴露调度表。
3. 任务接受到实际安排执行具有可靠衔接，验证 Spring 事务连接或持久待办补安排；普通内存异步与提交后回调不是唯一可靠机制。
4. 可能重复执行的任务具备业务幂等、有限重试、取消阶段和旧执行者提交保护；不能以框架领取协调宣称所有外部副作用恰好一次。
5. 收款、退款、消耗、锁月等保持既有强事务边界；排课计算在事务外，提交草稿时复检资源与授权，多班失败保留整批回退语义。
6. 调度扫描与单租户业务执行分别限制权限；当前不强制引入 RabbitMQ、Kafka、Redis 或 Temporal，不开始 AI 主动巡检或无人值守平台。

### 取舍与验证

相比先引入独立消息/工作流服务，复用 PostgreSQL 减少 SaaS 和客户内网部署依赖；用户接受自行补充业务任务界面。代价是需要维护业务状态、幂等、进度、清理、观测和数据库负载隔离。JobRunr 的现成后台、Quartz 的触发器、RabbitMQ 的跨服务分发、Kafka 的事件流与 Temporal 的持久流程保留比较结论，未选择为当前底座。

具体版本、许可/依赖兼容、表与索引、事务/RLS 路径、参数序列化、重试/心跳/取消、执行凭证、资源配额和运行配置继续验证。首个真实任务覆盖回滚不执行、提交后宕机恢复、重试不重复、旧执行者恢复、撤权与取消竞态、多消费者和升级兼容。当前只完成文档检查，未开始代码、安装或部署。

详见[后台任务与可靠业务事件](../02-架构设计/任务事件/后台任务与可靠业务事件.md)。

## DEC-010 自建 SeaweedFS 与统一文件存储接口

- 状态：Accepted，自建首选与接口方向已确认；未实现或运行验证。
- 确认日期：2026-10-30。

## DEC-024 平台运营身份独立与首版数据边界

- 状态：Accepted，身份体系与首版数据边界已确认；具体模型、接口与页面仍是草案，未实施。
- 确认日期：2026-11-06。
- 用户依据：就“超级管理员/租户管理页面是否存在”确认现状为“没有”，并明确“平台身份是一个独立的账号体系”“平台账号能不能看租户业务数据后续再说，可以先不看只看基本需要的”“租户开通需要达到实际真实的业务效果”。
- 决定：
  1. 平台运营身份使用**独立账号体系**，不复用 `identity.account`，不通过给租户账号加标记实现；独立登录入口、独立会话、独立动作目录与独立审计（沿用 BASE-04 与 AGENT.md 第 6 节的既有边界）。
  2. **首版平台账号不读取租户业务数据**，只可见租户名称、编码、状态、开通时间、学校数、账号数等开通与状态信息；不提供“以租户身份登录”的模拟入口。放开该边界须另立设计，不得以改授权的方式顺带实现。
  3. 租户开通以**可立即登录使用**为验收口径：一次操作产出租户与可登录的管理员账号，事务性完成、可重试、有审计。
  4. **开通时不创建学校**。签约时通常还不知道客户要在哪个校区开课，学校、校区、部门、员工由客户登录后自行建立；开通只交付租户与账号。
  5. 首版交付的账号是**租户内权限最大的管理员**：覆盖本租户全部学校（含将来新建的），不跨租户、不是数据库超级用户。为支持“零学校”起步，需给账号增加租户管理员标记并调整「覆盖全部学校」的判断，否则新租户无法创建第一所学校。
  6. **账号交付**：开通时自动生成初始密码，明文只在响应中一次性返回；账号带强制改密标记，首次登录只能改密；密码策略首版为 ≥12 位、非纯数字/纯字母、不得与登录名相同。
  7. **平台可修改租户管理员密码（首版确定）**：在平台界面上对租户管理员（含开通时交付的初始管理员）执行重置，运维人员不需要接触数据库。支持随机生成与手工指定两种方式，均需通过密码策略；结果都会置为首次登录强制改密、吊销该账号既有会话、写平台审计。落库通过受控函数只写凭据列，平台角色不获得 `identity.account` 的直接 `UPDATE` 权限。手机号自助找回待短信通道到位后再做（Q43、Q83）。
  8. **首次进入引导**：无学校的租户登录后展示三步引导（建学校→建校区/部门→加员工与授权）；引导状态由“本租户没有 SCHOOL”派生，不新增持久化标记。
  9. 平台管理员对该租户的可见范围由此扩展为：租户名称/编码/状态/开通时间/学校数/账号数，以及租户管理员账号的登录名、状态与最后登录时间；仍不含任何业务数据。
  10. **平台身份不做双人复核与 MFA（首版）**：以单因素 + 强密码 + 强制改密 + 平台审计控制风险；平台账号持有人范围与离职交接流程另行确定（Q77）。
- 影响范围：新增 `platform` schema 与受限数据库角色 `ts_platform`；`identity.tenant` 增列；`tools/ops/bootstrap_admin.py` 改为调用同一开通服务。租户内的账号、角色、字段授权模型不变。
- 约束：平台账号的数据库角色不授予任何业务表权限，隔离由数据库保证而非应用自觉；不做租户删除，只停用。
- 草案与细节：[平台身份与租户开通方案](../02-架构设计/平台运营/平台身份与租户开通方案.md)。未决项 Q77～Q82 待登记。
- 验证：本轮仅文档，不含实现、迁移、页面或运行结果；F01 仍为局部实现。
