## I. 疑似旧系统缺陷（当前实现先照旧系统，等确认是否修）

这几个点是我在对照旧系统源码时发现的**可疑行为**：可能是业务规则，也可能是历史缺陷。目前一律先按旧系统实现，确认后再改。

| 编号 | 疑点 | 旧系统怎么做 | 我们的现状 | 疑点在哪 |
| --- | --- | --- | --- | --- |
| Q34 | **模式 2/3 不扣优惠** | `fee = curricula.getFee()`，优惠只在模式 1/4 里减 | 与旧系统一致 | 同一份优惠，模式 1 少收、模式 2/3 不少收；课程模式可能"消耗额 > 折后应收" |
| Q35 | **模式 5 不扣优惠** | `fee = curricula.getFee() − feeQuit` | 与旧系统一致（本批已改回） | 同上：退课后实际费用模式反而不扣优惠，账实可能不符 |
| Q36 | **课程费用与报名优惠互不关联** | 优惠存在报名级 `Price_Discount`，不摊到 `H_Student_Register_Curricula.Fee` | 我们已有 `enrollment.discount` + 按比例摊分能力，但默认不用 | 若要摊分，需要确定分摊到课程的口径（按金额比例？按课时比例？） |
| Q37 | **退费额不随优惠比例折算** | 退费按原价算，只有"重新报名"时按 `totalPrice × 旧优惠 / 旧价格` 折算 | 退费按课程单价算，未折算优惠 | 学员被优惠后按原价退，可能退超（退了优惠掉的钱） |

## 分类、类型与优先度口径（2026-11-10）

问题按 A～M 章节只能看出“哪批提出”，看不出“哪类最多、先回答哪个”。状态索引因此为每条问题登记领域、类型、重要度、紧急度四个字段；总览按它们分组、排序和筛选，并由生成器推导处理档位。新增问题时四个字段必须一并填写，不新造分类。

### 领域（一条问题只归一类，按回答它主要改变的业务面）

| 领域 | 覆盖范围 |
| --- | --- |
| 金额与结算 | 计价模式、优惠、服务费、退费、退课、期初与冲正、尾差 |
| 审批与期间 | 必批动作、岗位与额度、自批限制、财务月与锁月纠错、待办失效、验收责任 |
| 教务与排课 | 冲突分级、校历与停课、容量与名额、考勤与部分缺勤、调补换课、结班、多班入班 |
| 学员与招生 | 敏感字段、字段授权粒度、客户公海与回收、合并、转学员、电话检索、负责人、渠道 |
| 旧库迁移 | 迁移口径、切换时点与冻结、真实样本、编号与证件映射、历史承接 |

| 平台与租户 | 租户开通、套餐配额、编号规则、字典、校区资料、平台账号与找回 |

### 类型

| 类型 | 判定 | 回答方式 |
| --- | --- | --- |
| 规则口径 | 需要业务方给出业务含义或取舍，答案会改变金额、权限、流程或历史承接 | 结论 + 一个算例，说明适用范围与例外 |
| 证据缺失 | 需要旧库样本、旧代码事实或真实环境证据才能判断 | 补齐材料，或明确“查不到、按建议默认” |
| 实现缺陷 | 只需工程内部决定处理方式，不涉及业务取舍 | 工程决策，不占用负责人时间 |

### 重要度（不答对后续开发的影响）

| 重要度 | 判定 |
| --- | --- |
| 高 | 不答会写错真实资金、权限或历史事实，或要返工重写已实现规则，或阻断 G 关口验收 |
| 中 | 影响范围完整性和验收口径；可用安全默认继续，事后修正成本有限 |
| 低 | 体验、文案或流程细化，不改业务事实 |

### 紧急度（什么时候必须给答案）

| 紧急度 | 判定 |
| --- | --- |
| 立即 | 正在做或即将验收的 REV 任务被它卡住，答案会改动已落地代码 |
| 本阶段 | 当前 G 关口关闭前必须答；现在可按安全默认继续 |
| 可后置 | 不阻断当前关口，留到后续关口或上线前 |

### 档位由生成器推导，不手工填写

| 档位 | 生成规则 | 处理方式 |
| --- | --- | --- |
| S 立即阻断 | 重要 高 + 紧急 立即 | 本周内给结论；未答前只允许只读预检、小样本和防护性修复 |
| A 本阶段必答 | 重要 高 + 紧急 本阶段，或 紧急 立即 | 当前关口关闭前给结论 |
| B 排期处理 | 其余组合 | 随对应功能批次回答 |
| C 观察 | 重要 低 + 紧急 可后置 | 不主动追问，扩大范围时再看 |

档位只表达处理顺序，不改问题状态，也不把“已实现”当作“已确认”；“未回复”“等待时间”同样不能视为同意。各档当前条数以总览“待确认问题”页的矩阵为准，不在正文写死，避免与索引不一致。
