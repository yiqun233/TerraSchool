## 1. 分层与归属

| 目录 | 唯一职责 |

| 00-项目基线 | 目标、范围边界和全局约束 |

## 2. 稳定路径、日期与正文版本

### 2.1 持续维护文档

持续维护文档使用固定的 `主题名称.md`，不在文件名中放创建日期或版本号。例如：

| 用途 | 固定路径 |
| --- | --- |
| 统一索引 | `doc/文档导航.md` |
| 当前执行路线 | `doc/04-执行计划/后续开发执行路线.md` |
| 当前功能进度 | `doc/04-执行计划/系统功能拆分与完成情况.md` |
| 文档规范 | `doc/03-研发规范/文档管理规范.md` |
| 具体功能设计 | `doc/02-架构设计/对应领域/功能主题.md` |

根 `AGENT.md`、`README.md` 与其他已有固定入口保持原名。主题路径确定后，普通内容修订及正文版本升级均不重命名文件，也不要求修改其他文档的引用。链接文字优先使用主题名，不嵌入可变版本号。

### 2.2 验证记录与冻结快照

一次具体执行的验证记录、独立审阅/验收/发布基线使用 `YYYYMMDD-主题名称.md`，日期表示该记录或基线的实际日期，不随修订改变；文件名同样不带版本。相同主题下一次执行另建日期记录，同日多批次可增加明确、固定的批次标识，不能覆盖先前执行结果。

例如 `doc/03-研发规范/工程质量/验证记录/20261103-项目审阅验证记录.md`、`doc/04-执行计划/20261103-项目审阅与纠偏报告.md`。快照头部写清冻结范围、对应代码/发布基点与替代关系；不能将冻结快照当作当前进度入口。当前状态和路线始终链接固定的台账与计划。

### 2.3 正文版本与日期

版本仅维护在正文元数据中，与文件名解耦。主版本表示范围或约束的重大变化，次版本表示兼容补充；排版、错字、链接修复可以保留版本并记录修订。创建日期不变，更新日期据实填写，不将旧系统观察日期当作新文档创建日期。

普通历史由 Git 保存，每个主题只保留一份现行正文，不创建平行的“最终版”“新版”或每次升版副本。尚未提交的改动须在明确授权后按 Git 规范保存，不以改文件名替代版本管理。确需独立引用的冻结基线才按 2.2 创建。

### 2.4 路径变更的例外

只有主题拆分、职责归属搬迁、实际更名等确实改变文档身份时才调整路径；这时一次性修复全部入链和索引并检查链接。正文版本变化不属于路径变更理由。

## 3. 元数据与状态

每份文档包含标题、版本、状态、创建日期、更新日期、维护方及关联文档。业务或技术有固定编号时保留稳定编号，不以正文版本或修订日期作为文档路径身份。

状态明确：Draft 为草稿，Review 为评审中，Accepted/Approved 为明确确认内容，Reference 为参考。一个技术分析文档可以同时包含已确认主线和未决建议，应逐项区分，不通过文件整体状态扩大批准范围。

实施状态独立记录：未开始、进行中、已实现、已验证、已验收不能混用。旧系统的研究完成不等于新系统功能完成。

## 4. 更新与链接

- 新增功能或改范围：更新功能清单、规则和执行任务。
- 改业务口径、状态、权限：更新所属功能设计、案例和必要决策。
- 改技术、部署、数据结构或接口：更新相应决策、设计、契约与验证记录。
- 确认结论后及时更新旧的“未定”表述；未选择的细节继续列为未决。
- 文档间使用相对链接；旧源码可写原始证据位置，缩略路径标明为线索而非可直接打开路径。
- 新增、删除、搬移或实际更名时更新索引及受影响入链，检查链接存在和根目录范围；仅正文升版不修改引用路径。
- 新文档加入导航；普通内容更新只维护相关权威文档，不因版本数字变化改导航或其他入链。完成后检查稳定命名、正文版本元数据、状态、链接和相互一致性。

## 5. 内容与安全

使用中文，以清楚的业务意义和设计理由为主。普通文档不复制原始客户材料和秘密，不维护生产账号密码。环境入口与凭据通过受控配置管理，文档只记录用途、访问边界和核验状态。

不写开发工期、人员编制或交付日期。不伪造业务确认、测试通过或线上可用；建议、假设、推断与证据分别标注。

迁移验证：检查 107 份 Markdown（104 份 doc 正文及三个固定入口），711 个本地链接与 2 个章节链接全部有效；文档数量、导航覆盖和创建日期保持完整，仓库正文无旧路径残留，`git diff --check` 通过。另用内存中的正文版本变更验证链接集合不变，未为此修改实际版本。命名及规则之外的既有审阅成果保留，业务代码未修改，未提交或推送 Git。
