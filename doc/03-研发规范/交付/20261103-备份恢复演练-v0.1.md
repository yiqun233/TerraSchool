## 做了什么

`tools/ops/backup_restore_drill.py` 不是"备份脚本"，而是**演练脚本**：真的 dump、真的恢复到另一个库、再逐表核对。

| 步骤 | 内容 |
| --- | --- |
| 1 | `pg_dump --format=custom` 到临时文件，记录耗时与字节数，并把它拷出到 Windows 侧 |
| 2 | 建空的演练库（先 `drop ... with force` 保证干净） |
| 3 | `pg_restore --no-owner --no-privileges` 恢复 |
| 4 | 核对 11 张表的行数（含 `flyway_schema_history`）与 10 张业务表的 **RLS 是否仍然 FORCE** |
| 5 | 输出 `report.json`，默认删掉演练库（`--keep` 可保留） |

失败即非零退出；**行数不一致或 RLS 丢失都算失败**——"导入成功"不等于"恢复成了同一个库"。

## 本机实测（2026-11-03，WSL PostgreSQL 18.6）

| 项 | 数值 |
| --- | --- |
| 源库 | `teraschool_dev`（11 张表、32 条迁移记录） |
| dump 耗时 | 0.23 s |
| dump 体积 | 303,734 字节（约 297 KB） |
| restore 耗时 | 0.91 s |
| 全流程耗时 | 约 4 s（含建库、核对、删库） |
| 行数核对 | 全部一致 |
| RLS | 10 张业务表全部 `relrowsecurity/relforcerowsecurity = true/true` |
| 演练库清理 | 已删除 |

结论：**当前数据量下的恢复路径是通的**，且恢复后 RLS 没有被 `--no-owner` 破坏（这点必须每次演练都验，恢复脚本一改就可能丢）。

## 已知限制（必须知道）

- 数据量很小（学生/报名/收款表都是 0 行），**这个耗时不能外推**到生产；生产演练要用真实数据量重跑并记录；
- 只验证"能恢复"，没有验证 **PITR（按时间点恢复）**，方案文档里的 WAL 归档部分仍未演练；
- 没有验证"恢复到另一台机器"（跨机器恢复涉及角色、扩展、权限）；
- 脚本目前走 WSL 里的 `pg_dump/pg_restore`；生产环境需要换成对应主机的客户端或容器内执行；
- 没有做定时演练与告警。

## 建议的演练节奏

| 场景 | 频率 |
| --- | --- |
| 本机/测试环境演练 | 每次改动迁移或恢复脚本后 |
| 生产预演（脱敏数据） | 上线前一次 |
| 生产定期演练 | 每季度一次，记录 RTO |
