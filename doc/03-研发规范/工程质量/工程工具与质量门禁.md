## 1. 确认范围

用户已接受 Maven/Wrapper + pnpm、格式/类型/依赖/模块边界检查、分层测试与按变更风险执行门禁的组合。CI 平台使用 DEC-013 已确认的自有 GitLab CI。

本次确认工具与原则，不代表具体版本或配置已锁定，不代表已经安装、建工程或运行测试。具体格式风格、规则集合、测试命令、契约生成器及版本兼容矩阵在工程建立前验证。2026-10-30 用户回复 Runner“还未配置或暂不清楚”，当前按未确认、尚不可依赖的执行环境管理，不据此判断一定没有 Runner。

## 2. 构建与依赖

| 范围 | 已选组合 | 职责 |
| --- | --- | --- |
| Java | Maven 多模块 + Maven Wrapper | 显式声明模块依赖和构建步骤；Wrapper 固定 Maven 工具版本 |
| 前端 | pnpm + pnpm-lock.yaml | 统一安装工具，提交依赖锁文件；CI 安装校验锁文件一致性 |
| 运行工具 | 固定 JDK、Node、Maven、pnpm 版本 | 在文档、开发环境和 CI 中使用兼容组合；具体版本待验证 |

Maven 相比 Gradle 更符合当前显式依赖、普通多模块构建和人工阅读的需要；没有足够的复杂构建需求推动引入 Gradle DSL。前端统一 pnpm，npm/Yarn 不作为并行维护方案；不混用锁文件。该选择是本项目的维护取舍，不宣称其他工具不能胜任。

- 后端集中管理 BOM、直接依赖和构建插件版本，发布构建不采用浮动范围或 SNAPSHOT 依赖；核对传递依赖解析结果，按交付需要留存依赖清单。Wrapper 不固定 JDK，也不自动锁住全部传递依赖。
- 前端提交锁文件，CI 使用 frozen-lockfile 安装，依赖声明不一致时失败；版本升级连同锁文件、兼容验证和相关文档一起提交，不在 CI 中静默更新。
- Maven Enforcer 检查选定的工具/环境与依赖约束；依赖收敛等具体规则结合 BOM 和真实构建验证，不通过随意排除依赖把失败消掉。
- 缓存仅提高速度，缓存缺失时仍应能按受控来源重建；不能依赖某台开发机里未声明的包。具体依赖镜像、校验、网络及缓存策略在部署与构建配置中细化。
- Wrapper 首次引导、pnpm offline 或容器离线运行均有预备条件；离线构建需要事先备齐工具、依赖、镜像和测试资源，不把一个 offline 开关当作离线交付完成。
- 客户正常运行使用交付产物，不要求在客户服务器安装 Maven/pnpm 或从公网下载开发依赖。具体离线交付格式、镜像仓库和升级方式仍待后续讨论。

固定工具和依赖是可复现构建的基础，不自动保证产物逐字节相同；时间、插件、平台和生成过程等仍需单独控制与验证。

### 2.1 版本选择、验证与锁定（DEC-022）

- 选择仍受支持的稳定发布版本，Java、Node.js 优先 LTS；核对维护范围与交付约束，不把“稳定”误解为所有旧分支仍有免费维护。
- 优先使用 Spring Boot 管理的依赖版本。覆盖受管理版本时，明确原因、影响的传递依赖及生成/编译/运行验证结果，不通过任意覆盖或排除凑出可启动组合。
- AI 协作者负责调查官方兼容与许可信息、推荐组合并整理验证记录。涉及技术路线变化、付费依赖或部署要求变化时再讨论确认；普通补丁或常规配置在后续已授权实施范围内处理并记录，不逐库重复开选型讨论。
- 验证通过后固定 JDK 发行版/版本、Node/Maven/pnpm、直接依赖与插件、生成器、浏览器及容器镜像的实际版本；镜像可用不可变摘要核对，避免 latest 或其他可变标签成为唯一交付标识。前端锁文件和后端 BOM/插件管理共同维护，声明与解析结果可追溯。
- 版本基线升级同批更新锁定信息、相关配置和验证结果；不在 CI、客户启动或离线安装时静默追新。具体记录载体和检查命令在工程启动范围内落实。

版本矩阵至少保留以下字段，不以只有版本号的表格替代验证：

| 字段 | 记录要求 |
| --- | --- |
| 组件与用途 | 区分运行时、构建、生成、测试及部署，包含发行版/开源或商业版本 |
| 候选/锁定版本及依赖 | JDK、Spring Boot 管理、jOOQ 生成器与运行库、Flyway/驱动/PG、前端及镜像之间的关系 |
| 选择依据 | 官方支持、维护状态、许可和客户内网交付条件；有例外说明理由 |
| 复现与结果 | 环境、命令、日期、实际结果及限制；不能复现的问题保留未解决状态 |
| 状态与升级约束 | 候选、待验证、已验证锁定或被替代，记录后续升级影响 |

本轮独立原型已固定并验证核心组合，具体版本/结果见[R3-CORE-001](验证记录/20261031-核心技术组合验证记录.md)；正式发布 JDK 发行版/补丁与其他组件并未全部锁定。官方要求用于筛选，实际构建、数据库、契约和部署行为分别验证。Node.js 官方建议生产使用 Active LTS 或 Maintenance LTS；PostgreSQL 每个大版本有独立维护周期，补丁升级仍核对发行说明。[Node.js 发布政策](https://nodejs.org/en/about/previous-releases)、[PostgreSQL 版本政策](https://www.postgresql.org/support/versioning/)。

## 3. 格式、静态检查与模块边界

| 范围 | 已选工具 | 检查目的 |
| --- | --- | --- |
| Java 格式 | Spotless | 统一排版，减少无业务意义的差异；具体格式配置后验 |
| Java 环境和依赖 | Maven Enforcer | 检查约定的 JDK/Maven 版本和依赖规则 |
| 后端架构 | ArchUnit | 模块循环依赖、内部类型越界、允许依赖及装配入口反向依赖 |
| TypeScript | TypeScript 类型检查 | 检查源码及派生客户端类型；生产资源构建之外独立验证 |
| 前端代码规则 | ESLint | 选定的易错写法、React/hook 和模块导入规则 |
| 前端格式 | Prettier | 统一排版，与 ESLint 的格式规则避免重复冲突 |

后端多模块依赖和 ArchUnit 一起落实公开 api/internal 边界。ArchUnit 的静态依赖检查不能覆盖任意动态 SQL、反射或所有数据越权行为，跨域写表、RLS 和数据范围仍由实现约束、真实测试与评审共同保障。前端按既定 feature/shared 边界约束导入，不让 shared 反向依赖具体业务。

格式修复在本地显式执行并审阅差异，CI 以检查和报告为主，不自动修改源码或提交。生成目录不靠人工修改来通过格式检查；禁止为了通过检查广泛关闭规则或添加无理由忽略。

当前不默认叠加 Checkstyle、PMD、SpotBugs、Sonar 等整套工具；出现明确风险且现有检查不能覆盖时再评估。检查工具不能验证中文注释是否解释了正确的业务原因，可读性继续按根协作规范评审。

## 4. 测试层次与证据

| 层次 | 已选工具 | 主要覆盖 |
| --- | --- | --- |
| 后端规则 | JUnit + AssertJ | 金额/课时、舍入尾差、状态前置条件等确定性规则 |
| 真实数据库集成 | Testcontainers + PostgreSQL | RLS、授权查询、事务回滚、幂等、迁移、约束及并发 |
| 前端组件与交互 | Vitest + React Testing Library | 关键表单校验、错误反馈、异步状态及编辑保护 |
| 关键完整流程 | Playwright | 登录与操作、保存/发布、关键财务链路及最终业务结果 |

JUnit、AssertJ 等具体版本随 Spring Boot 与依赖兼容验证确定，不在此预先指定 JUnit 大版本。Vitest 的测试环境、组件测试配置、Playwright 浏览器范围和版本仍需验证；不为每个控件机械增加一条浏览器测试。

数据库测试必须验证真实 PostgreSQL 行为，H2、SQL 字符串匹配或纯 mock 不能作为 RLS、约束、事务与并发的验收证据。Testcontainers 需要可用且权限明确的容器运行环境；条件不具备时可使用隔离的真实 PostgreSQL 测试实例，但必须保留结构、角色、清理与可重复运行协议，不能跳过后声称测试通过。

迁移账号与普通业务角色分离。RLS 用例通过实际普通运行角色执行，不能只用 PostgreSQL 超级用户或表所有者测“隔离成功”；覆盖强制策略、缺失上下文、读/写/关联、事务回滚、连接复用与跨线程边界。普通业务角色不具备 BYPASSRLS 或其他绕过业务隔离的权限。

优先保护的业务结果：

- 同一收款/退款请求重复或并发执行，不重复入账，金额、分配与余额保持一致。
- 跨租户读写被拒绝，账号停用与撤权在约定边界生效，导出和文件访问同样授权。
- 并发保存/发布排课时资源不重复占用，过期版本被拒绝，多班失败保持整批回退语义。
- 任务中断、重领和重试后业务一致，旧执行者恢复后不能覆盖新执行结果。
- 锁月、关课、消耗、退款与转班按旧规则金标准核对，强事务失败不留半套权威事实。
- 身份切换后旧请求不能回灌敏感缓存，后台刷新不能静默覆盖未保存表单。

测试预期来自业务规则、旧系统证据及明确样例；旧代码与预期冲突时记录并确认实际歧义。AI 根据实现原样复制的测试不构成独立金标准。关键用例有清楚的中文场景和预期说明，不以覆盖率百分比、页面截图或构建成功代替业务验收。可逆、低影响展示变更不机械增加镜像测试。

## 5. 数据结构、生成与契约检查

### 5.1 数据库与 jOOQ

沿用数据访问方案：目标 Flyway 迁移 → 隔离 PostgreSQL → 应用迁移 → jOOQ 生成 → 后端编译 → 真实集成测试。不从生产库生成，不以个人数据库状态为构建输入，不在客户应用启动时生成。

结构变化根据影响验证空库建立及受支持旧结构升级；共享环境已执行迁移不随意改写。涉及数据回填、约束收紧或破坏性变更时验证数据兼容与恢复/补偿，不把开发数据库能重建当作线上可升级。

原型的 jOOQ 产物在 target、OpenAPI 和前端派生类型在生成目录且均不入库；正式工程产物政策、增量与缓存规则仍需确认；无论是否入库，都不能手改生成文件或把过期文件当作当前结构。迁移角色的权限不能被普通应用连接继承。

### 5.2 OpenAPI 与前端客户端

沿用接口契约方案：服务端公开 DTO、校验和接口声明 → 导出 OpenAPI → 生成前端类型/客户端 → TypeScript 检查及前端构建。生成器、规范版本和具体兼容检查工具另行验证，不在此新增第二套手工权威 schema。

检查范围包括真实 JSON 与 schema、十进制字符串/时间/空值/稳定枚举、错误结构及重要兼容变化。类型生成不能替代服务端授权和运行时输入校验；内部 jOOQ 类型不泄漏到公开契约。

## 6. 门禁按变化风险执行

| 变化 | 必要验证 |
| --- | --- |
| 纯文档 | 命名与版本、元数据、链接、引用和决策状态一致；不要求启动业务测试 |
| 普通功能代码 | 格式、类型、相关静态/架构检查、受影响的规则或集成测试及相应构建 |
| 权限、租户、资金、状态或并发 | 扩大真实集成、负向授权和并发测试，核对业务不变量 |
| 数据迁移、公共契约或生成配置 | 重新生成/编译，检查迁移与升级、实际序列化、客户端及受影响流程 |
| 合并与发布 | 汇总本批必要检查；关键业务切片做完整流程及对账，按变化增加恢复/内网交付/性能专项 |

影响分析包含依赖关系和业务结果，不只按文件路径过滤。公共权限、共享 DTO、构建生成或数据库规则变化可能影响多个模块和前端。检查分类和失败摘要明确，必需检查失败或未运行不能被汇总为通过。

测试使用隔离数据，异步等待与并发条件显式控制；不靠固定长 sleep 或无限重试掩盖不稳定。失败应保留足以复现的信息并保护秘密；外部系统使用受控适配，关键权限和数据库语义不能被 mock 掉。

## 7. GitLab CI 与交付边界

主仓库和 CI 平台以 DEC-013 为准。当前 Runner 未确认，尚无业务工程或流水线；成功推送不是构建/测试通过。本次只维护文档，不配置服务器、注册 Runner、安装依赖或创建空流水线任务。

本机 2026-10-31 已核验工具及 WSL 基础服务，Docker 由用户启动后 Windows/Ubuntu 的 Linux 引擎及 Compose 接口已复查通过，但随后 Java 21 下 Testcontainers 创建/连接/销毁已通过，Temurin 25 管道限制另记，详见[本地开发环境](../开发环境/Windows与WSL本地开发环境.md)。默认 Windows 测试进程连接 Linux 容器引擎，运行实际 Testcontainers 用例后才报告该路径通过；现有 `vectordb` 不作为可任意重置的测试实例。

工程初始化时核验 Linux Runner 的执行方式、标签、受保护任务与凭据范围、容器测试条件、数据库角色、依赖/镜像来源及缓存。Testcontainers 能否启动测试容器必须实测，不默认 Runner 具备容器权限，也不默认开放不受限宿主机权限。

流水线与本地复用同一套受控检查命令；CI 采用检查模式、固定依赖和可追踪产物，未运行/跳过/失败如实报告。测试数据使用人工构造或核验脱敏样本，参考资料、真实客户数据库和秘密不进入 Git、测试日志、截图、追踪或产物。缓存、产物留存、并发和清理配置后验。

GitLab CI 不自动获得生产部署权限。客户正常运行不依赖 GitLab 或公网，交付使用构建产物；生产发布与客户离线安装、升级和恢复在后续部署方案中明确。本轮未确认自动部署、生产凭据或特定 Runner 拓扑。

## 8. 中文注释、评审与未来 AI

公开操作、金额课时、权限、事务、幂等、并发和历史兼容处按根规范写清楚业务用途与设计原因；行为变化同步修订注释、契约、测试和文档。格式工具不能替代对业务解释的检查，也不能用注释掩盖大类、万能组件或循环依赖。

每个可交付代码批次按根规范做一次只读独立评审；纯文档不要求代码评审子智能体。修复本批阻断项，记录非阻断发现，不无限循环扩张任务；报告实际运行的检查和未验证范围。

页面、任务、未来 AI/Agent 共用业务应用契约，现有业务不变量测试持续保护各入口。DEC-022 要求首个切片通过页面接口及测试中的第二调用入口验证同一应用服务的授权、校验、事务和审计，覆盖未授权/跨租户、无效状态或过期方案、重复提交及结果对账；第二入口使用显式可信身份上下文，不绕过校验，也不把上下文创建权开放给任意调用方。实际开发 AI 时再增加参数/schema、员工委托、确认凭证和恶意材料指令等专项验证；现在不引入模型、Agent、外部工具服务或 AI 评测框架。

## 9. 工程准备与分阶段验证

DEC-022 的阶段边界统一见[工程准备规范第 6.1 节](../开发前准备与工程规范.md#61-准备事项的完成阶段dec-022)。实际验证与编码启动范围另行明确；在授权范围内由最小隔离实验验证关键组合，原型不默认成为正式代码。

1. 首个切片开发前：核心兼容版本、许可与锁定；最小格式/类型/架构及构建命令；jOOQ/OpenAPI 生成链和产物入库政策；真实 PostgreSQL 角色、租户事务连接、最小身份授权及隔离结果。
2. 工程准备中：核实 Linux Runner、标签/执行权限、测试容器条件、依赖/镜像来源、秘密与产物管理，运行必要流水线并如实报告，不将本地结果当作 CI 结果。
3. 随功能交付：用对应金标准验证规则、精度、状态、并发、权限、持久任务和生成结果；首个切片验证页面/第二入口及完整对账，其他模式与专项按实际依赖补齐。
4. 真实上线前：完整 P0、迁移、恢复演练、离线交付、容量安全和发布回退的实际结果；不把全部专项提前变成工程初始化的门槛。
