## 2. 结果

| 场景 | 结果 |
| --- | --- |
| 期初 +320.50 | 账户总额与可用均为 320.50，且**没有生成收款记录** |
| 期初 −120.00（历史欠费） | 总额与可用均为 −120.00 |
| 同一 requestId 重复提交 | 余额不变（幂等），第二次返回当前余额而不是报错 |
| 期初日期所在月已锁定 | `409 PERIOD_LOCKED`；解锁后成功 |
| 金额为 0 | 参数错误 |

## 3. 实现要点

- `account_entry.kind='OPENING'`，与收款分录并列但语义不同：不产生实收、不参与分配来源；
- 幂等台账 `funds.creation_request` 的 kind 增加 `OPENING`（V30）；
- 幂等命中时返回**学员当前余额**（分录 resource_id 不是学员 id，这点第一版写错并被测试抓到）。

## 5. 期初批量导入

| 场景 | 结果 |
| --- | --- |
| 一行同时带金额 500.00 与课时 4.00 | 成功，合计金额 500.00、合计课时 4.00 |
| 一行学员号不存在 | 该行 `FAILED`，其他行成功（逐行独立事务） |
| 同一批次重跑 | 余额不叠加（请求号由批次号派生） |
| 干跑 | `DRY_RUN`，合计照常给出但未写库 |
| 学员没有在读报名 | 金额照常导入，课时注明"没有在读报名，课时未带入" |

## 6. 批次对账

| 场景 | 结果 |
| --- | --- |
| 导入后立即对账 | 1 行 `MATCHED`，应有 = 实际 = 700.00 / 3.00 课时 |
| 导入后再人工补录 150.00 | `MISMATCHED`，应有 200.00、实际 350.00、差额 150.00 |
| 批次里有失败行 | 该行应有值存在、实际为 0，计为差异（不隐藏） |

## 7. 限制

- 未建"期初课时"，课时结余仍按消费对账推算；
- 无期初批次与汇总报告（逐学员调用）；
- 负余额无独立欠费台账。
