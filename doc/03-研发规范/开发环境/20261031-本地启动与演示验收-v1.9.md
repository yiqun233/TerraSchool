## 1. 日常启动和停止

本地页面查看使用WSL Ubuntu中现有PostgreSQL18，单独项目库teraschool_dev。Windows运行前后端；需要Java25、Python3、Node24、pnpm11.23.0及可用的Ubuntu WSL。日常启动不需要Docker Desktop。

双击根目录start-local.cmd，或在PowerShell执行：

```powershell
cd D:\TeraSchool
.\start-local.cmd
```

脚本检查WSL数据库，必要时启动Ubuntu现有postgresql服务；首次建立带归属标记的项目角色/库，执行迁移、生成及构建、一次性装载合成资料并启动前后端。打开 http://127.0.0.1:5173 ，保持启动终端运行。

双击stop-local.cmd或在启动窗口按Ctrl+C停止前后端。**不停止共享WSL PostgreSQL，也不停止WSL本身**，账号和数据保留。没有日常清库、删角色或删卷操作。

```powershell
python -X utf8 tools/dev/run.py status
python -X utf8 tools/dev/run.py prepare
python -X utf8 tools/dev/run.py check
```

prepare可单独准备环境；运行期间不会重复构建。check需要项目已启动，验证登录、代理、学校范围及只读写入拒绝。check --write额外创建/改名一条合成自检校区，持久requestId复用；普通check不修改组织。

## 4. WSL管理边界

项目使用本机Ubuntu中postgres的Unix套接字管理入口（Windows wsl -d Ubuntu -u root，再runuser -u postgres），不修改sudoers或全局权限，不要求在终端保存超级用户密码。管理入口只用于专用库/角色开通、迁移前核验和合成装载；Java运行通过5432及受限账号连接。

teraschool_dev和ts_migrator/ts_app/ts_identity/ts_session/ts_audit均有本环境归属标记。已有同名库/角色标记不匹配时，在写入前拒绝，不接管或覆盖。ts_migrator拥有项目结构但不是超级用户，无CREATEDB/CREATEROLE；应用账号保持既定职责，不拥有结构或BYPASSRLS。

初始化不删除其他库，不更改vecuser，不停止共享服务。启动进程持系统文件锁；停止通过回环控制端口及随机凭证通知实际监督进程，只清理自己启动的Java/Node进程树。数据库提供方式和地址进入构建指纹，切换后不会因复用旧build.json而继续加载55432。

## 5. 本次Docker到WSL的切换与清理

用户明确要求改用WSL，并单独授权删除WSL中无用vectordb。一次性工具tools/dev/migrate_wsl.py先备份Docker项目库，再恢复到带标记的WSL专用库。源与目标全部项目表逐表比较行数及按UTC规范化的内容摘要，核对成功后切换；已有不同目标数据不覆盖。恢复使用单事务，失败时原库、备份保留。

迁移分为数据核验、目标准备/连接文件、源停止三阶段。准备中断后重跑根据受限恢复记录续做，不重新覆盖目标库；完成记录存在且通过才直接返回。日常start/stop不调用Docker；只有这一历史迁移工具需读取旧容器。

本机备份和记录：

- .local/dev/backups/teraschool_dev-docker.dump：原演示库自定义格式备份。
- .local/dev/backups/docker-manifest.json：源表行数/摘要及备份SHA256。
- .local/dev/backups/docker-environment.json：原容器环境凭据，受限保管。
- .local/dev/backups/wsl-migration-result.json：切换核对记录。
- .local/dev/backups/vectordb-wsl.dump：用户授权删除前的vectordb备份。
- .local/dev/backups/vectordb-deletion.json：删除授权来源及备份摘要。

vectordb原有一个Navicat空闲连接；备份成功后按用户的删除授权仅断开该库连接并删除库，未停止PostgreSQL、未删除vecuser。旧Docker项目容器已停止，容器/卷留作回退副本，不再用于日常运行，也不自动双写或清理。

## 7. 常见问题

- WSL未启动：start会唤起Ubuntu；PostgreSQL未运行时尝试启动已有服务，失败需检查Ubuntu内PostgreSQL状态，不要求启动Docker Desktop。
- 提示库/角色归属不匹配：核对是否另一工作区已使用同名资源，不手工改标记绕过保护。
- 5173/8081占用：不终止其他程序，先status检查本项目实例，必要时stop。
- 准备或启动中执行stop：互斥保护会提示等待或在原终端Ctrl+C，不打断迁移或停止数据库。
- 前端源码由Vite热更新；后端修改需stop再start。真实日志在.local/dev目录。
- 全套自动化入口仍为python tools/engineering/verify.py，它使用Docker临时库和随机端口，结束清理；不要改为复用WSL日常库。运行前先stop本地前后端，避免Windows运行中JAR被占用。

## 人事与学校维护入口

组织目录的学校行提供管理入口；员工行提供人事档案、账号绑定和档案附件，教师行提供资质维护。敏感人事档案需要独立的 `PERSONNEL_READ` / `PERSONNEL_MAINTAIN` 授权；新学校不自动授予这两项，管理员需明确配置。学校停用后保留读取，但拒绝该校资料写入。

附件需要私有S3配置。请在受保护的 `.local/dev/storage.json` 提供 `endpoint`、`region`、`bucket`、`access-key`、`secret-key`，运行 `python -X utf8 tools/dev/run.py prepare` 后重启。配置缺失时普通功能仍能运行，上传提示存储未配置；不得把密钥提交到Git。详细限制见[附件文档](../../02-架构设计/文件存储/20261101-人事附件与照片-v0.2.md)。


## 本人邮箱与通讯资料

登录账号须先由授权管理员绑定员工，才可在“我的权限”中打开“我的邮箱配置”。密码或授权码只写入、不回显；本批只保存配置，不连接SMTP或发送邮件。员工列表的“通讯资料”需要独立人事查看/维护权限，这些标识不会自动建立外部登录。

本机首次准备时生成受保护的 `.local/dev/mail-credential-key.json`，每次启动都会验证其格式及与数据库中主密钥校验值是否一致；密钥丢失或与已有记录不匹配时拒绝继续启动，需从受控备份恢复。请独立、安全备份密钥文件和数据库，不要把密钥提交Git或发在聊天中；当前没有自动轮换或丢失恢复功能。详情见[邮箱配置文档](../../02-架构设计/身份权限/20261101-员工本人邮箱配置-v0.2.md)。
