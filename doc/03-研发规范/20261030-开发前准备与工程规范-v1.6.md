## 1. 当前重点

用户已明确业务清楚，以已有需求和旧系统为业务基线。现在推进工程规范、文档规范、项目结构和技术选型，不再启动一轮全量需求调研，不要求把全部财务案例、菜单映射和生产数据在开工前一次性补齐。

旧源码、数据库脚本、手册、研究结果和已保存的环境访问资料，是开发时核对细节的入口。具体功能设计时先查已有材料；只有材料冲突、无法确定的行为、需要改变旧业务或新增范围才询问用户。不得用“业务已清楚”替代关键计算与授权验证，也不得把局部核验扩大成全项目停工。

当前仍只有文档，Java/Spring Boot、PostgreSQL 和 React/TypeScript 主线已确认，见[技术决策记录](../05-决策与问题/20261030-技术决策记录-v1.5.md)；未开始新代码实现，具体版本及其他组件不自动锁定。

## 2. 开发规范

| 类别 | 规则 |
| --- | --- |
| 业务入口 | 页面、任务、未来 AI/Agent 复用同一应用服务；完整鉴权、校验和状态约束在业务入口执行 |
| 模块边界 | 按业务职责组织；每类权威事实有唯一所有者；跨模块通过公开契约，禁止直接修改他域数据 |
| 契约 | 输入输出使用明确类型，禁止直接暴露持久化实体；接口版本、分页、时间/时区、金额/课时单位、空值与错误语义统一 |
| 身份会话 | 已选 Spring Security、服务端会话与 Spring Session JDBC/PostgreSQL，见 DEC-008；版本、配置、撤销并发与受限身份访问路径在实现前验证 |
| 授权 | 保留角色、账号增减、按操作的数据范围和字段控制；默认拒绝、deny 优先；覆盖查询、关联选项、写入、统计、导出和下载 |
| 租户隔离 | 标准 SaaS 共享库/表 + tenant_id + PostgreSQL RLS；实际事务连接绑定租户，缺失拒绝；文件/缓存/任务同样隔离；本地版同代码独立部署，保留专属选项 |
| 数据一致性 | 关键不变量确定原子边界；非天然幂等写操作可安全重试；并发更新显式检测版本或采用经验证的并发协议 |
| 状态 | 业务状态与转换明确；草稿、发布、审批与执行可区分；不以多个独立布尔或一个大枚举掩盖状态维度 |
| 任务与事件 | 长任务持久化、可查询和恢复；事件有身份与版本，消费者幂等；不在长事务里等待外部系统或模型 |
| 配置 | 环境差异通过配置；业务规则配置有版本与作用域；禁止客户名分支和秘密常量散落业务代码 |
| 异常 | 区分输入不合法、权限不足、状态/版本冲突、业务拒绝与系统故障；错误可机器判断并可追踪 |
| 日志与审计 | 日志用于诊断，审计记录业务责任；不记录密码、令牌和原始敏感材料；失败与拒绝也有适当记录 |
| 验证 | 围绕真实不变量选择单元、集成、契约和端到端测试；资金、授权、租户隔离与并发不能只靠 mock |
| 交付 | 小范围可验收批次；变更同步文档；完成后记录一次只读评审及实际验证，不循环扩张范围 |

接下来按 Java 与 React/TypeScript 主线确定命名、格式化、静态检查和框架用法，并由工具执行；数据访问已确认 jOOQ + Flyway，具体版本和生成配置继续核验；前端组件等剩余事项继续讨论。

## 中文注释与可读性（用户已确认）

主要由 AI 开发，用户负责验收，也会阅读和修改代码。业务代码必须有清楚的中文注释，便于人工理解和维护：

- 公开业务操作说明用途、关键参数含义与单位、权限/状态前提、结果、异常及副作用。
- 资金、课时、权限、状态转换、算法、事务、幂等与并发处理，解释为什么这样做、边界条件以及必要的旧规则证据。
- 模块入口说明职责和依赖；特殊 SQL、配置开关和历史兼容写清原因与适用范围。
- 不逐行翻译语法，不用大量无意义注释替代清晰命名、合理拆分和测试；代码变更同步更新注释。
- 禁止在注释中记录密码、token 或真实客户敏感数据。核心测试明确说明验证的业务场景与预期。

## 3. 文档规范

- 当前需求、规则、设计和执行文档以本文件夹为统一入口，不再增加多个“总计划”作为平行事实来源。
- 文档标注标题、版本、状态、修订日期和关联；明确区分已确认需求、技术提案、已确认决策和实际实现。
- 需求写业务结果和验收；设计写职责、数据、契约、状态及一致性；决策写备选、取舍与验证；任务写本批范围和结果。
- 接口与数据结构文档优先从权威契约生成，避免手工维护多份相同字段定义；生成方式随技术选型确定。
- 旧系统证据保留源材料位置和必要的旧行为说明；不将旧表名或类名直接当成目标结构要求。
- 设计变更同步相关规则、契约、案例和决策；不靠历史聊天或已删除的文件才能理解当前状态。
- 未完成的条目如实记录，但不重复要求用户确认已明确的业务。问题要说明已查材料、剩余歧义、受影响操作和建议。
- 普通文档不保存环境密码、令牌、真实客户数据；访问配置与示例分开管理。
- 不维护工期、开发人员规模和交付日期；业务期限、SLA 和修订日期按需要记录。

单模块测试随模块维护；跨模块验证才使用独立测试目录。内部契约可随模块维护，不为每个 DTO 创建独立包。worker、移动应用和迁移工具是否独立工程由实际技术与交付决定，不提前创建空应用。

新工程建立时必须明确依赖方向、公开接口和禁止访问的内部区域；能用静态或架构测试检查的规则进入自动化检查。共享部分只承载跨域稳定能力，不吸收全部业务。

## 5. 技术选型推进方式

按以下顺序形成可实施的一套组合方案，不孤立挑选互不兼容的工具：

1. 应用形态、领域所有权、事务与部署边界。
2. 语言/运行时、后端框架、数据库、数据访问与结构迁移。
3. 管理端、移动端、排课工作台、接口契约与类型共享。
4. 已选身份会话/权限与租户隔离方案的落地细节、任务、事件、文件、报表与打印。
5. 本地开发、SaaS 和内网交付、构建发布、备份恢复与观测。

每项记录需求约束、合理备选、选择理由、放弃原因、许可与运维代价、关键验证和状态。无需每个小库都做大型比较；重大选择需讨论确认，常规实现细节在已授权方案内自主处理。

选择标准以复杂业务正确性、维护与测试、契约清晰、事务并发、隔离、本地交付和扩展为主。未来 AI 是否容易接入是一个条件，不能替代这些核心条件，也不要求现在挑选 AI 框架或模型。

主线选择已完成，见[技术决策记录](../05-决策与问题/20261030-技术决策记录-v1.5.md)；具体组件、版本、工程目录和部署布局尚需细化。AI 初期辅助，后期主入口是演进可能，当前不开发 AI，也不要求先重新盘点全部业务才推进。

## 6. 其他开发前准备

| 事项 | 开发前需明确的最小内容 | 可后续补充 |
| --- | --- | --- |
| 旧系统对照入口 | 源码、SQL、手册与研究索引；环境用途与访问资料的安全保存位置 | 对应功能的细节与实例，不要求一开始逐行读完旧代码 |
| 环境与权限 | 区分线上、演示、本地版和新测试环境；标注允许的只读/写操作 | 实际访问时核验地址与凭据有效性，不在文档输出秘密 |
| 领域与契约 | 核心实体、状态与动作、资金履约原子边界、身份与权限 | 具体字段和例外在对应功能设计中细化 |
| 数据规则 | ID、业务编号、金额/课时单位、时间/时区、删除历史与版本策略 | 与最终数据库对应的类型、索引与迁移实现 |
| 开发环境 | 可重复安装启动、示例配置、依赖锁定与测试数据隔离 | 技术确认后搭建；不先安装全套中间件 |
| 质量门禁 | 构建、格式/静态检查、必要测试、契约和数据结构变更检查 | 性能、恢复、内网交付按业务和交付阶段扩展 |
| 首个切片 | 明确第一条完整业务流、样例、交付范围和预期结果 | 其他场景随功能展开，不等待所有场景一次确认 |
| 发布与恢复 | 环境区分、秘密管理、结构升级和备份恢复策略 | 正式交付前通过恢复与切换演练 |

已有地址、账号或数据材料不等于刚刚验证过可访问；已有代码也不等于每条旧行为都已正确理解。准确记录核验状态，但不因此重新打开已确定的业务范围。

## 7. 开发准备就绪的判定

能明确回答“采用什么技术、代码放在哪里、模块如何协作、接口和数据遵守什么约定、怎样验证、如何运行与定位问题、先交付什么”时，可开始正式工程和首个切片。

业务细节对照、金标准扩充和菜单追踪随功能持续进行。只有影响当前动作的实际歧义阻塞该动作，不作为全项目统一的开工障碍。
