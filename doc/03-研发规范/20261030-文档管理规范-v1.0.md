## 1. 分层与归属

| 目录 | 唯一职责 |
| --- | --- |
| 00-项目基线 | 目标、范围边界和全局约束 |
| 01-业务需求 | 功能清单、业务规则与验收；按招生、报名、教务、财务等功能细分 |
| 02-架构设计/总体 | 逻辑架构、工程结构、跨域设计与 AI 预留 |
| 02-架构设计/选型 | 备选、论证与兼容验证，不代替已确认决策 |
| 02-架构设计/具体功能 | 有实际设计时创建，如身份权限、报名、排课、财务；不先建空目录 |
| 03-研发规范 | 开发、文档、接口、测试和交付等规范 |
| 04-执行计划 | 唯一执行路线；必要任务拆解和阶段验收记录 |
| 05-决策与问题 | 生效决策、未决事项与实际风险 |
| 06-旧系统研究 | 旧系统事实、算法、数据与证据，不能作为新技术锁定依据 |

功能需求说明“做什么及如何验收”，架构说明“如何组织及保证正确”，规范说明“一致做法”，决策说明“已选择什么及为什么”，执行路线说明“按什么依赖推进”。避免一事多处维护完整副本。

## 2. 命名、日期与版本

正文格式：`YYYYMMDD-文档名称-v主版本.次版本.md`，例如 `20261030-工程结构与模块边界-v1.0.md`。文件名日期是创建日期，修订时保持不变；修订日期写元数据。搬移旧材料不把旧系统观察日期冒充新文档创建日期。

根目录 `AGENT.md` 为用户指定的固定操作入口，保留固定文件名，其版本和日期写在头部；其他正式文档，包括文档导航，均遵循正文命名。

主版本用于明确影响范围或约束的重大变化；次版本用于兼容补充和整理。仅排版、错字和链接修复可以保持版本并更新修订记录。内容升版时重命名现行文件、同步索引及全部入链，避免“文件名 v1.0、正文 v1.2”。

每个主题维护一份现行文档；历史优先由 Git 保存。不自动保留平行“最终版”“新版”或归档副本。确需可独立引用的历史基线时，明确状态和替代关系后单独安排。

## 3. 元数据与状态

每份文档包含标题、版本、状态、创建日期、更新日期、维护方及关联文档。业务或技术有固定编号时保留稳定编号，不依赖可变文件名作为唯一身份。

状态明确：Draft 为草稿，Review 为评审中，Accepted/Approved 为明确确认内容，Reference 为参考。一个技术分析文档可以同时包含已确认主线和未决建议，应逐项区分，不通过文件整体状态扩大批准范围。

实施状态独立记录：未开始、进行中、已实现、已验证、已验收不能混用。旧系统的研究完成不等于新系统功能完成。

## 4. 更新与链接

- 新增功能或改范围：更新功能清单、规则和执行任务。
- 改业务口径、状态、权限：更新所属功能设计、案例和必要决策。
- 改技术、部署、数据结构或接口：更新相应决策、设计、契约与验证记录。
- 确认结论后及时更新旧的“未定”表述；未选择的细节继续列为未决。
- 文档间使用相对链接；旧源码可写原始证据位置，缩略路径标明为线索而非可直接打开路径。
- 搬移、改名、升版必须修复入链；检查链接存在和根目录范围，不依赖已删除文件或旧绝对路径。
- 新文档加入导航，完成后检查命名、版本、元数据、状态、链接和相互一致性。

## 5. 内容与安全

使用中文，以清楚的业务意义和设计理由为主。普通文档不复制原始客户材料和秘密，不维护生产账号密码。环境入口与凭据通过受控配置管理，文档只记录用途、访问边界和核验状态。

不写开发工期、人员编制或交付日期。不伪造业务确认、测试通过或线上可用；建议、假设、推断与证据分别标注。
