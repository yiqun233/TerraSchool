## 为什么先做防护而不是直接做 2–5

`product.price_version.settlement_mode` 接受 0–5 六种取值，但消费与退费目前只按**模式 1（平均价格）**计算。也就是说：**发布一个模式 2–5 的价格，系统会照常读取、照常消费、照常退费，但金额按错误的公式算出来，而且没有任何提示。** 这比"不支持"危险得多。

在公式落地前，先把这条路封死：发布、消费、退费三处都显式拒绝未实现的模式。

## 旧系统的权威定义（可直接引用的证据）

模式语义来自旧客户端自带的帮助文本 `TSchool_Client_Module/com/helxsoft/tschool/client/module/studentregister/dialog/SettlementModeDialog.java`：

| 模式 | 旧系统原文要点 |
| --- | --- |
| 0 自动 | 系统按班型自动选择：VIP 走"平均价格"，大班走"课程匹配" |
| 1 平均价格 | 每课时费用 = 所报课程总费用 ÷ 所报总课时；班表里**任何**课程课次都算消耗；消耗超过所报总课时后不再计算 |
| 2 课程匹配 | 每课时费用 = 该课次课程对应的"所报该课程平均费用"；只有**包含所报课程**的课次才算消耗；该课程消耗超过所报课时后该课程课次不再计算 |
| 3 完全匹配 | 计价方式与模式 2 相同，差别在课时与课程的匹配条件（旧文本表述接近，需以源码 `CSItemClose`/结算计算实现为准） |
| 4 | "平均价格"的改进型：退课时后按新单价重算 —— `(费用 − 退费) ÷ (课时 − 退课时)`，示例 100 课时 1000 元、退 50 课时退 200 元 → 新单价 160 元/课时 |
| 5 | "课程完全匹配"的改进型，公式形式同上 |

模式 2/3 的示例（旧系统原文）：报名"语文 1 课时 200 元 + 数学 3 课时 1800 元"——模式 1 每课时 500 元；模式 2/3 语文 200 元/课时、数学 600 元/课时。

**重要结论**：模式 2、3、4、5 都要求**一条报名记录包含多门课程及各自的课时与费用**。当前模型是"一条报名 = 一个价格版本 = 一门课程"，因此模式 2–5 不是加个公式就能做的，需要先建模"报名课程明细"。

## 本批实现

| 位置 | 行为 |
| --- | --- |
| 价格发布 `publishPriceVersion` | 结算模式 ≠ 1 时返回 `409 SETTLEMENT_MODE_UNSUPPORTED`，草稿仍可保存 |
| 关闭课次 `closeLesson` | 出勤学员的报名模式 ≠ 1 时返回 `409 SETTLEMENT_MODE_UNSUPPORTED`（防历史数据） |
| 退课时 `cancelHoursAndReturnToAccount` | 报名模式 ≠ 1 时返回 `409 SETTLEMENT_MODE_UNSUPPORTED` |
| 价格表单 | 结算模式仅可选模式 1，并提示"发布其他模式会被拒绝" |

## 后续实现模式 2–5 的前置条件

1. **报名课程明细**：一条报名可包含多门课程，各自记录课时与费用，且与价格版本快照一致；
2. **课次课程匹配**：按课次的课程（curriculum）匹配报名明细，决定该课次是否计消耗、用哪个单价；
3. **超课时封顶**：按课程维度而不是报名总额度判断"消耗超过所报课时后不再计算"；
4. **模式 4/5 的重算**：退课时后以"剩余费用 ÷ 剩余课时"重算单价，并处理尾差；
5. **金标准案例**：每个模式至少一组带旧系统行为证据的数值案例，作为回归基线。

在上述条件满足前，模式 2–5 保持"可建模、不可发布、不可消费、不可退费"。

## 已知边界

- 模式 0（自动）依赖班型（VIP/大班）判断，当前没有班型概念，同样被拒绝；
- 已有价格数据若存在非模式 1 的已发布版本（例如导入的历史数据），消费与退费会被拒绝而不是按模式 1 计算——这是刻意的失败优先；
- 本批没有迁移历史数据，也没有为模式 2–5 建表。
