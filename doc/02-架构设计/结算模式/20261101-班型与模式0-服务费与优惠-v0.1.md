## 结算模式 0（自动）

旧系统原文：模式 0 由系统按班型自动选择——**VIP 走"平均价格"（1），大班走"课程匹配"（2）**。

新系统实现：

| 项 | 做法 |
| --- | --- |
| 班型 | `teaching.class.class_type`：`VIP` / `LARGE` / `NORMAL`，建班时选择，默认 `NORMAL` |
| 解析时机 | 报名进班时（`addMember`）解析：声明值 0 → VIP 得 1，其余得 2 |
| 留痕 | `enrollment.declared_settlement_mode` 保存声明值，`settlement_mode_resolved_at` 记录解析时间；解析只发生一次（`update ... where settlement_mode=0`） |
| 未解析前 | 退费返回 `409 SETTLEMENT_MODE_UNRESOLVED`——没有班型就没有口径，不猜 |
| 发布 | 模式 0 与 1–5 都可发布；越界值在起草阶段就拒绝 |

之所以在"进班"解析而不是"创建报名"：创建报名时学员还没有班级，班型无从谈起；进班是第一个能确定班型的时刻，也是后续消费与退费的共同起点。

## 服务费

价格版本里的 `service_fee` 之前只是快照，不参与金额。现在：

**应收 = 商品价格 + 服务费**，写入报名原始应收（`ORIGINAL`），服务费不摊进课时单价——课时单价仍只由价格与课时决定，这样退课时按课时退不会把服务费重复算进去。

这是**解释性实现**：旧系统把服务费作为独立结算项，但其与应收、退费的精确关系没有可引用的规则文档，待财务确认。示例：价格 1000、服务费 100 → 净应收 1100。

## 优惠

只做"一次性减免"，不做优惠券、阶梯折扣、促销规则：

| 项 | 内容 |
| --- | --- |
| 表 | `enrollment.discount`（金额、原因、创建人） |
| 落账 | 写一条 `ADJUSTMENT` 应收减项，净应收相应减少 |
| 校验 | 减免后不得为负（`DISCOUNT_EXCEED_RECEIVABLE`）；报名须 ACTIVE |
| 权限 | 复用 `ENROLLMENT_MAINTAIN`；审批走通用审批流（如机构要求） |
| 界面 | 报名详情「登记减免」：金额 + 原因 |

同样属解释性实现：旧系统有优惠/减免字段，但"减免如何影响退费单价"没有明确口径，当前实现是**只减少应收、不改单价**。

## 已知边界

- 服务费不按课时摊销，也不参与退费计算；
- 优惠无有效期、无叠加规则、无审批强制；
- 模式 0 解析后不可回改（换班型不改已解析模式）；
- 模式 4/5 的净额仍只扣"退课时"金额，未扣优惠。

## 影响说明

既有报名（服务费为 0）的应收不变；SC01 主例（1000 元、服务费 0）结果不变。

## 优惠参与计价：旧系统证据（v0.2）

旧系统 `FClassStudent#getConsumeEHM`（`参考资料/analysis-v2/.../_settlement/FClassStudent.java`）里，五种模式对优惠的处理**并不一致**：

```java
long fee   = curricula != null ? curricula.getFee() : 0;   // 默认：课程费用
if (MODE_1 /*平均价格*/)              fee = getTotalPrice() - getPriceDiscount();
else if (MODE_5 /*完全匹配·退课时后*/)  fee = curricula.getFee() - curricula.getFeeQuit();
else if (MODE_4 /*平均价格·退课时后*/)  fee = getTotalPrice() - getPriceDiscount() - getTotalFeeQuit();
// 模式 2、3 落回默认：curricula.getFee()，既不扣优惠也不扣退费
```

| 模式 | 旧系统是否扣优惠 | 我们的实现 |
| --- | --- | --- |
| 1 平均价格 | **扣**（总价 − 优惠） | ✅ 已对齐 |
| 2 课程匹配 | 不扣（用课程费用原值） | ✅ 与旧系统一致 |
| 3 完全匹配 | 不扣（用课程费用原值） | ✅ 与旧系统一致 |
| 4 平均价格·退课后 | **扣**（总价 − 优惠 − 已退） | ✅ 已对齐 |
| 5 完全匹配·退课后 | 不扣（课程费用 − 已退） | ⚠️ 我们按"按金额比例摊分优惠"实现，比旧系统严格 |

关于模式 5 的偏差：旧系统不扣优惠，会让课程模式的实际消耗**超过**折后应收（旧系统用报名级优惠，不往下摊）。我们选择摊分，理由是避免"应收 800 却按 1000 消耗"的账实不符；这条偏差已记录在[待确认问题登记](../../05-决策与问题/20261101-待确认问题登记-v0.1.md)（Q2），如果要求与旧系统完全一致，可以去掉摊分。

模式 2/3 未扣优惠，如果业务认为"同一份优惠只影响一半模式"不合理，需要一起改——这仍是 Q2 的结论问题，不是实现遗漏。
