## 一、旧库相关表（实测字段）

| 旧表 | 作用 | 关键字段 |
| --- | --- | --- |
| `H_Student_Register` | 报名主表 | `Code`、`Student_Code`、`School_Code`、`Settlement_Mode`、`Class_Begin_Date/End_Date`、`Is_Quit`、`Quit_Date`、`Is_Audited`、`Is_Finance_Lock`、`Pre_Code`、`Price_Discount_Type` |
| `H_Student_Register_Curricula` | 报名课程明细 | `Student_Register_Code`、`Curricula_Code`、`CS_Hour`、`Price`、`Fee`、`CS_Hour_Quit`、`Fee_Quit`、`Pay_Money` |
| `H_Student_Register_Consume` | 报名级金额汇总 | `Price`、`Price_Discount`、`Fee`、`Fee_Quit`、`Fee_Service`、`Fee_Quit_Service`、`Receivables_Money`、`Consume`、`Consume_Lave`、`Pay_Money`、`Arrears_Money`、`CS_Hour`、`CS_Hour_Quit`、`CS_Hour_Consume` |
| `H_Student_Register_Pay_Record` | 收款流水 | `Student_Register_Code`、`Date_Stamp`、`Money`、`Is_Account_Pay` |
| `H_Class_Student_CS_Item_Consume` | 逐课次消费 | `Student_Register_Code`、`CS_Item_Code`、`Consume_EHM` |

已经能看出：**旧库的课程明细结构（`CS_Hour`/`Price`/`Fee`/`CS_Hour_Quit`/`Fee_Quit`）和新系统的 `enrollment.enrollment_course` 几乎一一对应**——这是本轮模式 2–5 能落地的前提。

## 二、字段级映射

分类：**A** 可直接映射（语义一致）；**B** 需业务确认（有多种合理做法）；**C** 无法映射（新系统没有对应物或旧数据不可信）。

### 2.1 报名主表 → `enrollment.enrollment`

| 旧字段 | 新字段 | 类 | 说明 |
| --- | --- | --- | --- |
| `Code` | `migration.import_log.legacy_id` | A | 旧主键只进台账，不进业务表 |
| `Student_Code` | `student_id` | A | 先迁学员，按学员号关联 |
| `School_Code` | `school_id` | A | 需一张学校映射表 |
| `Settlement_Mode` | `settlement_mode` / `declared_settlement_mode` | B | 旧值 0–5 与新模式 0–5 同名，但**旧库模式 0 的解析结果要重算**（旧系统按当时的班型解析） |
| `Is_Audited` | `status` | A | 已审核 → `ACTIVE`，未审核 → `PENDING_AUDIT` |
| `Is_Quit` / `Quit_Date` | `status`（退班） | C | 新系统没有"退班"状态；**建议**：退班报名不迁移，或迁为 `ACTIVE` 并在备注里记退班日期 |
| `Is_Finance_Lock` | — | C | 新系统用财务期间锁月，不按报名锁 |
| `Pre_Code`（前一条报名） | — | C | 旧"拼接"关系无对应；见 §四 选项 3 |
| `Class_Begin_Date` / `Class_End_Date` | `enrolledOn`（近似） | B | 旧日期是开班区间，不是报名日期；**建议**用 `Register_Time` 的日期 |

### 2.2 课程明细 → `enrollment.enrollment_course`

| 旧字段 | 新字段 | 类 | 说明 |
| --- | --- | --- | --- |
| `Curricula_Code` | `curriculum_id` | A | 需课程映射表 |
| `CS_Hour` | `hours` | A | 旧为 0.01 课时单位，需除以 100 |
| `Fee`（该课程应收） | `amount` | A | 旧金额单位为分，需除以 100 |
| `CS_Hour_Quit` | `cancelled_hours` | A | 同上换算 |
| `Fee_Quit` | `cancelled_amount` | A | 同上换算 |

### 2.3 收款 → `funds.receipt` + `funds.account_entry`

| 旧字段 | 新字段 | 类 | 说明 |
| --- | --- | --- | --- |
| `Code` | 台账 `legacy_id` | A | |
| `Money` | `amount` | A | 分 → 元 |
| `Date_Stamp` | `occurred_on` | A | 旧为 `yyyyMMdd` 整数 |
| `Is_Account_Pay` | `method` | B | 旧"账户支付"在新系统里是"分配"而非"收款"；**建议**：`Is_Account_Pay=1` 的行不迁成收款，改为按 §四 选项 2 处理 |
| `Student_Register_Code` | 关联报名 | B | 新系统收款挂在学员、再分配到报名；需要按旧报名把收款分配到对应报名 |

### 2.4 消费 → `teaching.consumption`

## 三、无法映射 / 需要丢弃的旧语义

| 旧语义 | 处理建议 |
| --- | --- |
| 报名"锁账"（`Is_Finance_Lock`） | 丢弃，改由新系统财务期间锁月 |
| 学员"退班"状态与退班日期 | 丢弃或在备注保留文本 |
| 旧"拼接"（`Pre_Code` 指向上一期报名） | 丢弃；新系统消费按报名封顶，见选项 3 |
| 旧优惠类型/活动码/折扣等级 | 丢弃类型，只保留金额（见选项 4） |
| 旧课次 B/C 教师、校区 A/B | 新系统课次只有一个教师/教室，多教师场景丢弃 |

## 四、关键口径选项（请挑一套）

### 选项 1：报名是否迁移？

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **1A 不迁报名** | 只迁学员、收款、期初余额；历史报名留在旧系统查询 | 最快、最少争议 | 新系统看不到历史报名与消费明细；客服要开两个系统 |
| **1B 迁报名 + 课程明细 + 消费汇总** | 报名按旧 `H_Student_Register` 迁，消费只迁累计（不迁逐课次） | 历史可查、可对账 | 逐课次明细缺失，退费重算无法核对 |
| **1C 全迁（报名 + 课程明细 + 逐课次消费）** | 课次也要迁，逐课次消费挂到课次 | 最完整 | 依赖旧课次与新班级的映射，工作量最大 |

**我的建议：1B**。理由是逐课次消费（`H_Class_Student_CS_Item_Consume`）依赖旧课次，而旧课次又要依赖旧班级/排课，链条太长；报名+汇总足以支撑"查历史、对余额"这两个真实诉求。

### 选项 2：期初余额怎么落？

| 方案 | 做法 |
| --- | --- |
| **2A 用收款补齐** | 按旧 `Pay_Money` 造收款记录，再按 `Consume` 造消费，余额自然算出来 |
| **2B 一条期初分录** | 直接写一条 `account_entry`（`kind=OPENING`）等于旧余额，历史收支不迁 |

**我的建议：2B**（若采纳 1A）或 **1B + 2A**。2A 的好处是余额可被新系统重算验证；2B 的好处是简单，但"余额怎么来的"就查不到了。

> 需要新增 `account_entry.kind='OPENING'`，并明确它是否参与期间锁月。

### 选项 3：旧"拼接/超排"怎么办？

- 3A：丢弃，超出课时即封顶（现状）；
- 3B：迁移时把拼接的两条报名合并成一条；
- 3C：实现跨报名消费（工作量大，等于补 Q8）。

**我的建议：3A**，并在迁移报告里列出受影响的报名，交人工判断。

### 选项 4：优惠怎么迁？

- 4A：按 `Price_Discount` 总额落一条 `enrollment.discount`（原因写"旧系统优惠迁移"）；
- 4B：不迁优惠，把它折进 `price`（会导致冻结价格与旧库不一致）。

**我的建议：4A**，保留"原价 + 优惠"两段信息，便于对账。

## 五、对账口径（无论选哪套都要满足）

| 等式 | 说明 |
| --- | --- |
| 旧 `Pay_Money` 合计 = 新 `account_entry(RECEIPT)` 合计 + 期初分录 | 收款对得上 |
| 旧 `Consume` 合计 = 新 `teaching.consumption` 合计 | 消费对得上 |
| 旧 `Fee - Fee_Quit - Consume` = 新余额 | 余额对得上 |
| 旧 `CS_Hour - CS_Hour_Quit - CS_Hour_Consume` = 新剩余课时 | 课时对得上 |

任一等式差额都要进迁移差异报告（见[旧库迁移与对账](20261101-旧库迁移与对账-v0.1.md)），不允许"抹平"。
