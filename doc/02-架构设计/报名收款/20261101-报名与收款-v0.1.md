## 范围与证据

报名到退款闭环的第三步：报名登记（冻结商品与价格快照）、原始应收、审核、收款确认、分配与释放、账户流水。按用户确认的 SC01 基准，本批覆盖 S0–S2：报名待审核 → 审核通过 → 确认收款 1000.00 → 全额分配给该报名。

旧结构 `H_Student_Register` 用布尔字段表达审核、退班、入班、完成，把收款金额直接挂在报名上；`H_Student_Money_Record` 与 `H_Student_Money` 分别保存收款与账户。本批不继承「报名自带余额」的做法：报名只冻结约定金额来源，收款、分配与账户流水由资金模块记账，账户余额始终由带符号流水汇总。

## 数据归属与对象

| 模块 | 对象 | 权威边界 |
| --- | --- | --- |
| 报名 | `enrollment.enrollment` | 学员、学校、产品与价格版本快照（名称、单价、课时、服务费、结算模式），状态与审核 |
| 报名 | `enrollment.charge` | 应收来源：原始约定与后续调整；同一报名只允许一条原始应收 |
| 报名 | `enrollment.creation_request` | 报名登记幂等身份 |
| 资金 | `funds.receipt` | 已确认收款与撤销；收款不等于已分配 |
| 资金 | `funds.allocation` | 把某笔收款分配到某条报名；释放保留历史 |
| 资金 | `funds.account_entry` | 带符号账户流水：收款、分配、释放、收款撤销 |
| 资金 | `funds.creation_request` | 收款幂等身份 |
| 审计 | `audit.enrollment_event`、`audit.funds_event` | 报名与资金动作的成功审计 |

**归属说明（与原设计提案的差异）**：SC01 设计把「当前净应收」放在资金域。本批把 `charge` 放在报名域，原因是资金分配需要读取报名未收金额，若应收同时属资金域会形成报名↔资金循环依赖。现在依赖方向单向：资金 → 报名（只读公开契约 `EnrollmentAccess`），报名不依赖资金。退款时的应收减项由后续批次在同一报名域内追加，资金侧只记录分配释放与退款权益。

## 权限与数据范围

| 动作 | 含义 |
| --- | --- |
| `ENROLLMENT_READ` | 查看报名与报名详情 |
| `ENROLLMENT_MAINTAIN` | 登记报名 |
| `ENROLLMENT_APPROVE` | 审核报名，独立于登记 |
| `FUNDS_READ` | 查看余额、收款与分配 |
| `FUNDS_RECEIPT` | 确认收款、撤销收款 |
| `FUNDS_ALLOCATE` | 分配收款、释放分配 |

审核、收款与分配各自使用独立动作检查（`requireAction`），不因具备登记或查看权限而自动获得。学校停用、授权撤销与这两类写入共用机构锁。

## 记账规则

- 收款确认写 `+amount` 流水；分配写 `−amount`；释放写 `+amount`；撤销收款写 `−amount`；
- **账户总额 = 该学员流水合计**；可用金额即总额（未分配的钱才留在账户里），不另存余额字段；
- **收款可用 = 收款金额 − 该收款的有效分配**；
- **报名未收 = 净应收 − 该报名的有效分配**，净应收为 `enrollment.charge` 合计；
- 分配必须同时满足：收款仍为已确认、收款与报名属于同一学员与同一学校、报名已审核生效、金额 ≤ 收款可用、金额 ≤ 报名未收；
- 撤销收款前必须先释放全部有效分配，避免出现「已被分配的钱被撤销」；
- 同一学员的资金动作先取事务级咨询锁，串行化并发分配与撤销，防止一笔钱被用两次。

金额与课时一律十进制字符串进出，服务端按 BigDecimal 校验两位小数；接口不接受调用方传入的单价。

## 操作与契约

| 操作 | 契约 | 说明 |
| --- | --- | --- |
| 报名能力 | `GET /api/enrollment/capabilities` | 可读学校、是否可登记、是否可审核 |
| 报名列表 | `GET /api/enrollment/enrollments?schoolId&status&page&size` | 先按范围过滤再分页 |
| 报名详情 | `GET /api/enrollment/enrollments/{id}` | 含冻结快照与净应收 |
| 登记报名 | `POST /api/enrollment/enrollments` | 只提交学员、价格版本与业务日期；幂等 `requestId` |
| 审核报名 | `POST /api/enrollment/enrollments/{id}/approve` | 需 `ENROLLMENT_APPROVE`，带 `expectedVersion` |
| 资金能力 | `GET /api/funds/capabilities` | 可收款/可分配的学校 |
| 余额 | `GET /api/funds/balance?studentId` | 总额、已分配、可用 |
| 收款列表 | `GET /api/funds/receipts?studentId` | 含每笔可用金额 |
| 分配列表 | `GET /api/funds/allocations?enrollmentId` | 含释放历史 |
| 未收金额 | `GET /api/funds/outstanding?enrollmentId` | 净应收 − 有效分配 |
| 确认收款 | `POST /api/funds/receipts` | 需 `FUNDS_RECEIPT`；幂等 `requestId` |
| 撤销收款 | `POST /api/funds/receipts/{id}/void` | 有有效分配时拒绝 |
| 分配 | `POST /api/funds/allocations` | 需 `FUNDS_ALLOCATE` |
| 释放分配 | `POST /api/funds/allocations/{id}/release` | 恢复收款与报名两侧可用金额 |

错误使用真实 HTTP 状态与 RFC 9457：`403 ACCESS_DENIED`、`409 VERSION_CONFLICT`、`409 IDEMPOTENCY_MISMATCH`、`409 PRICE_VERSION_NOT_SELLABLE`、`409 ENROLLMENT_NOT_PENDING`、`409 ENROLLMENT_NOT_ACTIVE`、`409 RECEIPT_NOT_CONFIRMED`、`409 RECEIPT_HAS_ALLOCATIONS`、`409 RECEIPT_INSUFFICIENT`、`409 ENROLLMENT_OVERPAID`、`409 STUDENT_MISMATCH`、`409 SCHOOL_MISMATCH`、`409 ALLOCATION_NOT_ACTIVE`、`400 INVALID_INPUT`。

## 事务、并发与审计

1. 事务外先取查看/维护或具名动作范围，事务内取机构锁后复核；
2. 读取价格快照与学员身份用于校验，价格必须是已发布且当天在有效期内；
3. 报名插入与原始应收、幂等记录、成功审计同事务提交；
4. 收款插入与账户流水、幂等记录、审计同事务；分配插入与负流水、审计同事务；
5. 同一学员的资金动作使用 `pg_advisory_xact_lock('funds:' + studentId)`，并对收款行使用 `FOR UPDATE`；
6. 失败/拒绝进入独立失败审计（动作名见验证记录）。

## 本批非目标

- 退课时、退费、现金退出与账户冻结（下一批）；
- 定金/尾款、发票、优惠与减免、服务费独立结算；
- 锁月、财务期间与差额结转；
- 银行/支付渠道对接（收款仍为线下实收的登记）；
- 报名修改、退班、转班与延期。

## 已知边界

- 报名列表按学校分页，未提供跨学校聚合视图；
- 「我的权限」页面未展示 `ENROLLMENT_*`/`FUNDS_*`；
- 收款方式只做受控枚举，未记录票据号与银行流水号；
- 学员选择依赖档案读取权限，缺少该权限的岗位目前无法在页面登记报名（接口本身只要求报名动作）。
