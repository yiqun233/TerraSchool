> 本文只描述**给业务人员使用和验证的权限界面与动作目录**，不改动已有授权算法、委派边界、最后管理员保护、版本与幂等协议。各节中“建议”未标注“已认可”的仍为待评审内容。

## 1. 要解决的问题

现有授权后端已经具备角色模板、按学校分配、账号 ALLOW/DENY、拒绝优先、维护与查看相交、委派范围、最后管理员、版本冲突与审计。问题集中在外层：**业务人员看不到、配不全、验不了**。

2026-11-09 对本地演示库（`teraschool_dev`）的只读核对结果：

| 观测项 | 实际结果 | 影响 |
| --- | --- | --- |
| `local-admin` 直接规则 | 143 条，覆盖 36 个动作 × 4 所学校 | 授权编辑窗口平铺 143 行下拉，无法核对 |
| `local-admin` 角色分配 | 0 条 | 演示库完全没跑过“角色”这一层 |
| 演示角色模板 | 2 个（`LOCAL_ORG_READER`、`LOCAL_ORG_MAINTAINER`），均未分配给任何账号 | 角色功能没有可演示样本 |
| 动作下拉 | 账号授权 18 项、角色模板 19 项，后端目录 47 项 | 学员、报名、收款、退款、教务、审批、财务、迁移、客户公海、品牌等动作**无法在界面上配置** |
| 学校覆盖 | `ORGANIZATION_READ` 4 所 + 1 条功能级；`PERSONNEL_READ` 仅 3 所 | 新建学校后权限不铺开，各动作覆盖不一致 |
| 导航 | “招生渠道”“本人客户”对 `local-admin` 可见，但接口 403 | 业务人员点进去直接报错 |

### 1.1 两个必须单独修的授权缺陷

| 动作 | 被谁校验 | 是否在 `PermissionRules.ACTIONS` | 后果 |
| --- | --- | --- | --- |
| `ENROLLMENT_DISCOUNT` | `EnrollmentService`（报名优惠/减款） | 否 | 授权接口以“无效权限规则”拒绝保存，**该权限永远授不出去**，优惠减免对所有租户不可用 |
| `PERIOD_UNLOCK` | `PeriodService`（`schoolsOf("PERIOD_UNLOCK")`） | 否 | **财务期间解锁无法授权**，锁月后只能直接改库才能解锁 |

两处都不会被现有测试发现：测试夹具用直接 SQL 写入 `account_permission`，绕过了公开授权服务的目录校验。这与 REV-004 修过的 `REFUND_*` 属于同一类事故，属于**第二次重复**。

> 2026-11-09 P0 已把这两项补进动作目录，并通过公开授权接口保存验证；目录与业务代码的一致性检查同时落地，见第 12 节。

### 1.2 目标与非目标

目标：

1. 业务人员登录后能看懂“我有哪些权限、覆盖哪些学校”。
2. 管理员能在界面上看到**所有角色、每个角色能做什么、谁在用**，并完成授权。
3. 演示环境能按岗位比对差异，验收时不用问开发。
4. 目录与实际校验动作不会再悄悄漂移。

非目标：不重做授权算法；不引入通用权限引擎或脚本化策略；不新增默认管理员；不在此批确定岗位矩阵结论（见 BQ-05/06）。

## 2. 旧系统对照与取舍

旧系统（标准版 2026082001）的权限实现来自代码包与 `TSchool_SQLServer.sql` 结构，不是凭印象：

| 维度 | 旧系统 | 本项目现状 |
| --- | --- | --- |
| 目录 | `PopedomCode` 354 个功能码，按业务域分段，中文名在 `getDescription()` | 47 个动作，无中文名与分组 |
| 角色 | `H_Role` + `H_Role_Popedom`，每个功能一行，四列勾选：**读取 / 修改 / 审核 / 反审核** | 动作式：`_READ`/`_MAINTAIN`/`_APPROVE` 分开 |
| 账号例外 | `H_Employee_User_Popedom`，与角色同结构 | 账号 ALLOW/DENY，拒绝优先 |
| 数据范围 | 账号维度，`DataScopeDialog` 五个页签：学校与教学区 / 项目 / 禁止项（只能看本人及下属）/ 客户资源 / 缴费审核缴费原因；EIC 定制版另有“允许项（允许查看所有数据）” | 只有学校 |
| 团队维度 | 由 `H_Seller_Charge`、`H_Teaching_Charge` 等“主管管理”表支撑 | 未实现（BQ-05） |
| 内置角色 | 财务、教务、课程顾问、课程顾问主管、全权限、人力、市场、学习顾问 | 无任何内置角色 |
| 界面 | 一张“权限矩阵表 + 左侧分组行头 + 四个勾选列”，数据权限另开页签弹窗 | 三处下拉框、嵌套弹窗 |
| 保护 | 无最后管理员、无版本、无并发保护、无审计 | 均有 |

**借鉴**：按业务域分组的矩阵视图；角色与账号例外分开呈现；数据范围按维度分页签；提供可直接使用的起始角色。

**不照搬**：单一 `int` 功能码加四个布尔标志（会把“审核”与“修改”混在一个维度）；把系统管理员当作部署级身份；角色与账号权限同构导致来源不清；缺少最后管理员和并发保护。

## 3. 动作目录

### 3.1 单一来源

目录从三处硬编码收敛为**后端一处声明**（`identity` 模块公开契约），每项包含：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `code` | 稳定动作码 | 存储与接口，不随文案变化 |
| `group` | 业务域分组 | 界面分组、我的权限排序 |
| `label` | 中文名 | 所有下拉、矩阵、审计展示 |
| `description` | 一句话说明“这个动作管什么” | 选项提示、动作目录页 |
| `pages` | 对应页面 | 帮助业务人员把权限和菜单对上 |
| `scope` | `SCHOOL`（按学校生效）或 `TENANT`（租户级，不随学校） | 决定范围选择器是否可编辑 |
| `risk` | 普通 / 敏感 | 高风险动作在界面上给出额外提示 |

对外提供 `GET /api/permissions/catalog`：登录即可读，不做学校过滤（它只是说明性目录，不含任何账号数据）。前端所有动作选项由它渲染，删除两处硬编码数组。

### 3.2 一致性校验

新增自动检查，任一条件不满足即失败：

1. 业务代码中 `requireAction`、`requireActionInTransaction`、`hasAction`、`schoolsOf` 等入口传入的字面动作，必须存在于目录。
2. 目录中的每个动作至少有一处真实使用点（防止只登记不校验）。
3. 资源类动作（`<KIND>_READ`/`<KIND>_MAINTAIN`/`_SENSITIVE_READ`）与 `PermissionRules` 的资源种类清单互为子集。

这条检查直接拦掉 `ENROLLMENT_DISCOUNT`、`PERIOD_UNLOCK` 这类漏登记。

### 3.4 补目录的落地方式

1. 目录增加两项，不改存储结构，不改已有规则。
2. 迁移脚本不重写、不清空 `identity.account_permission` 与 `identity.role_action`。
3. 新增回归：用公开授权接口给账号授予这两个动作并调用业务入口，验证放行；撤销后验证 403。测试不得再用直接 SQL 写规则绕过目录校验。
4. 演示库补两条规则只走新的本地演示种子（见第 7 节），不在产品迁移中给任何账号授权。

## 4. 权限管理页面

### 4.1 入口

侧栏“设置 → 权限管理”，路由 `/permissions`。导航项不做权限隐藏，改为**无权限时页面内四态展示**：说明需要 `AUTHORIZATION_MANAGE`、当前账号有哪几项、如何获得。理由是隐藏入口会让业务人员误以为“没有这个功能”。

顶栏现有“我的权限”保留为快捷入口，行为改为跳转到本页第一个页签，不再弹只显示四行数字的窗口。

### 4.2 页签一：我的权限

数据来源：扩展现有 `/api/session/permissions`，新增 `actions` 数组（动作 + 是否功能级 + 学校集合），或在 `GET /api/permissions/catalog` 与现有接口基础上组合，具体以不改动现有字段语义为准（新增字段，不修改既有字段）。

呈现：

```
身份     本地演示机构 / local-admin        租户管理员：否
功能     已开通 34 项 / 共 49 项

组织与身份
  组织查看        4 所学校    组织维护   4 所学校    授权管理  4 所学校
学员档案
  学员查看        4 所学校    学员维护   4 所学校    敏感字段  4 所学校
报名与收款
  报名查看        3 所学校    收款登记   2 所学校    收款分配  仅功能（无学校范围）
```

要求：四态齐全；“仅功能（无学校范围）”必须显式标注，不能让用户以为“有权限但没数据”是缺陷。

### 4.3 页签二：角色

列表字段：名称、代码、状态（可用/停用）、动作数、已分配账号数、是否有权维护。支持按名称/代码检索、包含停用。

打开某角色显示**动作矩阵**：左侧按业务域分组，右侧“允许 / 拒绝 / 未设置”，与旧系统的矩阵视图同构，但用三态代替四个勾选列。矩阵是编辑入口，沿用现有 `role-templates/{id}/replace` 的版本校验与影响保护，不新增写路径。

列表需要后端补充聚合：`RoleSummary` 增加 `actions`（或 `actionCount`）与 `assignedAccounts`，用一条 SQL 聚合，不做逐角色详情请求。

### 4.4 页签三：账号

列表字段：登录名、显示名/员工、状态、角色数、例外规则数、是否在我可管理范围。

详情分三段：

1. **角色分配**：表格（学校 × 角色），沿用现有分配与 `expectedRoleVersion` 协议。
2. **例外规则**：动作 × 学校（或“仅功能”）× 允许/拒绝，支持按业务域折叠。默认折叠为空，不再一次性平铺 143 行。
3. **有效权限预览**（只读）：服务端计算的最终结果，按业务域列出动作与学校，并标出“被拒绝”“范围为空”的原因。

现有 `AuthorizationForm` 的三段结构可复用，改造点是动作选项来源、折叠分组和有效预览。

### 4.5 页签四：动作目录

只读说明页：按业务域列出 49 个动作、中文名、说明、对应页面、是否按学校。用于业务人员自查“这个按钮归哪个权限”，减少来回询问。

### 4.6 与现有弹窗的关系

`AuthorizationManager`、`RoleTemplateManager`、`AccountLifecycleManager` 的写入逻辑保持不变，作为页签内的编辑组件复用；删除“弹窗套弹窗”的入口结构（`MyPermissions` 里的四个并列按钮）。`SchoolCreator` 移到组织目录页，与“新建学校 → 授权铺开”一起说明。

## 5. 角色与起始模板

现有原则是“不创建固定产品岗位模板”，避免把未确认的岗位矩阵写成事实。但演示与试点需要可直接使用的起点。建议折中：

> **提供一组“起始角色模板”，一键生成，生成后即普通可编辑模板**；不是系统内置、不可删除的硬编码角色，也不自动分配给任何账号。

生成内容（按当前学校建立动作集合，均可随后修改）：

| 模板 | 动作集合（建议） |
| --- | --- |
| 机构管理员 | 全部 49 项 |
| 教务 | 组织查看、员工/教师/教室查看、学员查看与维护、课程查看、班级课次查看与维护、考勤登记、关课、审批查看 |
| 课程顾问 | 组织查看、学员查看、渠道查看与维护、本人客户查看与录入、完整电话、报名查看与维护、收款查看与登记 |
| 财务 | 组织查看、学员查看、报名查看、收款查看/登记/分配、退款查看/申请/付款、审批查看与决定、期间查看/锁月/解锁 |
| 前台 | 组织查看、学员查看、课程查看、报名查看与维护、收款查看与登记 |
| 只读 | 各业务域的 `_READ` |

约束：

- 生成前检查代码冲突，已存在同代码模板时跳过并提示，不覆盖。
- 生成动作不包含 `AUTHORIZATION_MANAGE`，避免新增账号意外获得管理能力；机构管理员模板由管理员在生成后自行勾选。
- 模板动作受目录约束，`ENROLLMENT_DISCOUNT`、`PERIOD_UNLOCK` 必须在补目录之后才可出现。
- 生成是一次性动作，不做“模板版本升级自动同步到已有角色”。

## 6. 数据范围与新建学校

### 6.1 现状语义与误解点

`identity.account_permission.school_id = NULL` 表示“功能级规则”：功能打开但不产生任何学校范围。界面文案“仅功能级（不含学校范围）”与旧系统“允许查看所有数据”含义相反，业务人员极易配成“有菜单、无数据”。

### 6.2 建议：范围三选一

| 选项 | 语义 | 存储（首期） |
| --- | --- | --- |
| 本机构全部学校（含新建） | 功能开启且覆盖当前与将来的全部学校 | 首期用应用层自动铺开，不改表结构（见 6.3） |
| 指定学校 | 仅勾选学校 | 现有 `school_id` 行 |
| 不授予数据范围 | 仅功能开关，不产生范围 | 现有 `school_id = NULL` |

界面必须在选项上写清后果，并在选择后即时显示“当前将覆盖 N 所学校”。

### 6.3 新建学校的授权铺开

现状：`SchoolProvisioner.provision` 只为**创建者**补 9 个动作（授权管理、组织、员工、教师、教室），其他账号一概不补，且学员、报名、收款、教务等动作不在其中。演示库中 `PERSONNEL_READ` 只覆盖 3 所、其他动作覆盖 4 所，就是这一规则的直接结果。

三个候选：

| 方案 | 做法 | 评价 |
| --- | --- | --- |
| A 维持现状 | 只补创建者 9 项 | 建完学校后学员/收款/教务全部进不去，不适合试点 |
| B 应用层自动铺开（建议） | 新建学校时，对“范围为全部学校”的账号按动作集合补齐；同时明确写审计 | 不改表结构，可先落地；需要定义“全部学校”的判定 |
| C 按角色自动铺开 | 新建学校时按角色模板为所有已分配该角色的账号补该校 | 语义最贴近业务，但牵扯模板版本与影响范围，建议后置 |

首期建议 B：判定条件取现有 `tenantAdmin` 或“该动作已有全部现有学校 ALLOW 且无 DENY”的账号。注意这会让部分管理员在新建学校后自动变成“覆盖全部学校”，必须同时在最后管理员检查里保持“检查发生在铺开之后”，避免出现瞬时无全量管理员。

### 6.4 与 `tenantAdmin` 的关系

`tenantAdmin` 由平台开通时写入，当前在 `PermissionRules` 中使组织查看/维护/授权管理/品牌直接通过，但学校范围仍由显式授权决定。这一点需要在页面明确展示（“租户管理员”标签 + 说明“仍需学校授权”），否则会出现“我是管理员但看不到学校”的困惑。

### 6.5 存量规则归一

演示库的 143 条直接规则建议一次性归并为“角色 + 少量例外”，但**不在产品迁移中做**：只作为本地演示种子的新步骤（见 7.3），保证产品库行为不变。

### 7.1 演示账号

账号只在**带项目标记的本地合成库**创建，密码写入 `.local/dev/accounts.txt`，不进文档与代码。

### 7.2 预期权限卡

为每个账号写一页“该看到什么、该被拒绝什么”，用表格固定下来（菜单、页面、按钮三列）。验收时按卡核对，不靠口头描述。建议放在本文附录或单独的验收样例文档，随实现更新。

### 7.3 演示数据改造

新增本地种子步骤（如 `LOCAL-PERM-DEMO-001`），在既有 `LOCAL-*` 步骤之后执行，幂等且不覆盖手工调整：

1. 生成 6 个起始角色模板。
2. 创建 4 个演示账号并分配角色。
3. 将 `local-admin` 的直接规则替换为“机构管理员角色 + 2 条 DENY 例外”。
4. 保留 `local-reader` 现状。

风险与回滚：该步骤会改写演示账号授权，执行前置备份；失败即回滚事务；回滚方式为恢复升级前备份，不支持把旧规则与新角色混在一起长期并行。

### 7.4 自检工具

`tools/dev` 增加只读自检：用各演示账号登录，读取 `/api/session/permissions` 与各页面 capabilities，与 `tools/dev/permission_expectations.json` 逐项比较，输出差异清单。只读、不修改数据，可在每次权限相关改动后运行。

### 7.5 权限变更记录

`audit.authorization_event`、`audit.role_template_event` 已有数据，但普通业务连接只允许追加、不允许查询。要展示“最近权限变更”，需要新增受控读取（窄视图或专用函数）。此项涉及授权面变更，排在后面，不与首期一起做。
