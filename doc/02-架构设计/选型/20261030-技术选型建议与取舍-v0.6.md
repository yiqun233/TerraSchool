## 1. 本轮已确认条件

- 技术由 AI 先推荐最合适的选项、解释理由，用户选择；不要求用户先指定语言和框架。
- 主要由 AI 开发，用户负责验收，也会阅读和修改。中文注释、清晰命名、容易定位的业务代码是明确要求。
- 生产以产品方公有云 SaaS 为主，客户本地版部署在客户提供的 Linux 服务器；暂不扩大操作系统兼容。
- 客户服务器的资源规格没有在本轮确定，不能解释为普通办公电脑或承诺任意低配置可运行。
- AI 产品功能后置，业务底座现在预留；本轮不选择模型和 Agent 框架。

下文推荐是结合本项目需求的工程判断，官方资料用于验证技术能力与兼容性，不构成对本项目性能或开发效率的证明。

## 3. 为什么首选 Java 路线

本项目长期复杂度集中在结算、退费、资金分配、状态流转、细粒度授权和排课，不只是页面 CRUD。我的判断是：明确类型、可检查依赖、可测试的领域规则与成熟事务设施，对这些复杂度有较高价值。

Java 自带 BigDecimal，可统一精度与舍入，但语言和框架不会自动保证金额正确；必须封装金额/课时规则，避免散落计算和隐式转换。数据库使用精确类型，前端和接口的金额表示也需独立规定。[BigDecimal 官方说明](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/BigDecimal.html)、[PostgreSQL 精确数值](https://www.postgresql.org/docs/18/datatype-numeric.html)。

Java 25 被列为 LTS；Spring Boot 当前官方文档列出的 4.1.x 版本可运行在 Java 25 上。当前数据访问已选 jOOQ + Flyway。此前 MyBatis 兼容分析仅作为备选记录，不再表示主方案；完整 jOOQ/Flyway 依赖组合仍需验证。[Java 支持路线](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)、[Spring Boot 系统要求](https://docs.spring.io/spring-boot/system-requirements.html)、[MyBatis 兼容表](https://mybatis.org/spring-boot-starter/mybatis-spring-boot-autoconfigure/)。

代价是后端与前端两种语言、DTO 和映射代码较多，框架隐式机制也需要理解。应控制抽象：不引入大继承树、万能基础 Service、隐藏业务规则的注解链，也不为每个简单操作套完整领域设计。中文注释重点解释不变量与执行边界。

这不是恢复上一轮代码。重新评估后部分技术可能相同，但业务入口、授权边界、模块契约和可靠执行规范将按新的设计建立。

## 4. 备选 B：TypeScript + NestJS

| 方面 | 价值或代价 |
| --- | --- |
| 语言统一 | 前后端均可使用 TypeScript，阅读和类型/工具复用更集中 |
| 工程约束 | NestJS 提供模块、依赖注入、校验和守卫等组织能力，可实现同样的业务边界 |
| 精确计算 | 统一采用精确小数库或整数最小单位；运行时不能依靠普通 number 随意计算金额 |
| 运行时契约 | 静态类型不能替代外部输入校验，需统一 schema 与验证策略 |
| 排课计算 | CPU 密集任务应使用 worker 或独立进程，避免长计算阻塞请求处理；Java 路线也建议任务隔离 |
| 事务与 ORM | 事务、连接上下文、数据映射、隔离与迁移方案需选择一致组合，不拼装多套风格 |

这条路线可以正确实现本项目，不因使用 JavaScript 生态就判定无法处理财务。若用户高度重视单一语言与代码紧凑，可选择 B；我目前把资金履约与长期规则维护放在更高权重，因此优先 A。[NestJS 官方文档](https://docs.nestjs.com/)、[Node worker 官方说明](https://nodejs.org/api/worker_threads.html)。

C#/.NET 也是合理候选；目前没有必须使用该生态或既有组件的约束，先不扩大到第三套详细方案。Python 可用于未来特定 AI 或数据任务，当前不建议仅因未来要接 AI 就将其选为核心交易后端。

## 5. PostgreSQL 与前端的取舍

PostgreSQL 的 numeric 与 RLS 都有官方能力基础。标准 SaaS 共享库/表、tenant_id 与 RLS 已在 DEC-006 确认，应用授权与数据库隔离双重保护；客户本地版使用同代码独立部署，保留专属部署选项。当前没有单客户独立恢复或独占资源要求；运行角色配置、事务绑定实现及恢复演练继续细化。RLS 不能代替同租户内的功能/数据权限，表 owner、超级用户和 BYPASSRLS 的行为需验证。[RLS 官方说明](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)。

MySQL 可以作为业务库，但目前没有使它优于 PostgreSQL 的明确项目约束；旧系统 SQL Server 的存在也不要求新系统继续采用它。迁移复杂度主要来自业务语义和历史单位，而非目标数据库品牌本身。

前端已选择 React + TypeScript。原先 Vue/Element Plus 首选建议经过 AI 接入讨论后调整；Vue 仍是具备正常业务与 AI 接入能力的备选，不代表能力不足。

考虑未来可能增加方案确认、工具结果、材料证据和多步骤操作展示，React 可以直接评估 AI SDK 及 AI Elements 等组件生态；AI SDK UI 本身也支持 Vue。这是生态复用的选择因素，不是框架性能或模型效果的证明。[AI SDK UI](https://ai-sdk.dev/docs/ai-sdk-ui/overview)、[AI Elements](https://elements.ai-sdk.dev/docs)。

用户进一步确认初期 AI 是辅助助手，后期不排除成为主入口。当前交付正常管理页面，AI 功能以后开发；不为了未来主入口提前重做全部交互。组件库、构建工具及 AI 界面库仍待选择。

## 6. AI 开发与人工阅读的代码约束

中文注释是已确认开发要求，具体规则已同步工程规范和协作规则：公开业务操作写清用途、输入单位与含义、前置条件、失败和副作用；关键算法、资金规则、权限、幂等和并发段解释原因、边界及证据来源。

注释不逐行翻译语法，不靠注释补救复杂命名和超大方法，不写“临时如此”却没有关联问题，不记录秘密。行为变化同步更新注释和测试；测试是可执行证明，注释帮助理解设计。
