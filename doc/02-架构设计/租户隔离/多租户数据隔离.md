## 1. 确认范围与业务边界

DEC-006 已确认：标准 SaaS 共享数据库与业务表，tenant_id 明确业务数据归属，应用授权和 PostgreSQL 行级安全策略（RLS）双层执行。客户本地版使用同代码/结构独立部署，保留租户归属约定；有明确要求的 SaaS 客户可另行评估专属部署。

用户确认目前没有单客户独立时间点恢复或独占数据库资源要求。此结论不取消常规备份、故障恢复和恢复演练，也不构成具体恢复 SLA 承诺。

租户代表机构/品牌。学校承担财务与合同归属，校区承担教学地点，部门承担归属与审批；校区与部门是学校下平行分支。机构内组织权限不能由租户隔离自动替代，不改变现有业务基线。

当前仅设计文档，不创建数据库、角色、代码、AI 服务或部署平台。

## 2. 备选与取舍

| 方案 | 优势 | 代价与使用位置 |
| --- | --- | --- |
| 共享库/业务表 | 一份结构演进与较低运维成本 | 默认；必须严格隔离，单客户恢复更复杂，资源共享 |
| 每租户 schema | 表命名空间分离 | 不默认采用；结构迁移份数增加，仍共享实例和物理恢复边界 |
| 每租户数据库 | 逻辑备份和客户数据管理更独立 | 按需评估；连接、迁移与监控成本增加，同实例仍共享资源 |
| 专属实例/独立部署 | 资源与物理恢复边界更独立 | 强隔离客户或客户本地版按环境设计，不承诺任意硬件配置 |

保留专属部署选项不等于立即建设动态分库平台。数据归属和结构基线保持一致，真正拆分时再设计冻结、依赖闭包、附件迁移、校验、切换和失败回退。

## 3. 数据结构与关系

- 租户业务表明确记录 tenant_id，原则上非空；平台公共数据单独分类，禁止以随意空租户值绕过隔离。
- 业务编号按实际唯一性范围设计租户联合约束；引用租户业务对象时用联合外键等数据库约束防止跨租户关联。具体主键与联合唯一约束形式在数据设计时确定。
- 索引结合 tenant_id、业务过滤和排序实际设计，不机械要求所有索引相同；权限过滤先于分页和聚合。
- 原始 SQL、导入、批处理、统计投影和视图均审查隔离路径，不因未使用普通页面入口而例外。
- 一次业务事务只处理一个租户；平台跨租户需求用专门授权入口和明确处理协议，不能在普通事务中随意切换。

## 4. 应用授权与 RLS

可信入口根据已认证身份和有效授权建立租户上下文，普通请求或模型传入的租户标识只可作为待验证选择，不能直接成为权限依据。租户缺失、无效、停用及主体无权时拒绝。学校/校区/部门、功能与敏感字段继续由应用授权检查。

租户业务表启用并强制 RLS；分别验证可见行与允许插入/修改的数据，不能只过滤 SELECT。普通运行账号不是表所有者、超级用户，也不具备 BYPASSRLS；迁移账号单独管理且不用于普通业务。TRUNCATE 等不受 RLS 约束的操作不授予普通运行账号。

RLS 是漏过滤等错误的纵深保护，不代替业务授权，也不是对完全失陷应用或任意 SQL 执行的安全保证。禁止向 AI 开放数据库凭据、任意 SQL、租户设置或任意数据源选择。

官方依据：[行级安全与绕过角色](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)。引用版本用于能力说明，不自动锁定项目 PostgreSQL 版本。

## 5. 事务、连接池与任务

查询和写入均通过统一数据访问入口，在实际事务连接上绑定已校验租户。采用事务局部配置，结束后恢复；不使用会残留至下次借用连接的普通会话设置承载租户，也不只设置 Java ThreadLocal。

绑定必须早于业务 SQL，并对缺失/非法上下文拒绝；事务传播、独立事务、回滚及连接归还路径均需验证。不能在一条连接上设置租户后，从另一条未绑定连接查询。跨线程与任务显式携带租户和主体引用，执行时重新验证租户状态及当前权限，用后清理。

任务以最小权限执行，系统任务也需明确作用范围，不能默认拥有全租户绕过权限。外部模型、排课长计算和人工等待不占用长事务。

官方依据：[SET LOCAL 仅在当前事务生效，事务外无效](https://www.postgresql.org/docs/18/sql-set.html)。具体绑定 API 与连接池配置在工程验证时确定。

## 6. 非数据库资源与未来 AI

文件和导出记录归属租户，下载时重新鉴权；对象路径不代替权限控制。缓存键区分租户和必要权限版本，不能通过旧缓存绕过撤权。任务、事件、审计、查询投影和重试结果均保留租户归属及授权边界。

未来检索在选取候选材料时限制租户和资源权限，不能先交给模型再过滤答案。内置助手和外部 Agent 使用同一业务执行上下文，权限取员工、管理员客户端限制与委托范围的交集。更换云端/内网模型不改变隔离方式，当前不建设 AI 检索或委托产品。

## 7. 备份、恢复与专属部署

共享库必须具备整体备份和故障恢复。单客户恢复需另行制定流程：在隔离环境恢复历史副本，提取该客户依赖闭包，检查金额、课时、关系、附件及后续有效业务，再受控导入并对账；不能直接回滚共享线上库影响其他客户。

PostgreSQL 原生基于 WAL 的时间点物理恢复以整个数据库集群为单位，同实例每租户一个数据库或 schema 不自动提供独立物理恢复。逻辑备份与物理恢复是不同机制；专属实例也不替代备份和恢复演练。文件与业务库的一致恢复需单独设计。

官方依据：[连续归档与时间点恢复范围](https://www.postgresql.org/docs/18/continuous-archiving.html)。具体恢复工具、保留周期、RPO/RTO 和合同边界继续设计，不能以当前未要求独立恢复为理由省略恢复能力。

## 8. 实现验收与未决项

至少用真实 PostgreSQL 和两个租户验证以下场景，不以管理员连接或 mock 结果代替：

| 场景 | 预期 |
| --- | --- |
| 甲租户查询、更新、删除乙租户对象，或插入乙租户数据 | 不泄露数据、不修改成功；错误信息不暴露乙方敏感信息 |
| 跨租户外键关联、批量导入、关联选项、统计、导出 | 无非法关联或数据泄露，应用授权与数据库约束均有效 |
| 缺少/非法租户、停用账号/租户、撤权后任务重试 | 拒绝相应访问，不通过缓存或历史结果绕过 |
| 同一连接先服务甲方，再服务乙方或无上下文请求；提交/回滚/异常 | 不残留甲方上下文，缺失时拒绝 |
| 同租户不同学校/校区/部门及敏感字段 | RLS 不替代细粒度权限，按当前授权返回 |
| 文件下载、导出结果、缓存及异步任务 | 均验证当前租户与资源权限 |
| 普通运行角色执行请求，迁移角色执行结构升级 | 权限分离，普通角色不能绕过 RLS 或执行高权限表操作 |
| 故障恢复与租户数据提取演练 | 数量、关系、资金、课时和附件一致，其他客户不被回滚 |

未决：具体角色/策略 SQL、事务绑定实现、资源配额、备份恢复工具与 SLA、专属部署切换流程、身份会话与租户内权限实现。本次确认不等于这些实现已经完成。

R3-CORE-001 已在普通非 owner/非 BYPASSRLS 角色下验证强制 RLS、缺租户读写拒绝、跨租户读写、事务局部绑定、回滚/单连接池复用及同事务审计，详见[验证记录](../../03-研发规范/工程质量/验证记录/20261031-核心技术组合验证记录.md)。测试表/角色不是正式结构；字段/学校范围、撤权、文件/任务、恢复及全量并发仍未覆盖，不将最小原型当作完整隔离实现。
