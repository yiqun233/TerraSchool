## 1. 已确认范围

用户确认客户内网 Linux 服务器允许安装 Docker Engine 和 Docker Compose，优先采用容器部署。在比较维护窗口、应用双版本切换与完整高可用后，用户选择“初期采用A，之后使用B”。

- SaaS 初期采用 A：计划维护窗口发布；后续演进到 B：应用双版本切换，减少常规升级对使用的影响。
- 客户单台 Linux 版优先采用 Docker Engine + Compose 容器交付，默认维护窗口升级。SaaS 演进到 B 不自动要求所有客户单机版同时双版本运行。
- 现在设计多实例可运行、任务可恢复和版本兼容边界，正式实现随工程和对应业务切片落实，不在当前创建运行服务。
- 未确认 C 完整高可用、所有升级无感、具体服务器数量、SaaS 单机或分机拓扑、发行版/CPU 架构、版本、资源规格及 B 的启用条件。

本条确认时未批准全部入口或配置建议；标准入口随后由 DEC-016 确认 Nginx 开源版。配置与密钥随后由 DEC-017 确认外部 YAML/结构化校验和受限文件注入；独立密钥服务与自动部署仍未选定；备份工具随后由 DEC-018 确认方向，实际版本和配置待验证。文件存储仍以 DEC-010 为准，SaaS 必须支持自建开源对象存储，不能因公有云部署而改为只支持云托管存储。

## 2. 方案与取舍

| 方案 | 做法 | 发布影响与边界 | 当前结论 |
| --- | --- | --- | --- |
| A 维护窗口发布 | 暂停受影响业务，控制请求与任务，升级并验证后恢复 | 简化新旧应用共存；有明确维护窗口，时长取决于迁移、数据量与检查 | 初期采用；客户单机版默认升级方式 |
| B 应用双版本切换 | 先启动和验证新版，再切换流量并退出旧版 | 常规兼容升级减少中断；新旧程序短时共用数据库/对象，特殊迁移仍可能维护 | SaaS 后续演进方向，当前预留兼容能力 |
| C 完整高可用 | 冗余入口/应用及数据库、存储故障处理 | 面向节点故障，需要相应检测、切换与恢复演练；依赖实际拓扑与运维能力 | 未批准为首期必须建设项 |

A 的优势是交付和排障路径清楚，代价是发布影响所有受维护范围内的用户。B 增加版本兼容、流量切换、退出和回退验证成本；同一台机器上的两个应用容器仍可能同时受整机故障影响。B 的发布改进不等于数据库或对象存储已经高可用。

Docker Compose 可用于单服务器部署，但不会因为采用容器就自动获得冗余和故障切换。初期不以建设 Kubernetes 或整套高可用集群作为正式工程前提；未来其他拓扑另按需求验证。

## 3. 初期 A 的目标发布协议

| 阶段 | 需要验证的行为 |
| --- | --- |
| 发布准备 | 明确版本清单、变更和结构兼容范围，检查环境与资源、可恢复备份及失败处置 |
| 进入维护 | 对受影响范围建立实际写入/任务控制；覆盖 HTTP、定时任务和后台入口，不能仅在网页展示维护提示 |
| 处理在途操作 | 停止领取新任务，等待可完成操作或按既有恢复协议交接；请求/任务超时和停止边界明确，不以杀进程宣称事务或外部副作用已回滚 |
| 结构与程序升级 | 受控执行 Flyway 迁移并切换固定版本程序，使用独立升级权限；不让每个普通应用实例自行取得迁移账号权限 |
| 验证与恢复服务 | 检查运行就绪和必要业务结果，再开放写入与任务，记录实际版本、迁移和检查结果 |
| 失败处理 | 保留维护状态，按兼容范围切回程序或执行经验证的恢复/补偿；说明受影响数据与任务，不能自动假设旧镜像一定可用 |

维护窗口的控制方式、读请求是否保留、通知与排期规则、检查命令、超时及恢复手册在实现前细化，不在本轮指定固定停机分钟数。

业务持久数据不依赖容器可写层；更新程序与删除数据有明确边界。容器、卷、主机路径和备份位置在部署配置中显式管理，不将重新创建容器作为清空或重置数据库的授权。

## 4. 现在设计、后续实现的 B 支持能力

### 4.1 应用与会话

关键业务状态、任务、幂等结果和确认凭证由业务系统持久管理，不以单个应用进程内存为唯一事实。沿用服务端会话与 Spring Session JDBC/PostgreSQL 的决定；跨版本会话字段、序列化与撤权行为仍需实际验证，不能仅凭共享会话表承诺升级不掉登录。

应用具有可区分的就绪、停止接流量和退出阶段，暴露内容和权限受控；健康检查不代替业务验证。旧应用退出前停止接收新请求并处理在途请求，具体代理和运行环境配置后验。

### 4.2 任务与事件

任务参数和事件负载按已确认方案版本化。新旧处理器共存期间明确可处理版本、领取与执行凭证，旧执行者不能覆盖新结果；停止旧 worker 的新任务领取，在途任务完成或按恢复协议接管。不能假设 Web 请求退出就代表后台任务已经停止。

任务、排课草稿和未来 AI 长任务的业务进度/结果可恢复，外部模型或人工等待不占用数据库长事务。B 不改变关键资金履约的强事务、幂等和权限要求，也不自动启动 AI 产品开发。

### 4.3 数据结构与客户端兼容

新旧应用共用同一权威业务数据库和对象存储，结构变更需要明确共存窗口。优先采用先扩展兼容结构、再切换程序、最后清理旧结构的顺序；无法兼容的迁移继续使用维护窗口，不承诺全部升级零中断。

Flyway 迁移仍是结构权威，发布只安排受控升级入口；jOOQ 生成在构建侧完成，客户端服务器启动不承担代码生成。接口、旧浏览器页面、生成客户端、任务和会话的兼容范围需要共同验证，不只验证新页面配新后端。

前端静态资源、后端、任务处理器和迁移有可追踪版本关系；具体打包、路由切换、资源保留和发布清单格式继续设计，不通过长期运行两套权威数据库实现应用切换。

### 4.4 回退边界

程序回退以当前结构与旧程序兼容为条件，数据结构不兼容时不能只换旧镜像。数据库恢复可能影响升级后的写入，标准 SaaS 的共享库恢复还会影响其他机构，须明确维护范围、数据损失边界和授权，不把恢复共享库设为普通发布失败的自动动作。

## 5. B 的启用与验证

后续需要减少常规发布影响时，在既有设计基础上细化并验证流量切换、资源余量、兼容范围和失败处置，再启用 B。启用条件尚未确定，不维护时间或人员估算，不将多实例可运行等同于已经部署高可用。

验证包括旧/新应用共存、就绪判定、切换与在途请求、普通角色/RLS 与连接池、会话兼容、旧页面访问、任务重领/撤权/幂等、版本回退和不兼容迁移拒绝。实际机器或数据库故障测试按另行确定的拓扑实施。

客户单机版是否启用双版本切换取决于硬件余量和客户运维需求，未随 SaaS 后续方向自动锁定。

## 6. 配置、恢复与交付的未决边界

基础要求沿用根规范：秘密不进入仓库或日志；运行与迁移权限分离；客户内网运行不依赖 GitLab 或公网；备份恢复覆盖数据库、对象及必要存储元数据和密钥恢复条件。

入口已在 DEC-016 确认，详见[入口与 HTTPS 方案](20261030-入口与HTTPS方案-v1.1.md)；具体证书/代理配置仍需验证。环境配置与密钥首期方案已在 DEC-017 确认，保存/分发/注入及更换的具体实现继续验证，见[配置与密钥管理](20261030-配置与密钥管理-v1.1.md)；备份方向已在 DEC-018 确认，见[备份与恢复方案](../备份恢复/20261030-备份与恢复方案-v1.1.md)；离线镜像和依赖、具体备份与恢复协议继续细化。Compose 文件注入已另在 DEC-017 确认；SOPS/OpenBao 等仍为备选，不自动引入独立平台。

具体发行版、CPU 架构、Docker/Compose 和组件版本、镜像来源、节点/磁盘布局、备份副本及保留、RPO/RTO、日志观测和生产发布授权配置仍需验证。已有 99.9% 月可用性、RTO 4 小时、RPO 15 分钟保留为工作假设，不能因本条决策转为已兑现承诺。

当前仅文档整理，未创建代码/容器、安装依赖、配置服务器、注册 Runner 或执行部署/恢复测试。Git 提交与推送仍按每次任务授权处理。
