## 为什么单独做"期初余额"

旧库迁到新系统时，学员的历史余额不能靠"造一堆收款"来凑——那样会污染实收、也分不清哪笔是历史。因此新增一种**独立的账户分录**：

| 项 | 做法 |
| --- | --- |
| 分录类型 | `funds.account_entry.kind = 'OPENING'`（与收款、分配、释放、退费并列） |
| 契约 | `POST /api/funds/openings`；请求含学校、学员、金额、期初日期、原因 |
| 账务影响 | 只改账户余额；**不建收款、不参与分配来源**，因此不影响"未收金额" |
| 负数 | 允许（旧库余额可能为负，代表欠费），直接减少可用余额 |
| 幂等 | `requestId` + 指纹；重复提交返回当前余额 |
| 期间 | 按期初日期受锁月约束（月已锁则拒绝） |
| 审计 | `OPENING_POSTED`，记录金额与原因 |

## 与"用收款补齐"的差别

| | 期初分录（本实现） | 用收款补齐 |
| --- | --- | --- |
| 实收统计 | 不变 | 会被算进实收 |
| 余额可重算 | 只有一条分录，来源清晰 | 由多笔收款与消费推出来 |
| 对账 | 用"期初分录合计"单独核对 | 与其他收款混在一起 |
| 历史收支明细 | 不迁 | 迁 |

两种都能让余额对上；选择取决于"历史收支要不要在新系统里逐笔可查"——这在[候选表](../旧库迁移/迁移口径候选表.md)里是 C2。

## 期初课时（同批补齐）

金额之外，旧库还有"已消耗课时/已消耗金额"。它们没有对应课次，但如果不管，新系统的"可退课时"和"剩余课时"都会比实际多。

| 项 | 做法 |
| --- | --- |
| 载体 | 复用 `teaching.consumption`：允许 `lesson_id` 为空，新增 `source`（`LESSON` / `OPENING`） |
| 唯一性 | 课次消费仍是"一条课次一条"（部分唯一索引）；**同一报名只允许一条 OPENING** |
| 影响 | 现有"可退课时 = 购买 − 已消耗 − 已退"与"剩余课时"都从消费汇总，因此期初会自动被算进去 |
| 金额 | 允许 0（旧库可能只有课时没有金额），不接受负数 |
| 上限 | 期初消耗 + 已有消费不得超过购买课时 |
| 契约 | `POST /api/teaching/enrollments/{id}/opening-consumption` |
| 审计 | `OPENING_CONSUMPTION_POSTED` |

注意点：课时对账查询必须用**左连接**课次，否则 `lesson_id` 为空的期初消费会被过滤掉——这个坑在实现时被测试抓到过一次。

## 已知边界

- 期初课时按"已消耗"带入，不按"剩余"带入：若旧库只有剩余课时，需要先算出已消耗（购买 − 已退 − 剩余）再调用；
- 没有"期初批次"概念（一次迁移一个 requestId，逐学员调用）；
- 负余额没有单独的欠费台账，只是账户负值。
