## 为什么单独做"期初余额"

旧库迁到新系统时，学员的历史余额不能靠"造一堆收款"来凑——那样会污染实收、也分不清哪笔是历史。因此新增一种**独立的账户分录**：

| 项 | 做法 |
| --- | --- |
| 分录类型 | `funds.account_entry.kind = 'OPENING'`（与收款、分配、释放、退费并列） |
| 契约 | `POST /api/funds/openings`；请求含学校、学员、金额、期初日期、原因 |
| 账务影响 | 只改账户余额；**不建收款、不参与分配来源**，因此不影响"未收金额" |
| 负数 | 允许（旧库余额可能为负，代表欠费），直接减少可用余额 |
| 幂等 | `requestId` + 指纹；重复提交返回当前余额 |
| 期间 | 按期初日期受锁月约束（月已锁则拒绝） |
| 审计 | `OPENING_POSTED`，记录金额与原因 |

## 与"用收款补齐"的差别

| | 期初分录（本实现） | 用收款补齐 |
| --- | --- | --- |
| 实收统计 | 不变 | 会被算进实收 |
| 余额可重算 | 只有一条分录，来源清晰 | 由多笔收款与消费推出来 |
| 对账 | 用"期初分录合计"单独核对 | 与其他收款混在一起 |
| 历史收支明细 | 不迁 | 迁 |

两种都能让余额对上；选择取决于"历史收支要不要在新系统里逐笔可查"——这在[候选表](../旧库迁移/20261102-迁移口径候选表-v0.1.md)里是 C2。

## 已知边界

- 期初分录不区分"课时余额"与"金额余额"：旧库的课时结余目前仍要靠 `/api/teaching/enrollments/{id}/reconciliation` 对，未建期初课时；
- 没有"期初批次"概念（一次迁移一个 requestId，逐学员调用）；
- 负余额没有单独的欠费台账，只是账户负值。
