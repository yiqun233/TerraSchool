## 来自旧系统的依据

旧系统把冲突集中定义在 `ClashTypeDictionary`（15–23 种原因），其中与"能不能排"直接相关的有：

| 旧原因 | 新系统码 | 默认级别 |
| --- | --- | --- |
| 教师课程冲突 | `TEACHER_CLASH` | 阻断 |
| 教室课程冲突 | `ROOM_CLASH` | 阻断 |
| 本班已有课次占用该时段 | `LESSON_OVERLAP` | 阻断 |
| 教师参加活动 / 教师休假 | `TEACHER_UNAVAILABLE` | 阻断（可降级） |
| 教室预订 | `ROOM_UNAVAILABLE` | 阻断（可降级） |
| 教师最小课间（`MinSpaceMinute`） | `TEACHER_MIN_GAP` | 阻断 |
| 重复时段 | `DUPLICATE` | 阻断 |

旧系统另有 `isIgnoreTeacherSchoolClashForSearchCanUseCSItem`、`isIgnoreHoliday`、`isIgnoreActivity` 等开关——说明这些**本来就可配置**，不是绝对硬约束。新系统据此把"是否阻断"做成学校级策略，而不是写死在代码里。

## 本切片做了什么

| 项 | 内容 |
| --- | --- |
| V23 | `teaching.resource_block`（教师活动/休假、教室预订；二选一资源 + 日期 + 时段 + 原因）；`teaching.schedule_policy`（最小间隔、两个"是否阻断"开关） |
| 冲突分级 | 预览每行返回 `reason` + `severity`（`HARD` 阻断 / `WARN` 仅提示）；`available` 只对 HARD 为 false |
| 策略 | 未配置时默认：两个不可用都阻断、最小间隔 0（关闭） |
| 确认 | 只跳过 HARD，WARN 仍会生成课次（与"警告但仍排"的旧行为一致） |
| 契约 | `POST /api/teaching/resource-blocks`、`GET /api/teaching/resource-blocks`、`GET/POST /api/teaching/schedule-policy` |
| 前端 | 预览表新增"可排（有警告）"状态与中文原因（教师不可用、教室被预订、间隔不足） |

## 为什么这么定

用户没有给"绝对答案"，所以我按旧系统可考证的语义取默认值，并把判断留给配置：

1. **默认阻断**：旧系统在保存时对课程/资源冲突是阻断的（冲突只会清空教师或教室，不会无声保存），因此默认按阻断；
2. **可降级**：旧系统已有 ignore 开关，因此提供 `blockTeacherUnavailable` / `blockRoomUnavailable` 两个开关，关掉即只警告；
3. **不做的**：距离冲突、座位数、教室生命周期、其他系统占用、学员休假与会话冲突、深度交换搜索——这些要么需要地图/座位/外部系统数据，要么需要教务先给"警告还是阻断"的口径，本轮不猜。

## 维护界面

教学页新增「排课设置」，两个页签：

| 页签 | 内容 |
| --- | --- |
| 不可用时间 | 选择资源类型（教师/教室）与具体资源、日期与时段、原因后新增；下方列出该校期间的不可用时间 |
| 排课策略 | 两个开关（阻断 / 仅警告）与最小间隔分钟数，保存时带版本，冲突提示刷新 |

只读账号可以查看但不能提交（按钮隐藏）。不可用时间支持**撤销**：行内「撤销」按钮带二次确认（显示日期与时段），撤销后服务端返回 204；重复撤销按成功处理，避免因网络重试报错。

## 已知边界

- 只有"教师/教室"两类资源阻塞，没有"学员休假""班级休息日""跨校距离"；
- 最小间隔只作用于教师，未做教室的周转间隔；
- 没有"排不下时交换已有课次"的搜索（旧系统有深度 1–5 的交换）；
- 阻塞与策略只有接口，前端还没有维护界面（排课弹窗里能看到警告，但新增阻塞要走接口）。

## 契约

`ScheduleSlot` 增加 `severity`；`ScheduleRule` 与预览/确认不变。

新增错误码：`RESOURCE_REQUIRED`、`SCHEDULE_GAP_INVALID`。
