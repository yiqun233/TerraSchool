## 1. 已确认组合与实施边界

用户接受结构化运行日志、PostgreSQL 业务审计、Actuator/Micrometer 指标、SaaS Prometheus/Grafana/Alertmanager 及客户单机按需监控包的分层方案。底座先具备记录、关联和必要指标能力，集中日志与完整调用链平台按需增强。

| 职责 | 当前选择 | 实施范围 |
| --- | --- | --- |
| 运行日志 | SLF4j + Logback，JSON 结构化输出 | 本地/容器日志有轮转、容量与清理，基础排障可用 |
| 业务审计 | PostgreSQL 专用记录 | 应用动作生成，关键成功修改与审计同事务，租户与字段授权 |
| 监控指标 | Spring Boot Actuator + Micrometer | 基础资源/请求与必要任务、事件、备份指标，受限接口 |
| SaaS 指标与告警 | Prometheus + Grafana + Alertmanager | 指标采集/规则、运维看板、告警分组/去重/路由与维护静默 |
| 关联与未来追踪 | 统一追踪标识，预留 OpenTelemetry 接入 | 按选定 Boot 版本验证追踪集成；不立即建设完整采集/存储平台 |
| 客户单机 | 轻量日志、审计与指标接口，监控包按需 | 内网运行，不要求每套客户默认部署全部组件 |

Loki + Alloy 为后续集中日志增强选项，完整追踪后端及采集平台未设为初期必需依赖。不自动引入云监控服务、收费功能或 AI 运维助手。具体工具稳定版本/许可、资源、字段/schema、保留、阈值与通知渠道继续验证，当前不安装或部署。

## 2. 运行日志、审计、指标与追踪分别负责

运行日志解释错误和性能，审计记录业务责任，指标观察趋势与异常，追踪关联一次调用路径。财务流水和权威余额继续归业务领域，不能由审计或监控推算成另一份权威事实。

追踪可按需求采样，关键业务审计不能依赖采样追踪保存。持久操作/任务标识与单次请求的追踪标识区分：持续多天的任务或 Agent 流程可关联多次请求和执行尝试，不要求一条长生命周期 trace 包揽全部历史。

关联字段由可信调用上下文提供，来源、租户、主体和委托不接受模型或普通请求任意自报。外部追踪头可以按协议关联诊断，但不能授予权限或建立租户身份；线程/任务传播和清理按已有身份隔离规范验证。

## 3. 业务审计在应用操作生成

页面、后台任务和未来 AI/外部 Agent 复用应用服务，审计在该层围绕业务动作生成。记录重点是租户、可信主体、来源、动作、对象、结果、必要原因与变更摘要，以及操作/请求/任务/确认等关联信息。字段级前后值按业务用途、访问权限与脱敏策略确定，不默认保存完整实体或请求。

关键修改、审计记录和必要可靠事件在明确本地事务边界内一致提交。关键操作若必需成功审计不能写入，应失败或回滚，不能业务已成功却只依赖内存异步回调补记录；远端日志采集不可用不应因此让全部业务停摆。

失败、拒绝与安全尝试使用独立受控记录路径，避免随失败业务事务回滚消失。该路径同样明确持久性、容量、失败告警与敏感信息边界，不无条件同步写入每次低风险查询，也不通过无限重试拖住请求。

审计查询由业务权限体系检查租户、功能、数据范围和字段；适用租户记录执行 RLS，平台级运维/安全事件另按独立权限访问。普通账号不得任意更新/删除审计记录；清理有独立权限和保留规则，不随业务对象删除简单级联清空。

以退款为例，需要关联申请主体、确认、执行动作及真实结果，而不是只记录一次 HTTP 200。具体动作目录、字段、审计失败分类和事务实现随业务切片设计，不在本轮创建审计表或万能拦截平台。

## 4. 日志格式、内容与资源控制

JSON 日志包含稳定时间/服务/版本/级别、事件或错误码、消息和追踪标识；必要时关联受控业务标识。具体采用的 JSON schema、字段名和异常输出配置在工程中验证，避免多个模块各自定义不兼容格式。

- 默认不记录完整请求/响应、SQL 绑定值、聊天记录、附件原文、Cookie、令牌和密钥；错误栈和三方返回同样检查泄露。
- 用户输入作为数据安全编码，避免换行/控制字符伪造日志；诊断语句不允许拼入任意敏感材料。
- 日志有轮转、保留、总量和清理规则，控制重复错误与采集失败造成的资源压力，不能让日志占满业务磁盘。
- 敏感业务接口/下载地址不进入普通访问日志或告警原文；保留必要上下文时限定字段和访问范围。
- 生产调试级别变化受控并可追踪，避免长期全量 DEBUG。诊断包按白名单、脱敏、权限和受控导出设计，不默认包含数据库快照、秘密或原始客户材料。

Loki/Alloy 启用后也沿用来源脱敏与资源限制；集中存储不意味着可以把全部数据无约束发送。客户内网默认本地处理，需要向产品方提供诊断材料时由有权人员明确导出，不自动外发。

## 5. 指标与访问边界

Actuator/Micrometer 提供受控健康和指标能力，Prometheus 采集、Grafana 展示；管理端点不整体对公网开放，配置与日志级别等控制能力有独立访问限制。健康信息只暴露接入需要的内容，不输出秘密或内部敏感细节。

首期覆盖请求错误/耗时、数据库连接与必要资源、磁盘/存储、任务领取/失败/积压、租约/心跳异常、Outbox 积压和备份/归档/文件保护进度。主机级检查需部署层配合，不能只依赖应用自身还活着才能输出的指标。

指标标签有明确有界集合。学员/账号/任务 ID、手机号、邮箱、完整带 ID 路径和任意输入不作为无限增长标签；请求路由按模板归类。必要个体排障通过授权日志、审计或追踪关联，业务报表仍走业务查询契约。

Grafana 用于受权运维，不承担普通机构用户的租户审计查询入口；数据源、看板和查询范围按运维职责限制，不能靠界面隐藏代替授权。SaaS 与客户部署不因共用组件而混合传送敏感诊断数据。

## 6. 告警与部署层次

Prometheus 执行选定规则，Alertmanager 负责去重、分组、路由、静默与抑制，Grafana 主要展示看板；不同时无约束维护多套重复规则。告警包含必要的服务/版本/事件与处理线索，保护秘密和个人信息。

优先处理服务不可用/持续错误、资源/数据库/存储异常、任务失败与积压、Outbox 停滞、WAL 归档/备份/文件保护落后、恢复校验失败、证书到期以及重复高风险安全异常。预期的余额不足或排课冲突通常作为业务结果反馈，不直接将每次拒绝作为运维故障。

具体阈值、持续窗口、等级、接收人、通知渠道、维护静默和恢复通知未锁定。告警接收与处理属于运维职责；当前未确认 AI 自动处置，不因未来助手能力而自动授权修改系统。

SaaS 配统一指标看板与告警；客户单机版默认轻量排障能力，按资源条件启用内网监控包。发现整台业务服务器断电需要该服务器以外的检查点，同机监控不能独自提供此类外部发现保障；具体监控节点/故障域和通知通道在部署时确定。

## 7. 未来 AI/Agent 操作追溯

设计应能关联发起主体、代执行客户端/任务、委托授权、确认凭证、业务操作和最终结果，区分“谁发起”和“谁执行”。这些来自可信授权和执行上下文，模型输出的来源、确认或主体字段不构成证据。

现在保留稳定操作标识、来源与上下文扩展能力，随真实业务落实；不要求立即建立 AI 专属表、模型字段或调用平台。未来增加模型适配时再按需要关联模型/工具执行元数据，并遵守敏感信息与撤权规则，不默认记录全部提示词或聊天材料。

普通审计和日志不要求完整 OpenTelemetry 后端才能成立，未来更换采集/存储实现不应改变业务审计契约。

## 8. 保留、归档与恢复

运行日志、业务审计、指标和采样追踪分别设保留与清理规则。现有“审计保留一年”仍为待细化方向，结合用途、合同、容量和查询方式确认；不在本轮擅自锁定天数或把所有诊断数据都保留相同期限。

数据库审计随 DEC-018 的业务数据恢复范围管理，恢复后按该方案复核身份/权限和副作用。需要独立长期归档或更强篡改检测时另行设计保存与校验；普通数据库追加记录不能直接宣称防止所有高权限主体修改。

备份和监控互相提供状态，不相互替代：监控显示成功不能代替恢复演练。受控清理权限、容量和归档失败结果可观察；具体数据库索引/分区、归档介质和日志采集拓扑继续验证。

## 9. 验证与当前状态

工程和业务切片验证：成功审计同事务、回滚/拒绝独立记录、审计失败处理、租户/字段拒绝、跨线程上下文清理、敏感内容与输入安全编码、日志容量/轮转、指标标签界限、管理端点访问，以及告警分组/静默/路由和真实失败样例。

采集器不可用、磁盘不足、业务服务器不可达、客户断网和恢复后任务控制分别验证。通知渠道未确定时不能报告端到端告警已通过；只存在指标接口也不表示已经有人能收到通知。

版本/许可、JSON schema、审计动作/字段、阈值/渠道、保留、资源及 Loki/Alloy 和完整追踪平台启用条件仍需细化。当前只维护文档，没有安装组件、修改服务器、生成真实审计或执行业务/监控/告警测试；Git 按每次明确授权处理。
