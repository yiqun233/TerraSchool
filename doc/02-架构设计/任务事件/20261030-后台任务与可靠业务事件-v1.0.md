## 1. 已确认范围

DEC-009 确认采用 PostgreSQL 持久化任务与业务事件，db-scheduler 负责调度，事务 Outbox 保证业务修改与待处理事件一起提交；worker 按需独立进程运行。用户偏好优先开源，可自行补充业务界面。

调度库、消息队列与工作流引擎职责不同。当前不把 RabbitMQ、Kafka、Redis 或 Temporal 设为必需依赖；JobRunr 和 Quartz 是比较过的备选。业务任务的进度、取消、结果、权限与历史由系统掌握，不将框架表或运维后台作为产品契约。

当前只有文档确认，不创建工程、数据库、任务后台或 AI 功能。具体版本、许可与依赖兼容、参数、表结构及运行拓扑在工程建立前验证。

## 2. 同步事务、长任务与事件的边界

| 类型 | 示例 | 约束 |
| --- | --- | --- |
| 强一致业务修改 | 收款与分配、退款与流水、关课与消耗、锁月 | 同一明确业务原子边界完成，不用异步事件掩盖半成品交易 |
| 用户长任务 | 排课计算、大批量导入导出 | 先持久化任务，后台执行，结果可查询；按用例定义重试、取消与部分成功 |
| 提交后后续处理 | 课表通知、可重建统计投影、对外同步 | 业务与待处理事件同事务提交，再可靠处理；消费幂等，失败有可见状态 |

任务类型不改变业务正确性。例如退款由后台发起时，其资金写入仍须原子完成；通知失败可以独立重试，不自动撤销已发布课表。简单低风险操作不强制变成长任务。

## 3. 模型与职责

业务任务具有稳定 ID、租户归属、发起/执行身份、类型与参数版本、输入或材料引用、业务状态、当前阶段与进度、尝试历史、取消请求、错误分类、结果引用和必要时间信息；精确字段与存储类型在建模时确定。

任务状态表达真实结果，不能仅用“线程已结束”代表业务成功。进度可以按阶段表达，不伪造精确百分比；只有用例确实允许部分成功时才暴露相应状态。业务任务状态与调度尝试状态分开，调度记录清理不删除仍需保留的业务历史。

任务类型映射到受控处理器，调用模块公开业务契约；禁止任意方法名、SQL 或模型生成代码执行入口。负载优先保存稳定业务 ID 与版本化参数，不序列化整个实体、服务对象、密码或网页会话。任务处理器、参数和事件结构演进需考虑未执行旧任务，不能靠清空队列表解决升级兼容。

db-scheduler 负责领取、触发、重试安排与存活检测；业务系统负责输入校验、授权、业务幂等、进度、取消与结果。页面及未来 Agent 通过同一任务契约查询和操作，不能直接操纵调度表。

## 4. 事务一致性与 Outbox

业务修改与相应 Outbox 记录在同一个 PostgreSQL 事务中提交。派发器在提交后处理事件；可以直接调用同进程处理器或安排持久任务，未来需要时再通过适配器接消息队列。

任务接受记录及其后续调度也必须具有可靠衔接：可以在正确参与 Spring 事务的连接上一起写入调度记录，或通过持久待办扫描保证可补安排。禁止业务已提交后仅依靠一次内存回调安排任务；调用调度 API 不自动证明它加入了当前业务事务。

事件有稳定身份、类型/版本、租户、业务对象与必要顺序信息。按消费者记录完成情况，不因第一个消费者成功就将其他消费者视为完成。派发及消费允许重复，消费者以稳定身份和业务约束幂等；本地业务副作用与消费完成记录在适当事务内一致提交。必要时按业务对象处理顺序，不承诺全局总顺序。

Outbox 是可靠后续处理机制，不是把所有数据库修改改成事件溯源。保留、清理、失败重放和错误修复由明确规则管理；不能先删事件再确认必要消费者已完成。普通 Spring 事务提交后监听可用作唤醒优化，不作为唯一可靠待办存储。

官方依据：[db-scheduler 事务注意事项与示例](https://github.com/kagkarlsson/db-scheduler)、[Spring 事务事件](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)。集成时必须验证真实事务边界，不以官方支持替代项目验证。

## 5. 幂等、恢复与旧执行者保护

按可能重复执行设计，不承诺外部调用天然恰好一次。领取任务使用短事务，计算及网络等待在事务外进行；心跳或租约反映存活，不把一次领取当成永远独占。

恢复重领后，旧执行者仍可能运行。用执行代次/凭证、版本或其他经验证协议，在业务写入的原子边界检查执行资格，检查影响行数，禁止旧执行者覆盖新结果。调度库的单次领取协调不自动提供跨全部业务副作用的最终保障。

关键写操作复用既有持久化业务幂等身份；重试不能重新生成身份而重复入账或重复导入。任务和结果的幂等查询仍检查当前权限。

临时网络故障按上限和退避策略重试；数据不合法、权限不足、排课无解等返回明确结果，不盲目重试。按任务类型允许重新计算或从显式检查点恢复，不承诺所有算法都可在任意指令处续跑。尝试耗尽后进入可见失败处置，人工重试也须鉴权。

对外调用采用对方支持的幂等键与结果核对协议；若发生“对方可能成功但本地未收到响应”，应记录不确定结果并核对，不能靠本地去重表或数据库执行凭证保证外部不重复。对方不支持幂等时，明确人工处置或重复风险边界。

## 6. 取消与排课提交

取消请求与已经取消分别记录。等待任务可以阻止领取，运行任务在可取消阶段检查请求；不得以强杀线程代表安全回滚。已提交业务通过对应撤销、冲销或新业务操作处理。

排课在明确输入及资源版本下计算，提交草稿时重新检查资源、冲突、任务执行资格和当前授权。计算不持有长业务事务，提交时通过数据库约束与并发协议防止双重占用。

多班排课保留旧系统整批失败回退的业务边界，不能因为任务分步骤执行就默认保存半份有效课表；临时计算产物与正式可用草稿分开。导入是否允许分批或部分成功按对应业务规则定义，不把排课规则全局套用到所有任务。

草稿、发布和通知继续分开，未来 AI 只能按既有授权保存草稿，发布和通知另行确认。取消、失效与版本冲突的具体交互在功能设计中细化。

## 7. 租户、身份与 worker

任务与事件具有明确租户和执行身份。用户委托任务执行时重新检查租户、账号、权限及未来委托是否有效；系统后续处理使用明确受限的服务身份和业务规则，不自动继承平台全权。

调度扫描需要受限的基础设施路径，只允许必要的调度元数据访问；进入业务处理后绑定单租户应用上下文和实际事务连接，遵循 RLS。不能为扫描方便给普通业务连接赋予 BYPASSRLS。具体数据库角色、表分类及派发路径在实现前验证。

CPU 密集排课、文件处理和通知分别设置并发与资源边界，配置租户配额/公平策略，防止单客户占满系统。worker 可和应用一起部署，也可按负载独立运行，复用模块契约，不复制业务规则；具体进程拓扑不在本次锁定。

客户内网版使用相同可靠执行机制，内部任务不依赖公网队列。公网通知或外部渠道不可达时明确暂停、失败或重试边界。未来 AI 模型等待也不占用长事务，聊天窗口不是任务状态的唯一来源；主动巡检需求仍未确定。

## 8. 比较与未选方案

| 方案 | 价值 | 本轮取舍 |
| --- | --- | --- |
| db-scheduler + PostgreSQL | 嵌入式持久调度与故障恢复，复用已有存储 | 已选；业务任务界面、历史及授权自行维护 |
| JobRunr | 内置重试与监控界面，支持数据库存储 | 未选；开源/Pro 分层、事务插件与客户部署许可需额外评估，用户偏好开源和自行补业务界面 |
| Quartz | JDBC 集群、触发器与定时调度 | 未选；当前重点是用户任务，未体现复杂日历规则的必要性 |
| RabbitMQ | 消息路由、确认和消费者分发 | 后续按跨服务分发需求评估，不能代替业务任务状态或数据库 Outbox |
| Kafka | 持久事件流与多个消费者的回放处理 | 当前没有必须引入事件流平台的明确需求 |
| Temporal | 持久多步骤流程与历史重放 | 后续复杂长流程/Agent 编排再评估，自建服务与流程版本管理增加成本 |

官方依据：[JobRunr 功能](https://www.jobrunr.io/en/documentation/)、[JobRunr Pro 事务插件](https://www.jobrunr.io/en/documentation/pro/transactions/)、[生产集群许可说明](https://www.jobrunr.io/en/understanding-your-license/)、[Quartz 集群](https://www.quartz-scheduler.org/documentation/quartz-2.3.0/configuration/ConfigJDBCJobStoreClustering.html)、[RabbitMQ 可靠性](https://www.rabbitmq.com/docs/reliability)、[Kafka 定位](https://kafka.apache.org/41/getting-started/introduction/)、[Temporal 自建](https://docs.temporal.io/self-hosted-guide)。这些是能力/取舍依据，不是已完成的本项目性能或安全评测；第三方版本与许可正式引入时重新核验。

## 9. 实现验证与待细化项

首次真实用例验证至少覆盖：

- 业务回滚时不产生可执行任务/事件；提交后在安排、派发前宕机仍可恢复。
- 消费副作用成功、完成标记前宕机，重试不重复产生业务效果；多消费者状态独立。
- 多实例领取、心跳超时重领以及旧执行者恢复，旧执行者不能覆盖新结果。
- 等待/运行/提交竞态下取消，业务状态不伪装成已回滚。
- 账号/租户停用、权限撤销、跨租户任务查询/下载/重试被正确限制。
- 排课输入变化、资源竞争、无解及多班失败，按既有边界拒绝或回退。
- 任务/事件参数演进、滚动升级、无法识别的旧任务、保留与清理不会静默丢失待办。
- 负载隔离、租户公平、失败积压、人工重放及客户内网重启恢复。

待细化：db-scheduler 与 JDK/Boot/PostgreSQL 的版本兼容；事务连接/角色及 RLS 路径；序列化、轮询与唤醒、重试/心跳/清理、执行凭证、表与索引；任务具体状态、配额、观测和运维入口。上述能力随首个真实任务实现，不预先开发通用调度平台；当前未运行业务测试。
