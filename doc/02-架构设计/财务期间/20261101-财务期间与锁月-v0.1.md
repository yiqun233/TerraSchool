## 为什么需要锁月

前几批已经把收款、分配、消费、退费做成不可重算的事实，但**没有任何机制阻止写入历史月份**：财务结账后仍然可以补记上月的收款、关闭上月课次、退上月课时，导致已出的报表与账目被改写。锁月就是这条"历史不可回写"的闸门。

## 期间口径（首版）

- **自然月**，格式 `YYYY-MM`；
- 事实按**业务日期**归属期间：

| 事实 | 归属日期 |
| --- | --- |
| 确认收款 | 收款日期 `occurred_on` |
| 撤销收款 | 原收款日期 |
| 分配 / 释放分配 | 所属收款的日期 |
| 退课时、准备现金退款、确认已付 | 操作当日 |
| 课次消费（关闭课次） | 课次的上课日期 |

- 未登记的期间视为开放；只有显式锁定的月份才拦截写入。
- **不为了绕过锁定而改日期**：服务端不接受调用方自报日期来"挪月"，退费类事实一律按服务端当日判断。

## 规则

1. 锁定：把某学校某月置为 `LOCKED`；重复锁定幂等，不报错。
2. 解锁：必须携带版本号与原因，且该月当前确实处于锁定状态；版本不符返回 `VERSION_CONFLICT`，未锁定返回 `PERIOD_NOT_LOCKED`。
3. 拦截：无论从页面、接口还是服务内部调用，写库前统一经过期间闸门，命中返回 `409 PERIOD_LOCKED`。
4. 查询不受影响：锁月只阻止写入，历史数据照常可读、可对账。
5. 审计：锁定与解锁都写 `audit.period_event`，记录动作、期间、原因与操作人。

## 契约

| 操作 | 契约 |
| --- | --- |
| 能力 | `GET /api/finance/capabilities` |
| 期间列表 | `GET /api/finance/periods?schoolId&year`（固定返回 12 个月） |
| 锁定 | `POST /api/finance/periods/{period}/lock`（`schoolId`、`reason`） |
| 解锁 | `POST /api/finance/periods/{period}/unlock`（`expectedVersion`、`reason`） |

权限：`PERIOD_READ` 查看，`PERIOD_LOCK` 锁定与解锁。

## 影响面

`funds` 与 `teaching` 都依赖 `finance`（单向，无环）：

- `funds`：确认收款、撤销收款、分配、释放分配、退课时、准备现金退款、确认已付；
- `teaching`：关闭课次（按上课日期）。

因此"锁了 3 月"会同时拦住 3 月的收款、消费与退费，而不只拦住某一个模块。

## 已知边界

- 财务月若与自然月不同（例如 26 日至次月 25 日为一个期间），首版不支持，需要扩展期间定义与归属规则；
- 期末结账的差额结转、期间重开的多级审批、跨期调整单：未实现；
- 锁月不影响已有事实的金额，也不做"锁定前校验"（例如未分配完的收款不会在锁定时报错）；
- 未对锁定月份做导出/报表快照，报表能力仍待后续批次；
- 时区统一按服务端本地日期判断"当日"，未引入机构级时区配置。

## 兼容性

既有测试与演示数据都未锁定任何月份，因此行为不变。演示账号预置了 `PERIOD_READ`/`PERIOD_LOCK`，可在「财务期间」页面直接锁定当月验证拦截效果；解锁后即可恢复写入。
