## 1. 为什么现在要单独设计

业务基线 BASE-04 早已写明「平台运营身份独立」，功能清单 REQ-A01 也把「租户开通、套餐、订阅、配额」
列为 P0，`AGENT.md` 第 6 节要求「平台跨租户操作使用独立入口与明确授权」。也就是说**方向和范围
没有漏**，缺的是落地：现在没有任何字段、接口、页面能完成一次真实开通。

实际现状（2026-11-06 核对代码）：

| 问题 | 现状 |
| --- | --- |
| 谁在开通租户 | 只能跑脚本 `tools/ops/bootstrap_admin.py`，界面没有 |
| 平台身份 | 不存在。`identity.account` 的账号一定挂某一个 `tenant_id`，登录查询是 `account join tenant` |
| 开通产物 | 一个租户 + 一所学校 + 一个管理员（脚本强制要求先有校名） |
| 管理员权限 | 脚本直接授予**全部动作 + 全部字段**，不是岗位角色模板 |
| 幂等 | 没有。重复执行靠 `select ... where name=` 兜底拒绝 |
| 审计 | 没有平台侧记录 |
| 停用 | `identity.tenant.active` 字段存在，但没有入口修改 |

这个方案要解决的就是这几行。

## 2. 边界

### 2.1 本方案负责

1. **平台身份**：独立的账号体系、独立登录入口、独立会话、独立权限目录、独立审计。
2. **租户开通**：一次界面操作产出**租户 + 租户管理员账号**，不含学校——现实中签约时往往还不知道客户要在哪个校区开课，学校由客户登录后自己建。
3. **租户列表与停用/恢复**：平台只看到开通与状态信息。

### 2.2 本方案明确不做

1. **平台账号不读取租户业务数据**（本次已确认的先期边界）。平台只看到：租户名、编码、状态、
   开通时间、学校数、账号数、用量计数。业务明细（学员、报名、收款、课次）一律不可见，也不提供
   「以租户身份登录」的模拟入口。
2. **不做租户删除**。只停用，数据保留；删除与导出属合规议题（Q82）。
3. **不做套餐计费**。配额先只记录不限制（Q79）。
4. **不改租户内权限模型**。平台只在开通时给管理员一个初始角色模板。

## 3. 平台身份

### 3.1 为什么用独立表而不是给 `identity.account` 加标记

- `identity.account.login` 在部署内全局唯一，登录查询按 `account join tenant` 走，平台账号没有租户；
- 业务表全部启用 `FORCE ROW LEVEL SECURITY` 且按 `app.tenant_id` 过滤，平台账号没有租户上下文；
- 加标记意味着「同一个账号表里混两种授权模型」，越权和审计混淆的风险比多一张表高得多。

结论：**平台账号独立成表、独立 schema、独立数据库角色**（DEC-024）。

### 3.2 数据模型

```sql
CREATE SCHEMA IF NOT EXISTS platform;

-- 平台运营账号：与租户账号物理隔离，登录名只在平台内唯一
CREATE TABLE platform.operator (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  login varchar(60) NOT NULL UNIQUE,
  password_hash varchar(200) NOT NULL,
  display_name varchar(100) NOT NULL,
  active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
  last_login_at timestamptz
);

-- 平台动作目录（不进入租户权限目录）
CREATE TABLE platform.operator_permission (
  operator_id uuid NOT NULL REFERENCES platform.operator(id),
  action varchar(60) NOT NULL,
  effect varchar(10) NOT NULL DEFAULT 'ALLOW' CHECK (effect IN ('ALLOW','DENY')),
  PRIMARY KEY (operator_id, action)
);

-- 平台审计：独立表，不写 audit.*（那是租户审计）
CREATE TABLE platform.audit_event (
  id uuid PRIMARY KEY DEFAULT uuidv7(),
  operator_id uuid NOT NULL,
  action varchar(60) NOT NULL,
  tenant_id uuid,                         -- 目标租户，可空（如登录）
  changed_fields varchar(400) NOT NULL DEFAULT '',
  trace_id uuid NOT NULL,
  happened_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

会话沿用现有 Spring Session 机制，但**表与 Cookie 都独立**：`platform.operator_session`、
Cookie 名 `TS_PLATFORM_SESSION`，与租户会话互不覆盖。

### 3.3 数据库角色（这是「不看业务数据」的技术保证）

新增受限角色 `ts_platform`：

```sql
CREATE ROLE ts_platform LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS;
GRANT USAGE ON SCHEMA platform TO ts_platform;
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA platform TO ts_platform;
-- 只读开通所需的 identity.tenant / organization.unit 计数，且不加 RLS 绕过
GRANT SELECT ON identity.tenant TO ts_platform;
```

**不授予任何 `teaching.* / enrollment.* / funds.* / archive.*` 权限**。平台接口即使被改坏，
数据库也会拒绝——不依赖应用层自觉。

平台需要「重置租户管理员密码」时，不能因此给 `ts_platform` 开 `UPDATE identity.account` 全表权限
（那样等于能改任意账号）。做法是一个窄接口函数：

```sql
CREATE FUNCTION platform.reset_tenant_admin_password(
  target_tenant uuid, target_login varchar, new_hash varchar, require_change boolean)
RETURNS boolean LANGUAGE plpgsql SECURITY DEFINER SET search_path = pg_catalog, identity AS $$
  -- 只允许改“该租户内 tenant_admin=true 且 active”的账号的凭据列；
  -- 返回是否命中，未命中即拒绝。
$$;
REVOKE ALL ON FUNCTION platform.reset_tenant_admin_password FROM PUBLIC;
GRANT EXECUTE ON FUNCTION platform.reset_tenant_admin_password TO ts_platform;
```

函数体内只写 `password_hash`、`password_change_required`、`credential_version`，不碰其它列；
`ts_platform` 拿不到 `identity.account` 的直接写权限。

**这段只是应用内部的落库方式，运维人员不需要执行任何 SQL。** 平台界面上点一次「重置密码」即完成；
之所以不直接给表权限，是为了让“平台能改密码”这件事的权限范围恰好等于它需要的那几列，
而不是把整张账号表交出去。

### 3.4 登录与过滤链

- 独立入口 `/api/platform/session/login|logout|me`。
- Spring Security 两条独立过滤链：`/api/platform/**` 只认平台会话；`/api/**` 不认平台会话。
- 平台会话调业务接口必须得到 401/403，这条要写成测试。
- 不提供「平台账号切换到某租户」的能力。

### 3.5 平台动作目录（首版）

| 动作 | 含义 |
| --- | --- |
| `TENANT_READ` | 查看租户列表与详情（仅状态与计数） |
| `TENANT_CREATE` | 开通新租户、重置租户管理员密码 |
| `TENANT_BRANDING_WRITE` | 平台代改/回滚租户品牌（V88 起独立，不与开通复用） |
| `TENANT_SUSPEND` / `TENANT_RESUME` | 停用 / 恢复 |
| `PROVISIONING_READ` | 查看开通记录与失败原因 |

## 4. 租户开通

### 4.1 目标：一次界面操作得到「能登录、能自建学校」的租户

开通一个租户，必须在**同一个事务**里产出以下内容；缺任何一项都视为失败：

1. `identity.tenant`：名称、状态 `ACTIVE`、创建时间（当前无编码列，见 Q78）；
2. 该租户的**管理员账号** `identity.account`（登录名部署内全局唯一，初始密码一次性生成）；
3. 把该账号标记为**租户管理员**（见 4.2）：租户内权限最大，且不依赖“先有学校”；
4. `platform.provisioning_request` 记录（请求身份、摘要、状态、结果）；
5. `platform.audit_event` 一条开通审计。

**不创建学校。** 学校、校区、部门、员工、角色都由客户在租户内自己建。

### 4.2 租户管理员与「零学校」问题

现有授权模型有个硬限制：`SchoolProvisioner.provision()` 要求调用者是「覆盖全部学校的权限管理员」，
而 `full()` 在 `manageableSchoolIds` 为空时直接返回 false。也就是说，**没有任何学校的租户，
其管理员建不了第一所学校**——先建租户再建学校的流程会被卡死。

草案的处理办法（需在实施前确认）：

1. `identity.account` 增加租户管理员标记（`tenant_admin boolean`），`CurrentPermissions` 增加同名字段；
2. `full()` 改为：`tenant_admin` 直接为真；否则仍按“覆盖全部学校”判断，空集不自动放行；
3. 租户管理员的动作与学校范围**动态全量**：动作取目录全量（以后新增的功能自动包含），
   学校范围取本租户当前全部学校（含以后新建的），不依赖建校时写入的规则行，见
   [权限界面与动作目录方案](../身份权限/权限界面与动作目录方案.md) 6.4；
4. 租户管理员不可被删除或降级到无人，保留现有 `LAST_AUTHORIZATION_ADMINISTRATOR` 保护；
5. 该标记只在租户内生效，跨租户仍然拒绝。

这样「权限最大的管理员」有明确边界：**覆盖本租户全部学校（含将来新建的），不是跨租户，也不是数据库超管**。

### 4.3 状态机

```text
(无) --提交--> PROVISIONING --成功--> ACTIVE
                     |
                     +--失败--> FAILED（可用同一 requestId 重试）
```

`identity.tenant.active` 仍是唯一的生效标志；不新增与之并存的「状态」字段，避免两个真相源。
开通中/失败的租户通过 `platform.provisioning_request.status` 表达，此时 `tenant.active=false`，
不会被登录查询命中。

刚开通的租户是「有管理员、无学校」的合法状态：管理员能登录、能建学校，但没有学校时任何业务
接口都会因为没有可读学校而拒绝，这是预期行为，不是缺陷。

### 4.4 幂等与并发

- 请求身份 `requestId` + 参数摘要（租户名、管理员登录名）一起持久化；
- 同 `requestId` 重试：参数一致则返回原结果，不一致则拒绝并说明差异；
- 同一租户名 / 编码 / 登录名并发提交：靠唯一约束拦截，返回可读冲突错误，不产生第二个租户。

### 4.5 失败与回滚

- 编排全程一个事务；任一步失败整体回滚，数据库里不留「有租户没管理员」的半成品；
- 若失败发生在密码生成后，初始密码作废，重试时重新生成；
- 失败原因写成稳定错误码 + 可读文案（例如 `TENANT_NAME_TAKEN`、`LOGIN_TAKEN`、`WEAK_PASSWORD`）。

### 4.6 账号交付与密码

1. **自动生成初始密码**：开通时由服务端生成强随机密码（建议 16 位，含大小写/数字），
   只以 bcrypt（现有 `PasswordEncoderFactories` 口径）落库，**明文只在开通响应的那一次返回**，
   不写日志、不进审计变更明细、不可再次查询。
2. **一次性显示**：平台页面展示后可复制发给客户；页面离开即失效。丢失只能走重置。
3. **首次登录强制改密**：账号带 `password_change_required` 标记。登录成功后会话进入
   「仅可改密」的受限状态——除改密、查看本人信息、退出以外，其它业务接口一律拒绝；
   改密成功清除标记并吊销该账号其它会话。
4. **密码策略**（首版）：长度 ≥ 12、不得与登录名相同、不得为纯数字或纯字母；
   与登录名同名的初始密码直接拒绝。
5. **平台可修改租户管理员密码（首版已定）**：在平台界面上对**该租户的租户管理员账号**
   （含开通时交付的初始管理员）执行一次「重置密码」，无需运维接触数据库。两种方式：
   - **生成随机密码**（默认）：服务端生成 16 位强随机密码，一次性显示；
   - **手工指定密码**：由平台人员填写，必须通过同一套密码策略校验。
   两种方式都会——把密码置回「首次登录强制改密」、吊销该账号全部既有会话、写平台审计。
   平台能看到该租户 `tenant_admin` 账号的登录名、状态与最后登录时间；这是执行操作所必需，
   仍不属于业务数据。
6. **客户自助找回**（后续）：绑定手机号后通过短信验证码自助重置；依赖短信供应商（Q43），
   当前未实现，见 Q83。在此之前客户丢密码只能联系平台重置。

### 4.7 首次进入引导

新租户管理员登录后没有任何学校。**不做持久化的“引导状态”字段**，用派生条件判断：

- 条件：本租户 `organization.unit` 中不存在 `kind='SCHOOL'` 的记录；
- 表现：进入后展示引导页，说明三步——① 建学校 ② 建校区/部门 ③ 加员工并分配角色，
  每一步有直达按钮；同时说明“学校建好之前，业务菜单不可用”；
- 可跳过；跳过不记录状态，下次登录仍按派生条件展示；
- 建好第一所学校后条件不成立，引导自动消失。

这样避免了新增一个可能与事实不一致的“已引导”标记。

### 4.8 停用与恢复

- 停用：`identity.tenant.active=false`（由 `platform.set_tenant_active` 执行）；立即影响登录查询（现有登录已 join tenant 校验 `t.active`）。填原因与版本号尚未落地。
- 恢复：`active=true`，记录审计。
- 停用不影响已产生的业务数据；后台任务（客户自动回收、导出任务）已经按 `tenant.active` 过滤，无需额外改动。

## 6. 页面（平台运营后台）

**本端是[界面与交互规范](../../03-研发规范/界面与交互规范.md)的第一批执行页面。** 页面按该规范做，
不复用租户管理端的布局与导航，也不做“能点就行”的临时界面。三条具体落地要求：

1. 开通表单分两步呈现：先填租户与管理员信息，提交后进入结果页（展示一次性初始密码 + 复制按钮 +
   「离开后无法再次查看」提示），不再回到空表单；
2. 租户列表的四态齐全：加载、空（尚无租户，给“开通第一个租户”入口）、错误（可重试）、
   无权限（说明缺 `TENANT_READ`）；
3. 停用与重置密码都是危险操作：二次确认写清后果（“停用后该机构所有人无法登录”“重置后对方须立即改密”）。


独立入口与独立布局，不复用租户管理端；页面清单如下（REV-021 已完成首版）：

| 页面 | 要点 |
| --- | --- |
| 登录页 | 平台账号专用，不显示租户信息 |
| 租户列表 | 名称/编码/状态/开通时间/学校数/账号数；按状态与关键字筛选 |
| 开通表单 | 租户名、管理员登录名、初始密码（或自动生成并一次性展示）；提交后展示进度与结果，失败给出可读原因与重试入口 |
| 租户详情 | 状态、开通记录、停用/恢复 |
| 操作按钮 | 按平台动作目录显隐，后端二次校验 |

## 7. 与现有实现的差异与迁移

| 项 | 现状 | 目标 |
| --- | --- | --- |
| 开通入口 | 脚本 | 界面 + 脚本共用同一应用服务 |
| 管理员授权 | 全部动作 + 全部字段 | 「学校管理员」角色模板 |
| 幂等 | 无 | requestId + 摘要 |
| 审计 | 无 | `platform.audit_event` |
| `identity.tenant` 列 | id/name/active | 实际只增 `created_at`；`code`、`provisioned_at`、`suspend_reason`、`version` 未落地（Q78 跟踪） |

迁移落点（实际占用 `V81`～`V88`，均已执行）：

- `identity.tenant` 仅新增 `created_at`；`code`、`provisioned_at` 未加，租户编码至今无列（Q78）；`active` 保持原值；
- 新建 `platform` schema 与三张表；
- 新增 `ts_platform` 角色并授权；
- 已有库不需要 `flyway repair`（新版本号新增，不改旧迁移）。

脚本 `bootstrap_admin.py` 改为调用同一开通服务，保留为应急通道；不再直接授予全部动作。

## 8. 验收口径（「真实业务效果」怎么算达到）

1. **从零到能干活**：有平台账号的前提下，界面上完成一次开通；新租户管理员在 **5 分钟内**登录，
   然后自行创建第一所学校并看到它出现在学校列表里。全程不跑脚本、不改库、不需要平台再次介入。
2. **不留半成品**：故意制造失败（租户名重复、登录名冲突、密码太弱）后，库里不出现半开通租户。
3. **幂等**：同一 `requestId` 重复提交只产生一个租户；改参数重试被拒绝并说明差异。
4. **隔离**：用平台会话调用任意 `/api/**` 业务接口必须 401/403；平台列表与详情响应里不出现
   学员姓名、电话、金额等业务字段。
5. **零学校可用**：新开通、还没有学校的租户，管理员能登录、能建第一所学校；建校后自动获得该校
   的组织/员工/教师/教室/授权权限，且不需要平台或运维再介入。
6. **停用生效**：停用后该租户账号立即无法登录；恢复后可登录；两次操作都有审计。
7. **审计可查**：按租户能查到开通、停用、恢复记录，含操作者、时间、请求身份。
8. **账号交付闭环**：开通响应里能拿到一次性初始密码；该密码登录后必须改密，改密前调业务接口被拒；
   平台重置后旧会话立即失效、新密码仍强制改密。
9. **空租户有引导**：没有学校的租户登录后看到引导页与三步入口，建校后引导自动消失。

## 11. 已知风险

1. **看得到的诱惑**：一旦有平台后台，很容易顺手加「查看租户数据」按钮。本方案在数据库角色层面
   掐断，后续要放开必须新开设计，不能改一行授权就放行。
2. **初始密码传递**：一次性展示是权宜之计；正式方案应结合邮件/短信（短信供应商未定，Q43）。
3. **脚本与界面双入口**：必须共用同一服务，否则会出现两套开通语义。
4. **「权限最大」的边界**：租户管理员是“覆盖本租户全部学校”，不是跨租户、也不是数据库超级用户；
   实施时必须用测试证明它调不到别的租户，也不能绕过 RLS。
5. **初始密码的传递链路**：一次性显示意味着平台人员短暂持有客户密码。正式做法是客户自助激活
   （需要短信/邮件，Q43/Q83），首版靠“强制改密 + 平台审计 + 平台重置”控制风险。
6. **平台改密是一项实质权力**：能改租户管理员密码，等于能在客户不知情时接管该租户。
   首版不做双人复核（已确认），以“强制改密 + 吊销旧会话 + 平台审计”控制；平台账号仅限少数人持有，
   人员范围与交接流程见 Q77。
